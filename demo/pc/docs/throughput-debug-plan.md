# ESP32 数据链路分层修复与测试计划

## 1. 目标

定位并修复 MCU 持续上传时出现的以下问题：

- `MCU 数据入队失败`，数据块被丢弃；
- `pong` 序号滞后或不匹配；
- TCP 数据积压、重连或误判心跳超时；
- 上位机接收、落盘或设备端发送队列成为瓶颈。

测试原则：每轮只修改一层，固定其他条件，保留日志和数据文件，确认效果后再进入下一层。

## 2. 固定测试条件

每轮测试前记录：

- ESP32 固件版本、提交号和编译时间；
- 上位机版本、提交号和构建配置；
- MCU 波特率、单帧长度、每秒帧数和理论字节率；
- WiFi 距离、热点配置和 RSSI；
- 测试持续时间，建议每轮至少 5 分钟；
- 实际烧录源码中 `MCU 数据入队失败` 对应的函数和队列。

每轮至少记录：

| 指标 | 说明 |
| --- | --- |
| MCU 理论输入字节/秒 | 根据帧长和帧率计算 |
| ESP32 串口接收字节/秒 | 判断 MCU 到 ESP32 是否正常 |
| ESP32 TCP 发送字节/秒 | 判断设备网络出口能力 |
| 上位机 recv 字节/秒 | 判断网络接收能力 |
| 上位机落盘字节/秒 | 判断磁盘消费者能力 |
| 各级队列当前/峰值水位 | 判断具体堵塞层 |
| 丢弃字节数 | 判断数据完整性 |
| 首次丢弃时间 | 判断积压速度 |
| ping/pong 最大延迟 | 判断控制面是否受数据面影响 |
| TCP 重连次数 | 判断链路稳定性 |

## 3. 第一层：增大上位机单次接收缓冲

### 修改

将在线连接单次 `recv` 缓冲从 512 字节提升至 4096 字节。

### 测试

保持 ESP32 固件和 MCU 输出不变，连续测试 5 至 10 分钟。

### 观察

- `MCU 数据入队失败` 是否消失或明显减少；
- `pong` 序号滞后是否减少；
- 上位机落盘文件是否持续增长；
- TCP 是否发生重连。

### 判断

- 完全正常：原 512 字节读取限制是主要瓶颈，继续第二层验证稳定性；
- 有改善但仍丢数据：继续第二层；
- 无改善：优先执行第三层，确认设备内部具体哪一级队列满。

## 4. 第二层：单轮有预算地排空 Socket

### 修改

每次 `Poll` 对在线 socket 连续调用 `recv`，直到满足任一条件：

- 返回 `DEMO_ERR_AGAIN`，表示当前内核接收缓冲已经排空；
- 单轮累计读取达到 256 KiB；
- 连接关闭或发生致命错误。

设置 256 KiB 预算是为了兼顾吞吐和公平性，防止持续数据流长期占用轮询线程，使发送队列、心跳判定和停止请求得不到处理。

### 测试

保持设备端不变，连续运行至少 10 分钟。

### 通过标准

- 上位机接收速率高于 MCU 平均生产速率；
- ESP32 入队失败为 0；
- 不再连续出现 `pong` 序号滞后；
- 上位机 UI 正常响应；
- 串口落盘字节数与理论输入字节数接近；
- CPU 占用处于可接受范围。

## 5. 第三层：确认具体满队列

先在实际烧录固件中定位 `MCU 数据入队失败` 日志，确认它属于：

1. UART RingBuffer；
2. 运行时命令队列；
3. 协议发送队列；
4. 其他自定义队列。

只增加每秒汇总统计，不修改容量：

```text
UART: rx_bytes/s, ring_used/ring_capacity, dropped_bytes
CMD:  count/capacity, push_failures
TX:   count/capacity, queued_bytes, enqueue_failures
TCP:  sent_bytes/s, EAGAIN次数, partial_write次数
```

避免每块数据都打印日志，大量日志本身可能影响设备实时性。

### 判断矩阵

| 现象 | 最可能的问题 |
| --- | --- |
| UART RingBuffer 满，CMD/TX 空 | 串口消费者调度不足 |
| CMD 队列满，TX 队列空 | 设备主循环处理命令太慢 |
| TX 队列满，`send EAGAIN` 多 | TCP、WiFi或上位机背压 |
| TX 队列满，`send EAGAIN` 少 | 发送队列冲刷调度异常 |
| 所有队列瞬间满后恢复 | MCU 突发输出过大 |
| 上位机 recv 快但 TCP 发送慢 | WiFi质量或 lwIP 参数限制 |

## 6. 第四层：控制面优先

将控制帧和数据帧分开调度：

- 高优先级：`device_hello`、`ping`、错误响应；
- 低优先级：`SERIAL_BYTES`；
- 控制队列预留固定容量，数据帧不得占用；
- 每发送若干数据帧后优先检查控制队列。

建议初始参数：

```text
控制队列容量：8
数据队列容量：32或64
每发送8个数据帧检查一次控制队列
```

### 通过标准

- 数据拥塞时心跳仍及时响应；
- 不因数据积压误判离线；
- 控制队列不溢出。

## 7. 第五层：聚合设备数据块

将多个小串口块合并后再封装为 `SERIAL_BYTES`：

```text
达到4096字节立即发送
或等待5至10ms后发送当前残留
```

依次测试 512、1024、4096、8192 字节聚合块。

### 通过标准

- 无入队失败；
- ESP32 内存稳定；
- TCP 吞吐提高；
- 数据延迟符合业务要求；
- 心跳不受影响。

建议优先使用 4096 字节作为起点。

## 8. 第六层：上位机接收与落盘解耦

当前网络轮询线程同步调用数据接收器并执行文件写入。改为：

```text
网络线程 recv
    ↓
有界内存队列
    ↓
独立落盘线程批量 fwrite
```

要求：

- 网络线程只复制数据并快速返回；
- 落盘线程按 64 KiB 或 20ms 批量写入；
- 队列必须有最大容量；
- 统计落盘队列水位和写入速度；
- 退出时停止接收、排空队列并 flush。

### 通过标准

- 磁盘短时变慢不影响心跳；
- 网络接收速率保持稳定；
- 落盘队列不会持续增长；
- 文件字节数与接收字节数一致。

## 9. 第七层：MCU 到 ESP32 背压

如果要求长时间连续采集且不允许丢数据，必须加入流控。优先级：

1. UART RTS/CTS 硬件流控；
2. MCU 协议 `PAUSE_UPLOAD` / `RESUME_UPLOAD`；
3. 降低 MCU 采样频率；
4. 扩大队列仅作为吸收短时突发的辅助方案。

建议高低水位：

```text
发送队列达到75%：通知MCU暂停
发送队列降至25%：通知MCU恢复
```

### 测试

人为让上位机停止读取 3 至 10 秒后恢复。

### 通过标准

- 停止读取期间设备不丢数据；
- ESP32 队列不溢出；
- MCU 正确暂停；
- 恢复后积压数据逐步发送完毕；
- MCU 自动恢复上传。

## 10. 第八层：调整心跳判定

数据面稳定后再调整心跳，避免用放宽超时掩盖吞吐问题。

建议初始参数：

```text
heartbeat_interval = 2秒
heartbeat_dead = 8至10秒
```

序号判断规则：

- `pong.seq` 属于当前未确认序号集合：有效；
- `pong.seq` 小于最近确认序号：重复或严重迟到；
- `pong.seq` 大于已发送最大序号：协议错误；
- 不应只与最新 `ping_seq` 比较。

### 通过标准

- 短时拥塞不误判离线；
- 真正断线能在预期时间检测；
- 迟到 `pong` 被记录但不触发错误重连。

## 11. 推荐执行顺序

1. 4096 字节接收缓冲；
2. 单轮有预算地连续 `recv` 到 `EAGAIN`；
3. 添加设备各级队列和 TCP 统计；
4. 控制帧优先级；
5. ESP32 聚合 4096 字节数据块；
6. 上位机接收和落盘线程解耦；
7. MCU 暂停/恢复流控；
8. 最后调整心跳判定。

每一层通过后保留修改和测试记录，再进入下一层。即使第二层已经消除当前故障，也建议至少完成第三层统计；若业务要求绝不丢数据，还必须完成第七层流控。
