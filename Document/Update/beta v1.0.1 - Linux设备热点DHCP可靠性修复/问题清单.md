### 置顶区（已关闭）

#### Q1. AP 网段冲突时应拒绝启动还是自动选择备用网段

- 问题描述：当前默认 AP `192.168.1.1/24` 与本机 STA `192.168.1.18/24` 已确认重叠。固定改为 `10.42.0.1/24` 能解决当前现场，但未来仍可能与 STA、VPN、容器或其他本机路由重叠。冲突后的行为决定配置契约、日志、测试范围和后续可用性。
- 建议方案：采用“固定首选网段 + 自动选择候选网段”。首选 `10.42.0.1/24`，依次尝试 `10.43.0.1/24`、`172.31.250.1/24`、`192.168.250.1/24`；启动前与本机所有有效 IPv4 直连路由比较，选择首个不重叠网段。日志必须打印配置网段、冲突对象和最终选中网段；所有候选均冲突时拒绝启动。
- 备选方案 A：固定 `10.42.0.1/24`，检测冲突后直接拒绝启动。行为最可预测，但现场网络碰巧使用 `10.42.0.0/24` 时设备无法配网，需要人工改配置。
- 备选方案 B：仅修改为固定 `10.42.0.1/24`，不增加冲突检测。不推荐，无法防止同类问题复发，不满足建议文档验收标准。
- 风险预警：自动选段会使真实 AP 地址不固定，协议和日志必须明确真实端点来自 DHCP router；但当前 PC 已按 DHCP router 动态获取设备地址，业务协议无需新增字段。
- 置信度：85%。
- 归入置顶原因：这是影响配置格式、地址选择算法、协议文档和大量测试用例的重大技术路线，选择错误会导致阶段二和阶段三大范围返工。

回复：按照建议方案来

#### Q2. 防火墙规则由设备程序还是部署环境负责

- 问题描述：`demo/net_linux/linux_hotspot.c` 当前只管理 NAT `POSTROUTING MASQUERADE`，不放行或检测 `ap0` UDP 67、UDP 68 和 TCP 5935。目标系统可能使用 iptables、nftables、firewalld 或 ufw；应用直接改全局规则可能与系统策略冲突。
- 建议方案：由部署环境负责防火墙策略；设备程序不创建 INPUT/OUTPUT 放行规则，只记录明确的端口要求并执行可观察的 readiness 检查。验收环境需保证 `ap0` UDP 67 和 TCP 5935 可达，验收报告保留 iptables/nftables 状态和 DHCP 抓包证据。
- 备选方案：设备程序使用带 `modu-provision` 标识的专用 iptables 规则，并在停止时精确删除。优点是 Demo 自包含，缺点是不能可靠覆盖 nftables/firewalld 最终策略，且增加全局网络副作用。
- 风险预警：若选择部署层负责但部署配置缺失，程序只能通过日志和抓包定位，不能自行修复防火墙阻断。
- 置信度：80%。
- 归入置顶原因：这是产品部署与应用代码之间的责任边界，直接决定是否修改系统防火墙及其清理契约，必须由用户确认。

回复：按照建议方案来吧，而且请你现在解决一下这个问题，你当前就在部署环境下，只需要验证当前环境的问题就好

#### Q3. NAT 是否继续作为真实配网热点默认能力

- 问题描述：配网仅要求客户端访问设备 AP 的 TCP 5935，不要求客户端经设备 STA 上网。当前 `nat=true`，规则仅按 STA 输出接口匹配，未限制 AP 源网段，并且停止热点时不删除规则。
- 建议方案：默认关闭 NAT（`nat=false`），将其保留为显式可选能力；本版本聚焦 DHCP 和本地 TCP 配网。若用户启用 NAT，则规则必须按最终 AP 子网限制来源、具备所有权标识并在 stop 时删除。
- 备选方案：继续默认启用 NAT，同时完善源网段、IP forwarding、FORWARD 规则与生命周期清理。功能更完整，但明显扩大本次 DHCP 修复范围。
- 风险预警：关闭 NAT 后，连接设备热点的 PC 在配网期间不能通过设备 STA 访问互联网，但不影响 DHCP、TCP 5935 或 `auth -> wifi_config`。
- 置信度：85%。
- 归入置顶原因：是否提供互联网共享属于产品行为变化，并决定网络规则和验收范围，不能由实现者单方面改变。

回复：按照建议方案来

### 自决区（不阻塞阶段流）

#### Q4. 热点地址前缀是否进入配置结构

- 问题描述：当前 `demo/net_linux/linux_hotspot.c` 将 `/24` 写死，`linux_hotspot_cfg_t` 没有 prefix 字段；地址池校验和 dnsmasq 掩码也无法表达其他前缀。
- 自决方案：新增 `prefix_length`，默认 24，允许范围 16 至 30；AP 地址配置、网段计算、DHCP 掩码和日志统一使用该字段。
- 自决理由：建议文档已给出明确字段契约；消除写死 `/24` 是实现正确地址校验和冲突检测的必要前置，不涉及产品路线分歧。
- 风险预警：需补充非法 prefix、网络地址、广播地址和地址池边界测试。
- 置信度：95%。

#### Q5. 真实模式热点配置错误采用 fail-closed

- 问题描述：当前配置文件缺失、空文件或非法 JSON 时，`linux_hotspot_init()` 静默使用默认值并返回成功，可能掩盖部署错误。
- 自决方案：真实 Linux 模式下配置文件不存在、不可读、为空、非法 JSON或字段校验失败均返回错误；不创建 AP，不启动 hostapd/dnsmasq。配置字段缺省时可使用结构默认值，但配置文件本身必须有效。
- 自决理由：这是安全、可诊断且可测试的错误处理原则；真实网络配置不应静默降级。模拟模式不依赖该文件，不受影响。
- 风险预警：旧部署若依赖“文件丢失后自动用默认值”会改为显式启动失败，需要更新部署文档。
- 置信度：95%。

#### Q6. DHCP readiness 使用何种实现

- 问题描述：当前只检查 dnsmasq 命令退出码、pidfile 和进程存活，不能证明 UDP 67 已绑定到 AP 接口。建议文档提出解析 `ss` 或使用 `/proc`/netlink。
- 自决方案：当前 Demo 使用无 shell 文本依赖的 `/proc/net/udp` + dnsmasq PID fd/socket inode 关联检查；最多等待 2 秒，每 100 ms 检查一次。检查目标为该 dnsmasq 进程持有 UDP 67 socket，并结合 AP 地址/接口回读验证形成 readiness。
- 自决理由：比解析不同版本 `ss` 输出稳定，也避免把 grep/管道拼入 root shell；实现规模可控，适合 Linux Demo。
- 风险预警：UDP socket 存活仍不等于客户端能收到 DHCP，实机验收必须保留真实客户端 DHCP 四步抓包。
- 置信度：92%。

#### Q7. AP 启动失败使用已有退避参数

- 问题描述：`demo/device/device_app.c` 中 `prov_server_start()` 失败后仅睡眠 100 ms，主循环约 10 ms 后再次调用，永久错误会持续重启 hostapd/dnsmasq并刷屏。
- 自决方案：失败后记录一次事件，将 `boot_backoff_until` 设置为 `now + provision_ap_backoff_ms`，切回 `DEV_STATE_BOOT`；退避到期后才允许再次进入 AP 配网。
- 自决理由：已有参数和其他状态路径已采用同一退避语义，无需新增配置或状态。
- 风险预警：默认退避 300000 ms，现场修复配置后可能需重启设备或等待五分钟；日志必须明确下一次重试时间。
- 置信度：98%。

#### Q8. dnsmasq 必须隔离系统配置并显式声明 DHCP 契约

- 问题描述：当前命令缺少 `--conf-file=/dev/null`，可能继承 `/etc/dnsmasq.conf`；DHCP range 未显式携带掩码。
- 自决方案：增加 `--conf-file=/dev/null`，保留 DHCP-only、接口/地址绑定、authoritative、router 和 server-id；由 `prefix_length` 生成 netmask并加入 range。不得因 UDP 67 被占用而杀死系统 DHCP 服务。
- 自决理由：这是避免环境配置干扰的直接根因防护，且不改变对外协议。
- 风险预警：需确认目标 dnsmasq 版本支持所用 option 语法；启动测试必须使用设备实际版本。
- 置信度：98%。

#### Q9. 真实地址与模拟地址语义必须拆分

- 问题描述：`demo/include/protocol.h` 的 `PROTO_AP_IP` 和 `demo/协议文档.md` 当前将 `192.168.1.1` 表述为统一设备 AP 地址，但模拟后端依赖该逻辑地址，真实 Linux 应使用运行时 AP 地址及 DHCP router。
- 自决方案：共用代码将常量改名或新增为 `PROTO_SIM_AP_IP`，仅供模拟后端与模拟测试使用；真实 Linux 配网端点定义为“设备 DHCP router 地址:5935”。同步协议、设计和修复说明文档，不修改 PC 专有代码。
- 自决理由：PC 已通过网络抽象层动态获取 DHCP gateway；拆分语义能保留模拟兼容并消除真实地址硬编码误导。
- 风险预警：需全仓搜索旧常量，避免 vtable 或模拟地址翻译回归。
- 置信度：95%。

#### Q10. Linux 实机只支持单设备进程实例

- 问题描述：真实模式固定 AP 接口名、TCP 5935、hostapd/dnsmasq pidfile 和配置文件名，多实例并行必然冲突。
- 自决方案：本版本明确 Linux 真实设备模式只允许单实例；启动时检测本程序资源被占用并明确失败，不设计多实例资源命名。Windows/模拟多设备能力保持不变。
- 自决理由：一台物理设备运行一个设备进程符合当前产品语义；扩展真实多实例与 DHCP 修复无关且会显著扩大范围。
- 风险预警：测试脚本必须先清理旧实例，不能把残留进程误判为当前实例成功。
- 置信度：95%。

#### Q11. 测试与验收必须包含自动化和真实客户端两层

- 问题描述：当前测试没有覆盖 Linux 热点配置、地址池、冲突检测、dnsmasq 参数、readiness、失败回滚和资源清理；UDP 67 监听也不能替代真实 DHCP 租约验证。
- 自决方案：阶段三新增纯逻辑单元测试和可注入系统操作测试；阶段四在 Linux 实机启动设备，并使用真实 Windows PC 或其他独立无线客户端完成 DHCP 四步、合法租约、默认网关、TCP 5935 和 `auth_result` 验收。无法获得真实客户端证据时对应验收项标记阻塞，不得默认通过。
- 自决理由：符合 `Document/Agent开发规范.md` 的单元测试、启动测试和零上下文验收要求，也直接对应本次故障层级。
- 风险预警：同机 macvlan/network namespace 受无线驱动二层回环限制，不能代替独立无线客户端。
- 置信度：99%。

- 已增加持久部署规则：`allow in on ap0 proto udp to any port 67`，注释 `modu provision DHCP`。
- 已增加持久部署规则：`allow in on ap0 proto tcp to any port 5935`，注释 `modu provision TCP`。
- 已删除旧测试遗留的无源网段限制规则 `POSTROUTING -o wlP2p33s0 -j MASQUERADE`。
