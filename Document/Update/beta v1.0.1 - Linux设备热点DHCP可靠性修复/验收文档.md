# beta v1.0.1 Linux 设备热点 DHCP 可靠性修复验收文档

## 1. 验收范围

覆盖 Linux 设备端热点配置、动态选段、hostapd/AP IPv4/dnsmasq readiness、UDP 67、TCP 5935、失败退避、资源清理、可选 NAT、模拟地址回归，以及真实无线客户端 DHCP 和现有 Windows PC 配网流程。

不覆盖 PC 端代码修改、Windows 后端修改、TCP/JSON 协议变更或 Linux 真实多实例。

## 2. 验收环境

- 设备：当前 Orange Pi Linux，aarch64，具备 `wlP2p33s0` 和 AP 并发能力。
- 权限：设备端真实启动和网络检查需要 sudo。
- 依赖：CMake、C/C++ 编译器、Qt6、hostapd、dnsmasq、iw、iproute2、iptables/UFW。
- 独立客户端：一台 Windows 10/11 PC 或独立无线设备；同机 namespace/macvlan 不算独立客户端。
- 配置：`use_real_wifi_sta=1`；热点默认首选 `10.42.0.1/24`；NAT默认关闭。

## 3. 当前部署前置

阶段二已确认并处理当前设备防火墙：

- UFW active，默认 deny incoming。
- 已持久放行 `ap0` UDP 67，注释 `modu provision DHCP`。
- 已持久放行 `ap0` TCP 5935，注释 `modu provision TCP`。
- 已删除旧的全局 `POSTROUTING -o wlP2p33s0 -j MASQUERADE` 遗留规则。

阶段四必须重新采集规则并通过真实客户端验证，不能只依据上述记录判定通过。

## 4. 证据目录

每次验收使用：

```text
artifacts/beta-v1.0.1-acceptance/<YYYYMMDD-HHMMSS>/
```

建议子目录：`environment/`、`build/`、`unit/`、`startup/`、`subnet/`、`invalid-config/`、`dnsmasq/`、`readiness/`、`backoff/`、`cycle/`、`firewall/`、`client/`、`windows/`。

证据不得包含 WiFi 密码、Gitee 密码或其他账号凭据。

## 5. 前置条件

- 仓库处于待验收提交，记录 commit 和 `git status`。
- 无不明 `ap0`、设备进程、产品 hostapd/dnsmasq、UDP 67 或 TCP 5935占用。
- 不得用 killall/pkill 掩盖产品清理缺陷；未知资源归属不清时标记阻塞。
- 独立客户端忘记旧 `Modu_XXXX` 租约或执行 DHCP release/renew。

## 6. 编译与自动化

### A1. 环境基线

- 目的：保证结果可复现。
- 操作步骤：记录 commit、工作树、系统/内核/架构、工具版本、接口、IPv4、路由、`iw dev` 和 AP并发能力。
- 期望结果：依赖齐全，无未知产品残留；无线支持 AP和当前 STA+AP组合。
- 通过标准：信息完整且环境满足启动要求。
- 失败标准：缺依赖、无 AP能力或资源归属不明。
- 证据要求：`environment/system.txt`、`environment/network.txt`、`environment/iw-list.txt`。

### A2. 设备与测试工程构建

- 目的：验证可编译且无新增警告。
- 操作步骤：使用干净构建目录配置并构建设备工程和测试工程，保存 stdout/stderr。
- 期望结果：两者退出 0；本版本修改文件零警告；总警告不高于基线。
- 通过标准：无编译/链接错误和新增警告。
- 失败标准：任一失败或新增警告。
- 证据要求：`build/device.log`、`build/tests.log`、`build/warnings.txt`。

### A3. 全量与定向单元测试

- 目的：验证纯逻辑、事务失败和回归。
- 操作步骤：运行 `ctest --output-on-failure`；单独运行 hotspot config/runtime、backoff和模拟配网测试。
- 期望结果：全部测试通过，包含正常和异常路径。
- 通过标准：零失败、零跳过、零崩溃。
- 失败标准：任一测试失败或关键分支无测试。
- 证据要求：`unit/ctest.log`、`unit/hotspot.log`、`unit/test-list.txt`。

## 7. 启动与配置

### B1. 非 root 启动拒绝

- 目的：验证权限错误 fail-closed。
- 操作步骤：普通用户以真实模式启动设备，观察一轮失败和退避，检查接口、进程、端口和临时文件。
- 期望结果：明确提示需要 root；不报告热点成功；不残留 TCP listener或热点资源；不高频重试。
- 通过标准：失败明确且资源为零。
- 失败标准：误报成功、残留或约100 ms重试。
- 证据要求：`startup/non-root.log`、`startup/non-root-after.txt`。

### B2. sudo 真实启动

- 目的：验证核心启动路径。
- 操作步骤：清洁状态下 sudo 启动，等待成功日志；采集 `iw dev ap0 info`、`ip -j -4 addr show dev ap0`、`ss -lntup`、进程树；发送 SIGTERM。
- 期望结果：AP 模式、最终 IPv4、当前产品 dnsmasq UDP67和设备 TCP5935全部就绪后才打印成功；退出后完全清理。
- 通过标准：顺序、所有权和清理均正确。
- 失败标准：readiness不足仍报成功、崩溃、孤儿或残留。
- 证据要求：`startup/device.log`、`startup/iw.txt`、`startup/ip.json`、`startup/listeners.txt`、`startup/after-stop.txt`。

### B3. 默认首选网段

- 目的：验证当前 STA `192.168.1.0/24` 不再与 AP冲突。
- 操作步骤：无 `10.42.0.0/24` 本机直连路由时启动。
- 期望结果：选择 `10.42.0.1/24`，池 `10.42.0.100-200`。
- 通过标准：AP、dnsmasq argv和日志一致。
- 失败标准：选择重叠网段或三者不一致。
- 证据要求：`subnet/preferred-routes.txt`、`subnet/preferred.log`。

### B4. 候选网段切换

- 目的：验证检查全部本机直连路由和候选顺序。
- 操作步骤：使用临时 dummy接口依次制造 `10.42/24`、`10.43/24`、`172.31.250/24`、`192.168.250/24` 直连路由；每轮启动/停止。
- 期望结果：依次选择下一候选；四个均冲突时拒绝启动。
- 通过标准：顺序严格正确，全部冲突 fail-closed，测试资源清理。
- 失败标准：忽略非 STA路由、顺序错误或全冲突仍启动。
- 证据要求：`subnet/candidate-*/routes.txt`、`subnet/candidate-*/device.log`、`subnet/cleanup.txt`。

### B5. 非法配置 fail-closed

- 目的：验证配置错误不静默降级。
- 操作步骤：分别使用不存在、空、非法 JSON、类型错误、非法 IP/prefix、网络/广播 AP、池逆序/越界/包含 AP和不可访问 work_dir配置启动。
- 期望结果：每例明确失败，未创建任何热点资源。
- 通过标准：全部负例符合预期。
- 失败标准：任一使用默认网络继续启动或产生残留。
- 证据要求：`invalid-config/results.csv` 和逐例日志。

## 8. DHCP 与运行时

### C1. dnsmasq 系统配置隔离

- 目的：确认产品 DHCP不受系统配置干扰。
- 操作步骤：从 `/proc/<pid>/cmdline` 读取实际 argv；记录 `/etc/dnsmasq*` 哈希和系统服务前后状态。
- 期望结果：包含 `--conf-file=/dev/null`、port0、最终接口/地址/池/掩码/router/server-id；系统配置与服务不变。
- 通过标准：argv完整且没有全局服务副作用。
- 失败标准：缺隔离参数、修改系统配置或杀系统 dnsmasq。
- 证据要求：`dnsmasq/cmdline.txt`、`dnsmasq/system-before.txt`、`dnsmasq/system-after.txt`。

### C2. AP IPv4 回读

- 目的：确认内核实际地址与计划一致。
- 操作步骤：正常路径交叉读取地址；注入路径模拟命令成功但回读缺失/错误。
- 期望结果：精确一致后才启动 dnsmasq；不一致立即回滚。
- 通过标准：正常和异常路径均符合。
- 失败标准：只看命令返回值或错误地址仍报成功。
- 证据要求：`readiness/ap-readback.json`、单测日志。

### C3. UDP 67 PID/socket readiness

- 目的：确认监听属于当前产品 dnsmasq。
- 操作步骤：关联 pidfile、`/proc/<pid>/fd` socket inode和 `/proc/net/udp` 端口 0043；用 `ss`旁证；注入进程退出和无socket场景。
- 期望结果：2秒内成功才继续；失败约2秒后回滚。
- 通过标准：PID、inode、端口、地址全部匹配。
- 失败标准：只凭 PID或误认其他服务端口。
- 证据要求：`readiness/pid.txt`、`readiness/fd.txt`、`readiness/proc-udp.txt`、`readiness/ss.txt`。

### C4. TCP 5935

- 目的：验证真实监听和失败关闭。
- 操作步骤：正常启动检查 listener PID和地址；制造 AP失败后复查；独立客户端连接 DHCP router:5935。
- 期望结果：正常由当前设备监听 `0.0.0.0:5935`；失败无残留；客户端可达。
- 通过标准：本地所有权和端到端可达均通过。
- 失败标准：loopback-only、其他PID、失败残留或固定旧地址才能连接。
- 证据要求：`readiness/tcp.txt`、`client/tcp.txt`。

### C5. 失败退避

- 目的：验证永久错误不刷屏。
- 操作步骤：临时设置 5000 ms退避，使用不存在 hostapd或受控 UDP67占用制造失败，记录至少两个周期。
- 期望结果：尝试间隔不早于配置值，退避期间调用数不增长。
- 通过标准：时间线符合且无孤儿。
- 失败标准：主循环级重试或重复事件刷屏。
- 证据要求：`backoff/device.log`、`backoff/timestamps.csv`。

### C6. NAT 默认与显式启用

- 目的：验证默认无全局副作用和可选规则所有权。
- 操作步骤：nat=false启动检查无产品 MASQUERADE；nat=true且 ip_forward=1时检查精确源CIDR/出口/comment；停止后复查。
- 期望结果：默认无规则；显式规则准确且完全删除。
- 通过标准：规则与最终 AP计划一致，stop后归零。
- 失败标准：默认添加、无源限制、修改 ip_forward或残留。
- 证据要求：`firewall/nat-false.txt`、`firewall/nat-true.txt`、`firewall/nat-after.txt`。

### C7. 防火墙部署规则

- 目的：确认当前部署允许端到端 DHCP/TCP，且应用不擅自改放行规则。
- 操作步骤：采集 UFW、iptables、nftables实际后端启动前后状态；确认 ap0 UDP67/TCP5935规则；结合独立客户端抓包。
- 期望结果：部署规则存在；应用启动前后 INPUT/OUTPUT/FORWARD无变化。
- 通过标准：规则和端到端结果均通过。
- 失败标准：默认阻断或应用修改全局放行策略。
- 证据要求：`firewall/before.txt`、`firewall/after.txt`、`firewall/diff.txt`。

### C8. 20次启停

- 目的：验证资源生命周期稳定。
- 操作步骤：20轮 sudo启动至全部 readiness、SIGTERM、检查 ap0/进程/UDP67/TCP5935/pidfile/config/NAT。
- 期望结果：20/20启动和清理成功。
- 通过标准：每轮停止后资源为零。
- 失败标准：任一轮失败或残留，即使下一轮会清理也判失败。
- 证据要求：`cycle/summary.csv`、逐轮日志和状态。

## 9. 独立客户端与 Windows

### D1. 独立无线客户端 DHCP 四步

- 目的：证明 DHCP真正对无线客户端可用。
- 操作步骤：设备侧抓取 ap0 UDP67/68；独立客户端连接热点并 renew；保存客户端地址、掩码、server-id、gateway和路由。
- 期望结果：DISCOVER/OFFER/REQUEST/ACK完整；地址在最终池内；非 APIPA；router和server-id等于最终 AP。
- 通过标准：pcap和客户端配置同时满足。
- 失败标准：任一步缺失、NAK、APIPA或 option错误。
- 证据要求：`client/dhcp.pcap`、`client/dhcp-decode.txt`、`client/ip-config.txt`。
- 阻塞处理：没有独立客户端时标记阻塞，不得通过。

### D2. TCP 与 auth

- 目的：验证 DHCP后的配网入口。
- 操作步骤：从租约读取 router，连接 router:5935，按协议发送长度前缀 auth并接收 auth_result。
- 期望结果：正确 PIN返回 status ok，设备记录认证成功。
- 通过标准：TCP和协议应答均成功。
- 失败标准：只能连固定旧地址、无帧应答或错误状态。
- 证据要求：`client/auth-client.log`、`client/auth-device.log`。

### D3. Windows 现有 PC 程序端到端

- 目的：复核原故障流程。
- 操作步骤：不修改 PC代码，运行现有 `provision_pc`；保存 netsh、ipconfig、route和应用日志；设备同步抓包。
- 期望结果：Windows非APIPA，从目标WLAN取得 DHCP router，连接 router:5935并完成 auth。
- 通过标准：PC日志和设备pcap证据一致。
- 失败标准：只有关联无租约、使用固定旧地址或未进入auth。
- 证据要求：`windows/pc.log`、`windows/ipconfig.txt`、`windows/route.txt`、`windows/device.pcap`。
- 阻塞处理：无Windows环境时标记阻塞，不得通过。

## 10. 回归范围

- 模拟多设备、模拟 AP地址翻译、完整模拟配网。
- PIN错误和非法 wifi_config。
- 设备状态机启动、AP超时、PIN锁定和close_ap路径。
- 参数加载和热点配置路径。
- 不回归或修改 PC内部实现，只运行现有程序做端到端验收。

## 11. 失败与阻塞处理

- 编译/单测失败：退回对应 SubStage 修复。
- sudo启动失败：定位配置、依赖、PHY、路由、readiness或部署规则，不得跳过。
- 独立客户端/Windows不可用：标记阻塞并保留已完成设备侧证据。
- 任一无法执行项不得默认通过。
