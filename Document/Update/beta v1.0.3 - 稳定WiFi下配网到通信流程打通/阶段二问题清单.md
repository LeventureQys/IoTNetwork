# 问题清单 - beta v1.0.3 / 阶段二

## v1（设计梳理，2026-08-05）

### 置顶区（待用户确认，阶段阻塞）

无。阶段一已确认只面向稳定 WiFi 主流程，当前设计不存在重大路线分歧。

### 自决区

#### Q1. 是否新增设备状态枚举

- 问题描述：自动交接可以增加 `HANDOFF` 状态，也可以作为 AP_PROVISION 内部子阶段。
- 自决方案：不新增状态枚举，只增加 deadline 字段。
- 自决理由：当前 UI、测试和状态字符串都依赖现有枚举；内部 deadline 足以表达短暂交接，修改更集中且便于 ESP32-C3 迁移。
- 风险预警：日志必须明确子阶段，否则 UI 仍只显示 ap_provision。
- 置信度：97%。

#### Q2. 宽限期默认值

- 问题描述：需要给 PC 一次发送 close_ap 的机会，同时不能明显延迟 UDP 发现。
- 自决方案：默认 1000ms，并支持 JSON 配置；测试使用更短值。
- 自决理由：本地 TCP 小消息通常远低于 1 秒完成，1 秒也不会明显影响配网体验。
- 风险预警：真实环境若需调整可直接改配置，不需要改状态机。
- 置信度：94%。

#### Q3. close_ap 是否重试

- 问题描述：PC 可以增加重试，但旧 SoftAP TCP 在设备连接 STA 后可能已经失效。
- 自决方案：PC 只发送一次并检查结果；设备负责自动交接。
- 自决理由：在不增加新 ACK 协议的前提下，重试不能证明设备收到，反而延迟 PC 切回目标 WiFi。
- 风险预警：必须保留准确失败日志。
- 置信度：98%。

#### Q4. 是否重构所有 TCP send 为 send_all

- 问题描述：当前 send 可能部分写，但全局重构会扩大版本范围。
- 自决方案：仅让 PC 本地 `send_frame()` 判断是否完整写入，不在本版本实现循环重试或公共 send_all。
- 自决理由：满足 close_ap 结果准确性，同时保持小版本边界。
- 风险预警：其他核心消息的部分写健壮性仍属于后续改进。
- 置信度：92%。

#### Q5. wifi_result 发送失败后是否自动交接

- 问题描述：如果设备已经成功连接并保存 WiFi，但 wifi_result 没有送达，继续等待可能再次卡住。
- 自决方案：仍安排自动交接，但记录发送失败；PC 最终可能把本轮显示为失败，设备则可通过目标网络回连证明配置已生效。
- 自决理由：设备已验证目标 WiFi，回滚或永久保留 AP 都没有额外收益；自主进入业务网络更符合最终目标。
- 风险预警：PC UI 可能先显示配网失败、随后设备上线，需要日志解释该情况；本版本不增加跨网络确认协议。
- 置信度：91%。

#### Q6. PC 是否在 ProvisionDevice 内等待设备上线

- 问题描述：等待上线可以直接返回完整成功，但会阻塞串行配网和混合两个网络阶段。
- 自决方案：不等待；`ProvisionDevice()` 只返回 WiFi 配置结果，设备上线由 HostApp 注册表异步确认。
- 自决理由：符合现有类职责和线程模型，也能清晰区分两个成功阶段。
- 风险预警：UI 需要分别展示“等待回连”和“在线”。
- 置信度：99%。
