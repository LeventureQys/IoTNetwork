# beta v1.0.3 总体设计

## 1. 设计目标

在一个稳定、可用的目标 WiFi 环境中，打通以下真实主流程：

```text
SoftAP 配网
  -> 设备连接目标 WiFi
  -> 配网阶段可靠结束
  -> UDP 组播发现 PC
  -> TCP 注册会话
  -> ping/pong
```

本版本不重构完整网络框架。设备端和 PC 端分别修改，通过现有协议字段协同，不增加新的协议命令。

## 2. 平台边界

### 2.1 当前验证平台

- 设备端流程运行在 Linux。
- PC 端运行现有上位机程序。
- 目标网络为稳定的 2.4GHz WiFi。
- UDP 组播 `224.0.2.1:5936` 为本版本服务发现主路径。

### 2.2 后续设备平台

设备端后续迁移到 ESP32-C3。设备状态机代码只能依赖 `net_abstraction`，不得直接引用 Linux NetworkManager、`nmcli`、网卡名称或 Linux 专属 socket API。

## 3. 修改边界

### 3.1 设备端修改

- 增加配网成功后的短宽限期。
- `close_ap` 从唯一迁移条件改为提前结束宽限期的兼容命令。
- 修正成功后仍打印 wifi_config 超时的问题。
- 增加 UDP 组播启动日志。
- 增加设备端状态机测试。

详细任务见 `设备端修改计划.md`。

### 3.2 PC 端修改

- 检查 `close_ap` 的实际发送结果。
- 发送失败时准确记录，但继续结束配网连接并切回目标 WiFi。
- 区分“WiFi 配置已接受”和“业务会话已建立”。
- 增加 PC 端配网行为测试。

详细任务见 `PC端修改计划.md`。

### 3.3 不修改

- 不新增协议命令或应答。
- 不实现 `close_ap_ack`。
- 不实现复杂重发。
- 不修复弱信号、WiFi 短断、多凭据退避。
- 不实现真实 mDNS、多网卡选择、BLE、TLS、OTA。
- 不修改 ESP32-C3 后端；本版本只保证核心逻辑可迁移。

## 4. 双端时序设计

```text
PC                                      设备
 │                                       │
 │ wifi_config                           │
 │──────────────────────────────────────>│
 │                                       │ 连接并校验目标 WiFi
 │                                       │ 保存未确认凭据
 │ wifi_result ok                        │
 │<──────────────────────────────────────│
 │                                       │ 启动 1000ms 交接宽限期
 │ close_ap（最佳努力，一次）              │
 │──────────────────────────────────────>│
 │                                       │ 收到则立即停止 AP
 │                                       │ 未收到则宽限期到期停止 AP
 │ 关闭配网 TCP、切回目标 WiFi             │
 │                                       │
 │ host_announce（UDP 5936）              │
 │──────────────────────────────────────>│
 │                                       │ TCP connect PC:5935
 │ device_hello                          │
 │<──────────────────────────────────────│
 │ host_ack ok                           │
 │──────────────────────────────────────>│
 │ ping / pong                           │
 │<─────────────────────────────────────>│
```

## 5. 配网交接契约

### 5.1 新配置参数

在 `demo_params_t` 阶段二参数中增加：

```c
int provision_handoff_grace_ms;
```

契约：

- 默认值：`1000` 毫秒。
- 配置 JSON 字段：`provision_handoff_grace_ms`。
- 必须大于等于 0。
- `0` 表示 `wifi_result ok` 写出后下一次状态机轮询即可自动关闭 AP。
- 当前 `demo/config/demo_config.json` 显式配置为 `1000`，便于真实验证。

### 5.2 设备运行字段

在 `device_app_t` 阶段二字段中增加：

```c
uint64_t provision_handoff_deadline_ms;
```

生命周期：

- `prov_server_start()` 时清零。
- `wifi_config` 成功且 `wifi_result ok` 发送成功后设置为 `now + grace`。
- `close_ap` 到达时清零并停止 AP。
- 自动交接执行时清零并停止 AP。
- 配网失败、重新启动 AP 或退出时清零。

### 5.3 自动交接前置条件

设备只能在以下条件全部满足时自动关闭 AP 并进入 discovery：

- `provision_auth_ok == 1`
- `provision_wifi_ok == 1`
- `provision_handoff_deadline_ms > 0`，或者 grace 配置为 0 后已安排交接
- 目标 WiFi 当前仍有有效 IPv4
- 当前 SSID 与 `creds[cred_active]` 一致

如果最终 STA 校验失败，沿现有 `ensure_expected_wifi_or_recover()` 路径处理，不进入 discovery。

### 5.4 `close_ap` 语义

- 协议 JSON 保持 `{"cmd":"close_ap"}`。
- PC 在收到 `wifi_result ok` 后发送一次。
- 设备收到时立即停止 AP。
- 如果设备已自动停止 AP，旧连接上的 `close_ap` 自然不可达，不视为错误。
- PC 不等待应答，不增加重试协议。

## 6. 状态迁移设计

不增加新的 `device_state_t`。

`DEV_STATE_AP_PROVISION` 内部增加两个子阶段语义：

1. 正常配网：等待 auth/wifi_config。
2. 成功交接：`provision_wifi_ok=1`，等待 `close_ap` 或宽限期到期。

宽限期到期后调用 `prov_server_stop()`。状态机现有的 `ap_listen == NULL && provision_auth_ok && provision_wifi_ok` 条件继续负责进入 `DEV_STATE_DISCOVERY`。

这样修改集中在现有字段和函数内，不增加状态枚举，也不改变 UI 状态映射。

## 7. 日志契约

### 7.1 设备端

必须新增或调整：

```text
配网：目标 WiFi 配置成功，等待 close_ap 或 1000 毫秒后自动交接
配网：已收到 close_ap
配网：未收到 close_ap，设备主动完成交接
配网：设备热点已停止
状态切换 -> discovery
服务发现：UDP 组播监听已启动，地址=224.0.2.1:5936
```

`provision_wifi_ok=1` 后不得打印“等待 wifi_config 超时”。

### 7.2 PC 端

必须区分：

```text
设备已接受目标 WiFi 配置，等待设备回连
配网：close_ap 已完整写入配网连接
配网：close_ap 写入失败，返回码=<rc>，设备将自动完成交接
正在切回目标 WiFi <SSID>
已切回目标 WiFi <SSID>
```

收到 `device_hello` 并回复 `host_ack ok` 后，记录业务会话建立；不得在仅收到 `wifi_result ok` 时记录完整业务成功。

## 8. Stage 与执行顺序

### Stage 1：设备端交接

- 实现参数和运行字段。
- 实现自动交接。
- 修正超时和日志。
- 增加设备端测试。

### Stage 2：PC 端收尾

- 检查 close_ap 发送结果。
- 调整配网阶段日志。
- 增加 PC 端测试。

Stage 1 和 Stage 2 的源码无编译依赖，可以分别开发；双端联调必须等待两端都完成。

### Stage 3：集成验收

- 构建和自动化测试。
- Linux 模拟启动测试。
- 稳定 WiFi 真实端到端测试。

## 9. 完成条件

- 不发送 `close_ap` 的测试中，设备仍进入 discovery。
- 正常发送 `close_ap` 的既有流程不回归。
- PC 准确记录 close_ap 发送结果。
- 真实日志出现 UDP discovery、device_hello、host_ack 和至少三轮 ping/pong。
- 设备端核心修改不包含 Linux 专属 API。
