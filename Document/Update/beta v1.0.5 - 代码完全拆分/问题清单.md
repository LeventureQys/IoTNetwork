#### Q1. 拆分后的设备端需要交付哪一种可运行产品 —— 【已关闭：采用建议方案 A】

- 问题描述：当前 `demo/device/CMakeLists.txt:33` 构建的是 Windows/Linux 宿主机上的 Qt 设备模拟器，入口 `demo/device/app/main.cpp` 同时负责 Qt、配置、线程、文件系统和模拟网络后端生命周期；真实 ESP32 后端 `demo/net_esp32c2/esp32c2_backend.c` 尚未加入该构建，且仍是待移植骨架。因此，“设备端文件夹”可能指宿主机设备模拟器、ESP32 固件工程，或同时包含二者，三种选择会直接改变目录结构、构建系统和验收环境。
- 建议方案：选择 **方案 A：一个自包含的设备端文件夹，同时保留宿主机 Qt 模拟器和 ESP32 纯 C 移植代码**。设备业务核心和全部非 UI 基础设施保持纯 C；Qt 模拟器仅作为顶层可视化外壳；ESP32 后端及移植资料一并归入设备端，但本版本不虚构未完成的实机实现。
- 备选方案：
  - 方案 B：设备端文件夹只保留宿主机 Qt 模拟器，本版本不纳入 `net_esp32c2/`；优点是可继续执行现有双进程演示，缺点是“设备端”仍不是可直接烧录的固件工程。
  - 方案 C：设备端文件夹只形成 ESP32/ESP-IDF 工程，删除宿主机 Qt 模拟器；这会改变现有 Demo 产品形态，并需要补全硬件后端和实机验收，已超出单纯代码拆分。
- 风险预警：若产品形态判断错误，阶段二的目录、构建、测试和验收设计都需整体返工。方案 A 可以保留历史演示能力和嵌入式移植入口，但必须明确“模拟器可运行、ESP32 后端仍待硬件实现”的交付边界。**需用户决策**。
- 置信度：75%。
- 归入置顶原因：直接决定设备端最终构建目标和交付范围，属于重大技术路线分歧。

回复：按照建议方案来吧。

#### Q2. “最上层界面”允许使用 C++ 的准确边界 —— 【已关闭：采用建议方案】

- 问题描述：当前设备端除 `demo/device/ui/device_window.cpp` 外，`demo/device/app/main.cpp`、`demo/net_sim/sim_world.cpp`、`demo/net_sim/sim_backend.cpp`、`demo/net_sim/sim_tcp_endpoint.cpp` 也使用 C++。其中 `main.cpp` 同时创建 `QApplication` 和窗口，Qt 程序入口无法直接改为纯 C；其余 `net_sim/*.cpp` 明确属于非 UI 基础设施，不符合需求中的纯 C 边界。需要确认 Qt 应用启动胶水是否也算“最上层界面”。
- 建议方案：允许设备端仅在 `ui/` 和一个最薄的 Qt 启动入口中使用 C++，即 C++ 范围限定为窗口/控件、Qt 信号槽、`QApplication` 创建与销毁；配置解析、线程任务、状态机、协议、文件/NVS、网络后端、模拟网络和生命周期编排全部下沉为 C 接口与 C 实现。C++ UI 只能调用公开的 C facade，不得被 C 核心反向依赖。
- 备选方案：严格限定只有 `ui/` 内文件可使用 C++，另用纯 C `main` 启动业务，再通过独立 C++ 包装目标启动 Qt；语言边界更字面化，但最终可执行文件仍需要 C++ 链接入口，增加无实际隔离收益的启动包装层。
- 风险预警：若不把启动入口纳入 UI 外壳，Qt 模拟器无法以自然方式保留；若允许范围过宽，则可能继续把配置、线程和网络逻辑留在 C++ 中，违背需求。**需用户决策**。
- 置信度：85%。
- 归入置顶原因：这是本版本的核心语言边界，直接决定大批 C++ 文件是重写、包装还是保留。

回复：按照建议方案来

#### Q3. 是否允许在两个产品文件夹之外保留独立的跨端集成测试入口 —— 【已关闭：采用建议方案】

- 问题描述：当前 `demo/tests/CMakeLists.txt:16` 与 `demo/tests/CMakeLists.txt:32` 会同时重新编译设备核心和 PC 核心，`demo/tests/test_host_app.cpp` 等用例在同一进程中覆盖两端联调。完全拆分后，端侧单元测试可分别归入 PC 和设备文件夹，但跨端兼容、配网和重连测试天然同时依赖两个产品；如果严格只允许两个文件夹且互不引用，现有跨端测试无法原样保留。
- 建议方案：允许保留一个**不含生产源码**的独立集成测试入口，例如 `demo/integration_tests/`。它只能消费两个端侧已构建的公开产物或启动两个进程，不得直接编译、包含 PC/设备私有源码；PC 和设备各自的单元测试分别放入各自文件夹。这样产品代码仍完全拆分，同时保留协议兼容和端到端质量门禁。
- 备选方案：不允许第三个测试入口；将所有测试分别归入两端，跨端验证仅作为启动测试脚本放在 PC 或设备一侧。该方案目录更严格，但测试所有权偏置，且难以证明双端版本兼容。
- 风险预警：若不保留独立集成层，现有端到端回归能力会下降；若保留但继续直接包含两端源码，则只是把原耦合换了目录名，不能算完全拆分。**需用户决策**。
- 置信度：85%。
- 归入置顶原因：测试拓扑会影响最终目录定义、CMake 导出契约和“完全拆分”的验收标准。

**置顶区结论（作为阶段二设计输入）：**

1. **Q1 结论**：设备端采用一个自包含文件夹，同时保留宿主机 Qt 模拟器和 ESP32 纯 C 移植代码；模拟器是本版本可运行目标，ESP32 后端保持真实完成度，不将未实现骨架描述为可用固件。
2. **Q2 结论**：设备端仅允许 `ui/` 和最薄的 Qt 启动入口使用 C++；配置、线程任务、状态机、协议、文件/NVS、网络后端、模拟网络和生命周期编排全部使用纯 C；C++ UI 只能依赖公开 C facade，C 核心不得反向依赖 C++。
3. **Q3 结论**：允许保留不含生产源码的独立 `demo/integration_tests/`；它只能消费双端公开构建产物或执行双进程测试，不得直接编译或包含两端私有源码；端侧单元测试分别归入 PC 和设备文件夹。

回复：按照建议方案执行。

### 自决区（不阻塞，作为阶段二设计输入）

#### Q4. 公共生产代码的处理方式

- 问题描述：PC 与设备当前共同编译 `demo/common/`、`demo/include/`、`demo/net_sim/`、`demo/shared_ui/` 和 `demo/third_party/cjson/`，两端 CMake 都通过 `DEMO_ROOT` 引用父目录，见 `demo/pc/CMakeLists.txt:10` 和 `demo/device/CMakeLists.txt:10`。
- 自决方案：严格按需求允许的方式，将每端需要的公共源码、头文件、第三方依赖和构建辅助分别复制到自己的目录；完成后两个产品的 CMake 不得引用对方目录或原 `demo/` 根目录中的生产源码。公共代码不再保留第三份可编译权威副本。
- 自决理由：需求已明确“公用代码直接复制一份到两个不同目录下都可以”，并要求“完全分成两个文件夹”；复制是最符合字面要求且没有额外公共包依赖的方案。
- 风险预警：协议和帧实现会形成双份源码，后续必须增加协议版本、兼容测试及必要的一致性检查，防止静默漂移。
- 置信度：97%。

#### Q5. 完全拆分的最低验收定义

- 问题描述：当前 PC、设备虽然可分别从 `demo/pc`、`demo/device` 配置构建，但都依赖父目录资源，单独复制任一目录都无法构建或运行。
- 自决方案：将“完全拆分”定义为：任一端文件夹单独复制到仓库外后，可只使用自身源码、配置、文档和声明的系统依赖完成配置、构建、单元测试与启动；源码/CMake 不出现指向另一端或原根共享源码的相对路径；运行时不依赖从原 `demo/` 工作目录启动。
- 自决理由：该定义可客观验证“两个独立、自包含文件夹”，避免仅移动目录但保留隐式耦合。
- 风险预警：Qt、CMake、系统网络库等外部工具链不属于仓库源码耦合，仍按各端 README 声明安装。
- 置信度：96%。

#### Q6. 协议行为和持久化格式保持不变

- 问题描述：本需求只要求代码拆分和设备端语言边界管理，没有要求修改协议、配网流程或持久化数据。
- 自决方案：不修改帧格式、命令名、端口、组播地址、设备状态值、NVS 键、配置字段语义和错误码；复制后的两端协议实现以拆分前现状为兼容基线，并通过跨端测试验证。
- 自决理由：避免目录重构引入无关行为变化，符合根因修复和最小变更原则。
- 风险预警：配置可按端侧职责拆成两份文件，但双方互操作字段必须保持同值和兼容。
- 置信度：98%。

#### Q7. 平台后端的默认归属

- 问题描述：`demo/net_win/` 是 PC Windows 后端；`demo/net_linux/` 包含 Linux 热点和 WiFi 设备能力；`demo/net_esp32c2/` 是设备硬件后端骨架；`demo/net_sim/` 当前被双端共同使用且为 C++。
- 自决方案：`net_win` 归 PC；`net_linux` 按实际职责拆分，PC 只保留上位机所需能力，设备保留热点/STA 能力；`net_esp32c2` 归设备；`net_sim` 按需复制到两端并移除双端非 UI C++，设备侧改为纯 C。不得再让 Linux PC 构建无条件携带设备热点实现。
- 自决理由：现有平台职责和需求中的端侧边界足以确定归属，不涉及产品路线选择。
- 风险预警：设备侧 `net_sim` C 化改动较大，必须补齐正常路径和异常路径单元测试。
- 置信度：92%。

#### Q8. 配置、运行目录与启动脚本随端拆分

- 问题描述：两端当前默认读取同一个 `demo/config/demo_config.json`，设备启动入口还依赖配置位置推导 `run/`、`logs/` 和热点配置目录；这会导致拆分后的程序仍依赖原根目录。
- 自决方案：两端各自拥有配置模板、日志/状态目录约定和启动脚本；公共互操作参数保持一致；所有路径以端侧配置文件位置或显式命令行参数解析，不依赖进程从原 `demo/` 根目录启动。
- 自决理由：运行资源自包含是代码完全拆分的必要条件，具体文件名和参数名可在阶段二按现有风格确定。
- 风险预警：双进程模拟若需要共享状态目录，必须通过显式参数传递同一路径，不能恢复隐式根目录耦合。
- 置信度：94%。

#### Q9. 文档和历史空目录处理

- 自决方案：更新根导航文档，并在两个端侧文件夹内各提供独立构建、运行、测试和语言边界说明；确认无构建或脚本引用后删除无用途空目录。版本过程文档继续保留在 `Document/Update/beta v1.0.5 - 代码完全拆分/`。
- 自决理由：这是目录重构的必要文档同步和无行为清理，不影响技术路线。
- 风险预警：删除前需检查未跟踪脚本和文档引用，避免破坏外部操作说明。
- 置信度：95%。
