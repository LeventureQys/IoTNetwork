#### Q2. "整理成一个单独的硬件层"的组织形态：文档化固化现状 vs 物理目录重组 —— 【已关闭：用户选择"方案 A：文档化固化"】

- 问题描述：需求 0 要求"把连接 WiFi、AP、TCP 等关键接口整理成一个单独的硬件层，让嵌入式开发只需修改硬件层代码即可使用"。经调研，**该抽象实际已存在且相当完整**：
  - 接口层：`demo/include/net_abstraction.h` 定义 `net_backend_t` vtable（生命周期 / WiFi 扫描与 STA / AP 启停 / RSSI / IP / TCP / UDP 组播 / mDNS / NVS / time_ms / random / inject，共 29 个函数指针）+ `net_ctx_t` 便捷封装；
  - 后端实现：`net_sim`（仿真）、`net_win`（Windows）、`net_linux`（Linux 真实热点/STA，PC 侧）、`net_esp32c2`（嵌入式骨架，含移植指南）；

- 建议方案：**方案 A（推荐）——固化与文档化，不做物理重组**：
  1. 对现有 vtable 做接口完备性审计（对照 docx 全流程逐一确认每个流程点都有接口支撑，补齐缺口或明确标注不适用项）；

  4. 更新 `demo/README.md` 与目录说明，明确"硬件层 = net_abstraction.h 接口 + net_* 后端"的层次边界。

#### Q3. "直接发送消息"小功能的协议与交互设计

- 问题描述：需求 2 要求在上下位机界面都添加"直接发送消息"功能，用于配网结束后两边联调。协议层面已有现成占位：`CMD_APP_DATA "app_data"`（`demo/include/protocol.h`），两端收包路径已实现"收到 app_data → 日志后丢弃不崩溃"（`demo/device/device_session.c`、`demo/pc/core/host_tcp_server.cpp`），协议文档 2.5 节定义 `data` 为任意业务负载占位。
- 自决方案：
  1. 报文格式沿用协议文档 2.5 节占位框架：`{"cmd":"app_data","seq":N,"data":{"type":"debug_text","text":"<用户输入>"}}`，走既有 2 字节长度前缀帧，受 1024 字节上限约束（超长 UI 侧截断/禁止发送）。
  2. 上位机端：设备表格选中某在线设备 → 输入框 + 发送按钮 → 经该设备会话连接发送；设备离线时按钮禁用。
  3. 设备端：会话建立后（DEV_STATE_SESSION）输入框 + 发送按钮可用，其余状态禁用；经会话 socket 发往 host。
  4. 接收展示：复用两端既有日志窗口（收到 app_data 时打印 text 内容），不新增独立消息面板——联调定位用途，够用即可。
- 自决理由：协议占位框架已存在且两端已兼容接收，无需协议变更；"配网结束后联调才用得上"与仅会话态可用的设计吻合。
- 风险预警：无重大风险；`app_data` 当前语义为"日志后丢弃"，本次将其升级为"日志展示内容"，属协议文档 2.5 允许的业务负载用法。
- 置信度：94%。

- 问题描述：需求 1 要求阅读 git 提交日志与 `ESP32-C2配网与连接保障流程.docx`（v3 增强版 H005），特别关注固定 PING 码、命名规则等。已逐项核对代码现状：
  - 心跳命令：`CMD_PING "ping"` / `CMD_PONG "pong"`，带 `seq` 单调递增（与 docx 3.4 节一致）；
  - 热点命名：`Modu_XXXX`（MAC 后 2 字节大写十六进制，`device_app.c` 生成、`host_provision_client.cpp` 按 `Modu_` 前缀过滤，与 docx 3.2 节一致）；
  - 端口/组播：TCP 5935（配网 + 业务）、UDP 组播 224.0.2.1:5936、mDNS `_tactile._tcp`（与 docx 4.2 参数表一致）；

- 自决方案：本版本**不改动任何协议常量**；硬件层文档与移植指南在描述协议相关内容时直接引用上述已核对常量，保证与 docx 一致；后续若 docx 再变更，以该核对表为基线做差异比对。

- 风险预警：docx 为二进制文件无法用 git diff 追踪历史改动（git 中无该文件修改记录可 diff），核对基于当前文件内容与代码的比对。

#### Q9. 设备端 UI→device 循环跨线程传递机制

- 问题描述：设备 UI（Qt 主线程）与 `device_app_run`（独立线程）分属两线程，UI 不能直接写会话 socket，需确定跨线程传递方式。
- 自决方案：单槽请求缓冲（`ui_tx_text[513]` + `ui_tx_pending` 标志），UI 线程写入、device 循环每轮消费；新请求覆盖未消费旧请求（手动联调场景可接受）。上位机侧同构问题采用互斥锁队列（`pending_tx_` + `tx_mu_`），因 host 侧已有互斥锁风格的注册表先例。
- 自决理由：与代码库既有单线程事件循环风格一致（device 模块零平台依赖，不引入 Qt 同步原语）；单槽覆盖语义对低频手动操作无实质损失。
- 风险预警：无（覆盖时记日志可观察）。
- 置信度：93%。

#### Q11. E2E 日志断言命中发送方自身 TX 日志造成假通过

- 问题描述：`DeviceAppData.SendToHost` 初版等待条件 `LogCaptured("hello-host")` 会先命中设备自身的 `TX {...}` 发送日志，循环提前退出时上位机尚未处理该帧，断言失败。

- 自决理由：断言必须锁定接收方日志，避免发送方回显干扰；同类教训适用于后续 E2E 日志断言。
