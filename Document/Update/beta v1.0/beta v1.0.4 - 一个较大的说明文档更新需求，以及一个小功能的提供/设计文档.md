# 设计文档 - beta v1.0.4（硬件抽象层文档化 + 联调消息发送功能）

## 1. 背景与目标

本项目在 Linux（rk3588 OrangePi）上验证了"ESP32 设备配网 → 服务发现 → TCP 会话 → 自愈"全流程，最终目标是将设备端代码移植到 ESP32-C3（ESP-IDF）。本版本两项工作：

1. **硬件抽象层文档化（需求 0，主要工作）**：项目中硬件抽象已完整存在（`demo/include/net_abstraction.h` 的 `net_backend_t` vtable + `net_sim`/`net_win`/`net_linux`/`net_esp32c2` 四个后端，业务层 `demo/device/` 与 `demo/common/` 零平台依赖）。本版本**不做物理目录重组**（阶段一 Q2 用户已确认方案 A），工作内容为：接口完备性审计 + 产出《硬件抽象层接口规范》与《硬件抽象层移植指南》两份零上下文文档 + 更新 README 层次说明。文档口径为 **ESP32 系列通用 + 以 esp32-c3 为主移植目标，保留 C2 兼容说明**（阶段一 Q1 用户已确认）。
2. **联调消息发送小功能（需求 2）**：在上位机与设备端界面各增加"直接发送消息"入口，仅在配网完成、会话建立后用于双向联调。复用协议既有 `app_data` 占位命令（`demo/include/protocol.h` 的 `CMD_APP_DATA`），不变更任何协议常量（阶段一 Q4 已完成与 docx 的一致性核对）。

**明确不做**：协议常量改动、物理目录重组、LED/GPIO 硬件接口（仅在接口规范中预留扩展说明，阶段一 Q6）。

## 2. 总体架构与层次边界

```text
┌─────────────────────────────────────────────────────────────┐
│  UI 层（Qt）       pc/ui/host_window      device/ui/device_window │
├─────────────────────────────────────────────────────────────┤
│  业务层（零平台依赖）                                         │
│    pc/core/host_*（C++17）   device/device_*（C11）           │
│    common/frame、common/protocol、common/params、common/log │
├─────────────────────────────────────────────────────────────┤
│  硬件抽象层（本版本文档化的对象）                              │
│    接口：include/net_abstraction.h（net_backend_t vtable，   │
│          29 个函数指针）+ common/net_abstraction.c 便捷封装    │
│    后端：net_sim（仿真） net_win（Windows）                    │
│          net_linux（Linux 真实热点/STA） net_esp32c2（嵌入式骨架）│
└─────────────────────────────────────────────────────────────┘
```

移植到 ESP32-C3 时，**只需实现一个新的 `net_backend_t` 实例**（参照 `net_esp32c2/esp32c2_backend.c` 骨架），业务层代码原样复用——这是两份文档要传达的核心结论。

## 3. 联调消息发送功能设计

### 3.1 消息契约（跨 SubStage 契约，两端必须一致）

- 报文：`{"cmd":"app_data","seq":N,"data":{"type":"debug_text","text":"<UTF-8 文本>"}}`
  - `cmd` 固定 `"app_data"`（`CMD_APP_DATA`，协议文档 2.5 节业务占位命令）。
  - `seq`：发送方每次发送自增 1（每连接会话内单调；重连后从 1 重新开始即可，接收方不校验）。
  - `data.type` 固定 `"debug_text"`；`data.text` 为用户输入文本。
- 传输：走既有 TCP 业务连接（上位机 5935 端口），2 字节大端长度前缀帧（`frame_wrap`/`frame_parse`），JSON 负载 ≤ `PROTO_MSG_MAX_LEN`（1024 B）。
- **UI 文本上限**：`#define APP_DATA_TEXT_MAX 512`（字节，UTF-8）。512 + JSON 包装（约 70 B + 转义余量）保证不超过 1024 B 帧上限。常量定义位置：`demo/include/protocol.h`（新增一行，两端共享）。
- 超长/空文本：发送 API 返回 `DEMO_ERR`，UI 记录警告日志，不弹窗。
- 接收展示：两端均通过既有日志窗口展示（日志内容含 text 原文），不新增独立消息面板。

### 3.2 上位机侧（SubStage_01）

**线程模型**：`HostApp::Run()` 跑在 host 线程（`pc/app/main.cpp`），UI 在 Qt 主线程。UI 线程**不得**直接写 socket。

实现要点：

1. `HostTcpServer`（`demo/pc/core/host_tcp_server.h/.cpp`）新增：
   - 成员：`std::mutex tx_mu_;`、`std::vector<std::pair<std::string, std::string>> pending_tx_;`、`uint32_t app_data_seq_ = 0;`
   - `int QueueAppData(const std::string &device_id, const std::string &text);`：UI 线程调用。校验 text 非空且 ≤ 512 字节，通过则加锁压入 `pending_tx_` 返回 `DEMO_OK`，否则返回 `DEMO_ERR`。
   - `Poll()`（host 线程）末尾冲刷 `pending_tx_`：逐条在 `reg_` 中查条目；`state=="online"` 且 `conn!=nullptr` → 构造 JSON → 复用私有 `SendFrame` 发送，`LOG_I` 记录"已向 <id> 发送调试消息（N 字节）"；设备离线 → 丢弃并 `LOG_W`。
   - `HandleOnline` 中 `CMD_APP_DATA` 分支由"已忽略"改为：解析 `data.text`（字符串）→ `LOG_I("HOST", "收到来自 %s 的调试消息：%s", ...)`；无 `data.text` 时保留原占位日志。
2. `HostApp`（`demo/pc/core/host_app.h/.cpp`）新增门面：`int SendAppDataToDevice(const std::string &id, const std::string &text);` → 转发 `tcp_server_.QueueAppData`。
3. `HostWindow`（`demo/pc/ui/host_window.h/.cpp`）新增：
   - `QLineEdit *msg_edit_`（placeholder "输入发给所选设备的联调消息（≤512 字节）"）+ `QPushButton *msg_send_button_`（"发送消息"），加入既有 `buttons` 横向布局（配网按钮、停止按钮之后，stretch 之前）。
   - 发送槽：取 `device_table_->currentRow()` → `host_->registry().Snapshot()` 按行号取条目 → 校验行有效且 `state=="online"` → 调 `host_->SendAppDataToDevice`；结果与异常（未选中/离线/超长）均写 `LOG_W`/`LOG_I`，不弹窗。发送成功不清空输入框（便于重复发送微调）。

### 3.3 设备侧（SubStage_02）

**线程模型**：`device_app_run` 跑在 device 线程（`device/app/main.cpp`），UI 在 Qt 主线程。UI 线程**不得**直接写 socket；采用单槽请求缓冲，由 device 循环消费（与既有 `inject` 之外唯一跨线程入口风格一致）。

实现要点：

1. `device_priv.h` 阶段四会话区新增字段：
   ```c
   char     ui_tx_text[APP_DATA_TEXT_MAX + 1]; /* UI 线程写，device 循环消费 */
   int      ui_tx_pending;                     /* 0/1，单槽（新请求覆盖未消费旧请求） */
   uint32_t app_data_seq;
   ```
   `device_app_create` 中初始化为 0/空串（确认现有初始化方式后就近补齐）。
2. `device_app.h/.c` 新增公开 API：
   ```c
   int device_app_send_app_data(device_app_t *app, const char *text);
   ```
   行为：`app`/`text` 为 NULL、text 为空、`strlen(text) > APP_DATA_TEXT_MAX`、`device_app_get_state(app) != DEV_STATE_SESSION` → 返回 `DEMO_ERR`；否则拷贝进 `ui_tx_text` 后置 `ui_tx_pending = 1`，返回 `DEMO_OK`。单槽覆盖语义：上一条未消费时被新请求覆盖，日志记录一次覆盖事件。
3. `device_session.c`：
   - `session_poll` 末尾新增冲刷：`ui_tx_pending && sess_sock != NULL` → 构造 `{"cmd":"app_data","seq":++app_data_seq,"data":{"type":"debug_text","text":...}}` → `device_send_frame(app, app->sess_sock, obj)` → 清 `ui_tx_pending` → `LOG_I`"会话：已向上位机发送调试消息（N 字节）"。发送失败（连接已断）同样清标志并 `LOG_W`。
   - `session_on_msg` 的 `CMD_APP_DATA` 分支由"已忽略"改为：解析 `data.text`（字符串）→ `LOG_I(device_id, "会话：收到上位机调试消息：%s", ...)`；无 `data.text` 时保留原占位日志。
4. `DeviceWindow`（`demo/device/ui/device_window.h/.cpp`）新增：
   - `QLineEdit *msg_edit_`（placeholder "输入发给上位机的联调消息（≤512 字节）"）+ `QPushButton *msg_send_button_`（"发送消息"），加入既有 `controls` 横向布局（注入按钮与停止按钮之间或之后均可，保持一行）。
   - 发送槽：调 `device_app_send_app_data(device_, text)`；`DEMO_OK` → `LOG_I`"下位机界面：联调消息已提交发送"；`DEMO_ERR` → `LOG_W`"发送失败：未在会话状态或消息为空/超长"。

## 4. 硬件抽象层文档设计（SubStage_03 / SubStage_04）

### 4.1 接口完备性审计（SubStage_03 前置工作）

对照 `ESP32-C2配网与连接保障流程.docx` 五阶段流程逐点核对 `net_backend_t` 29 个接口的覆盖情况，结论写入《硬件抽象层接口规范》附录。审计基线（阶段一已初步核对）：

| 流程点 | 依赖接口 |
|--------|----------|
| WiFi 扫描/STA 连接/reason code | `wifi_scan`、`wifi_sta_connect`（`wifi_reason_t` 出参）、`wifi_sta_disconnect` |
| SoftAP 配网热点 | `wifi_ap_start`（ssid/pass/pin）、`wifi_ap_stop`、`wifi_get_ip` |
| RSSI 监测 | `wifi_get_rssi` |
| TCP 配网服务器/业务连接 | `tcp_listen/accept/connect/send/recv/close` |
| mDNS 主发现 | `mdns_register/unregister/resolve` |
| UDP 组播兜底 | `udp_mcast_join/send/recv` |
| NVS 持久化（凭据/候选列表/事件日志） | `nvs_get/set/erase` |
| 错峰/退避/心跳计时 | `time_ms`、`random` |

审计如发现缺口：接口层面补齐（需同步四后端时上报 MainAgent 评估）；纯平台特性差异在文档中标注"不适用项"。
