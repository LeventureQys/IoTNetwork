## 2. 当前问题结论

当前问题发生在设备热点的 DHCP 阶段，不是 TCP 协议、PIN 认证或 WiFi 配置消息阶段。

PC 已经成功扫描并关联设备热点 `Modu_0001`，但设备端没有向 PC 提供可用的 DHCP 租约。Windows 等待约 10 秒后只能生成 APIPA 自分配地址 `169.254.150.251`，因此无法取得设备 AP 网关，也不可能继续连接设备 TCP `5935`。

本次流程尚未执行到以下步骤：

- 没有取得设备服务器地址。
- 没有发起 TCP `5935` 连接。
- 没有发送 `auth`。
- 没有发送 `wifi_config`。
- 没有涉及目标 WiFi `CMCC-KnW5` 密码是否正确。

因此，当前首先需要修复 Linux 设备端 SoftAP DHCP 服务。

## 4. 设备端最可能的问题

在开始修改代码前，需要区分“日志已经证明的事实”和“需要在 Linux 设备上继续验证的根因”。

| 结论 | 证据级别 | 说明 |
|---|---|---|
| PC 已成功关联 `Modu_0001` | 已确认 | Windows WLAN 日志明确显示关联成功 |
| PC 没有获得设备 DHCP 租约 | 已确认 | Windows 最终只有 `169.254.150.251` |
| TCP `5935` 连接失败 | 尚未发生 | 流程在 DHCP 阶段已经终止，没有执行 TCP connect |
| `dnsmasq` 没有发出有效 DHCPACK | 高概率 | APIPA 说明 PC 没有完成 DHCP，但仍需设备抓包确认是无 OFFER、OFFER 无效还是报文被丢弃 |
| AP 与 STA/LAN 网段冲突 | 高风险、待设备确认 | PC 原网络为 `192.168.1.0/24`；若设备 STA 也在该网段，则与 AP 配置重叠 |
| 防火墙丢弃 DHCP | 待设备确认 | 需要查看规则和 `tcpdump` |
| 系统 dnsmasq 配置干扰 | 待设备确认 | 当前命令未隔离 `/etc/dnsmasq.conf` |

因此，本次可以直接确认的问题是“设备 DHCP 对 PC 不可用”。具体是网段冲突、dnsmasq 绑定失败、系统配置冲突还是防火墙丢包，应按本文第 10 节的诊断树逐项确认。

### 4.1 AP 网段与现有局域网网段冲突

这是本次日志新增暴露出的最高优先级风险，但在取得设备 STA 地址和 DHCP 抓包前，不能把它写成唯一根因。

PC 配网前地址为：

```text
192.168.1.191
```

当前 Linux 设备 AP 配置为：

```text
AP 网关：192.168.1.1/24
DHCP 池：192.168.1.100 - 192.168.1.200
```

相关配置：

```text
demo/config/linux_hotspot.json
demo/net_linux/linux_hotspot.c
```

这意味着 PC 原局域网和设备 SoftAP 使用了相同的 `192.168.1.0/24`。

如果 Linux 设备的 STA 网卡也连接在该局域网，它很可能也有一个 `192.168.1.x/24` 地址。设备将同时拥有：

```text
STA 接口：192.168.1.x/24
AP 接口：192.168.1.1/24
```

这会造成：

- 同一 Linux 主机的 STA 和 AP 接口拥有重叠路由。
- `192.168.1.1` 很可能已经是上游路由器地址，设备 AP 再使用该地址会产生地址语义冲突。
- DHCP 地址池与上游局域网地址池重叠。
- DHCP、ARP、路由选择和 NAT 行为不确定。
- 即使 DHCP 偶尔成功，后续 TCP 和切换目标 WiFi 也可能走错接口。

上一轮为了与旧协议固定地址保持一致，将真实 Linux AP 从 `10.42.0.1` 改为 `192.168.1.1`。本次真实日志证明，真实设备不应继续强制使用容易与现场路由器冲突的 `192.168.1.0/24`。

### 4.2 设备只检查 dnsmasq 进程，没有检查 DHCP 服务就绪

当前代码在启动 `dnsmasq` 后只检查：

```text
PID 文件存在
进程 kill -0 成功
```

位置：

```text
demo/net_linux/linux_hotspot.c
linux_hotspot_start()
```

这不能证明：

- `dnsmasq` 已在 `ap0` 的 UDP 67 上监听。
- DHCP range 已正确绑定到 `ap0`。
- DHCP 配置没有被系统配置文件干扰。
- 防火墙允许 `DHCPDISCOVER/DHCPOFFER`。
- PC 能收到 DHCP 广播响应。

因此设备可能打印“真实热点已启动”，但 DHCP 实际不可用。

### 4.3 dnsmasq 仍可能读取系统配置

当前命令没有显式使用：

```text
--conf-file=/dev/null
```

因此 `dnsmasq` 可能继续读取设备系统中的 `/etc/dnsmasq.conf` 或相关配置目录。系统配置中的接口、bind、DHCP range、用户、PID 文件等设置可能与程序命令冲突。

设备端启动的配网 DHCP 应使用一套完全独立、可预测的配置，不应继承系统 dnsmasq 配置。

### 4.4 没有处理设备防火墙

代码当前配置了 NAT，但没有确保 AP 接口允许 DHCP：

```text
客户端 UDP 68 -> 服务端 UDP 67
服务端 UDP 67 -> 客户端 UDP 68
```

如果设备启用了 `iptables/nftables/firewalld/ufw`，`dnsmasq` 即使正常监听，DHCP 报文仍可能被 INPUT/OUTPUT 规则丢弃。

### 4.5 热点开始广播早于 DHCP 完全就绪

当前时序为：

```text
启动 hostapd并开始广播
配置 ap0 地址
启动 dnsmasq
报告热点成功
```

PC 可能在 `dnsmasq` 就绪前立即关联并发送第一次 DHCPDISCOVER。正常 DHCP 客户端会重试，因此这通常不是永久失败的唯一原因，但设备代码仍应在 DHCP ready 后才向上层报告“热点可用于配网”。

## 5. PC 端是否还有问题

从本次日志看，PC 端在当前故障阶段的处理是正确的：

- 成功扫描 `Modu_0001`。
- 成功关联设备热点。
- 等待 DHCP 地址。
- 正确识别 `169.254.x.x` 为 DHCP 失败。
- 没有使用错误网关继续尝试 TCP。
- 给出了设备 DHCP/AP 网关诊断信息。

本次日志没有进入 `net_wifi_get_gateway()` 和 TCP 连接阶段，因为 `wlan_connect()` 已在 APIPA 检查处终止。

PC 端暂时不需要为了本次现象修改 TCP、PIN 或 JSON 协议代码。

## 6. 推荐的设备端代码修复

### 6.1 第一优先级：真实 AP 改用不冲突网段

推荐将 Linux 真实设备热点改回独立网段：

```text
AP 地址：10.42.0.1/24
DHCP 池：10.42.0.100 - 10.42.0.200
DHCP router：10.42.0.1
TCP 服务：10.42.0.1:5935
```

需要修改：

```text
demo/config/linux_hotspot.json
demo/net_linux/linux_hotspot.c
demo/net_linux/linux_hotspot.h
```

PC 已经通过目标 WLAN 的 DHCP router 动态获取设备服务器地址，因此真实 Linux 设备不需要固定为 `192.168.1.1`。

模拟环境可以继续使用逻辑地址 `192.168.1.1`，但必须在文档中明确：

```text
192.168.1.1：仅模拟逻辑地址或旧协议示例
真实 Linux：以 DHCP router option 为准
```

### 6.2 第二优先级：启动前检测 AP 与 STA 网段冲突

不能只把地址改成 `10.42.0.1` 后结束。设备代码应在每次启动热点前检查：

1. 读取 `sta_interface` 当前 IPv4 和前缀。
2. 计算 STA 子网。
3. 计算配置的 AP 子网和 DHCP 池。
4. 如果 AP 子网与 STA 子网重叠，拒绝启动并打印明确错误，或自动选择备用网段。

建议备用网段候选：

```text
10.42.0.0/24
10.43.0.0/24
172.31.250.0/24
192.168.250.0/24
```

建议新增内部函数：

```c
static int validate_hotspot_network(void);
static int interface_ipv4_subnet(const char *interface_name,
                                 uint32_t *network,
                                 uint32_t *netmask);
```

如果检测到冲突，应输出类似日志：

```text
AP 网段 192.168.1.0/24 与 STA wlP2p33s0 网段 192.168.1.0/24 冲突，拒绝启动 DHCP
```

### 6.3 第三优先级：隔离 dnsmasq 系统配置

启动参数应增加：

```text
--conf-file=/dev/null
```

建议 DHCP-only 参数语义：

```text
--conf-file=/dev/null
--port=0
--bind-interfaces
--interface=ap0
--listen-address=10.42.0.1
--dhcp-authoritative
--dhcp-range=10.42.0.100,10.42.0.200,255.255.255.0,12h
--dhcp-option=option:router,10.42.0.1
--dhcp-option=option:server-id,10.42.0.1
--pid-file=/tmp/dnsmasq_modu_ap.pid
--log-dhcp
```

应继续使用配置变量生成地址，不能在命令中写死 `10.42.0.1`。

### 6.4 第四优先级：增加 DHCP readiness 检查

`linux_hotspot_start()` 返回 `DEMO_OK` 前至少验证：

1. `ap0` 存在且类型为 AP。
2. `ap0` 拥有预期 IPv4/prefix。
3. `dnsmasq` 进程存活。
4. UDP 67 确实绑定在 AP 地址或 AP 接口。
5. AP 子网没有与 STA 子网重叠。

建议新增：

```c
static int ap_has_expected_ipv4(void);
static int dhcp_server_is_listening(void);
```

如果 readiness 检查失败：

```text
停止 dnsmasq
停止 hostapd
删除 ap0
返回 DEMO_ERR
```

上层不得记录“设备热点已启动”。

### 6.5 第五优先级：处理 DHCP 防火墙规则

如果产品设备默认启用防火墙，热点启动时应确保允许：

```text
AP 入站 UDP 67
AP 出站 UDP 68
AP 入站 TCP 5935
```

停止热点时应删除由本程序添加的规则，避免重复添加和污染系统规则。

如果防火墙由系统服务统一管理，则代码不应直接修改全局规则，但安装脚本或 systemd 单元必须提供对应规则，并在启动日志中检查/提示。

### 6.6 第六优先级：改进设备端失败日志

设备日志应至少打印：

```text
STA 接口及当前 IPv4/prefix
AP 接口及配置 IPv4/prefix
DHCP range
dnsmasq 完整启动结果
UDP 67 readiness 结果
TCP 5935 监听地址
AP/STA 网段是否冲突
```

这样 PC 出现 APIPA 时，可以直接从设备日志判断是网段冲突、dnsmasq、UDP 67 还是防火墙问题。

## 7. 推荐修复顺序

1. 将真实 Linux AP 改为 `10.42.0.1/24`，避免与现场 `192.168.1.0/24` 冲突。
2. 增加 AP/STA 网段冲突检测，防止未来换网络后再次冲突。
3. 为 `dnsmasq` 增加 `--conf-file=/dev/null`，隔离系统配置。
4. 增加 AP 地址和 UDP 67 readiness 检查。
5. 检查并放行 AP 接口 DHCP 和 TCP 5935 防火墙规则。
6. 在设备端抓包确认完整 DHCP 四步交互。
7. DHCP 成功后再检查 TCP `10.42.0.1:5935`。

### C. `demo/net_linux/linux_hotspot.c`：默认值和 JSON 加载

在 `linux_hotspot_cfg_defaults()` 中改为：

配置解析完成后必须校验：

- `subnet` 是合法 IPv4。
- `prefix_length` 建议限制在 16 到 30。
- `dhcp_start` 和 `dhcp_end` 是合法 IPv4。
- DHCP 起始地址小于等于结束地址。
- DHCP 池与 AP 地址位于同一子网。

建议新增纯逻辑函数：

```c
static int parse_ipv4_host_order(const char *text, uint32_t *value);
static uint32_t prefix_to_mask(int prefix_length);
static int validate_dhcp_range(const linux_hotspot_cfg_t *cfg);
```

示例校验逻辑：

```c
static int validate_dhcp_range(const linux_hotspot_cfg_t *cfg)
{
    uint32_t ap_ip;
    uint32_t start_ip;
    uint32_t end_ip;
    uint32_t mask;

    if (!parse_ipv4_host_order(cfg->subnet, &ap_ip) ||
        !parse_ipv4_host_order(cfg->dhcp_start, &start_ip) ||
        !parse_ipv4_host_order(cfg->dhcp_end, &end_ip))
        return DEMO_ERR_INVAL;
    if (cfg->prefix_length < 16 || cfg->prefix_length > 30)
        return DEMO_ERR_INVAL;

    mask = prefix_to_mask(cfg->prefix_length);
    if ((ap_ip & mask) != (start_ip & mask) ||
        (ap_ip & mask) != (end_ip & mask) ||
        start_ip > end_ip ||
        (ap_ip >= start_ip && ap_ip <= end_ip))
        return DEMO_ERR_INVAL;
    return DEMO_OK;
}
```

以上示例是实现方向，具体整数端序要在函数内部统一使用主机序，避免与 socket 网络序混用。

### D. `demo/net_linux/linux_hotspot.c`：AP/STA 网段冲突检测

建议不要通过解析 `ip` 命令文本实现，优先使用 `getifaddrs()`：

```c
#include <arpa/inet.h>
#include <ifaddrs.h>
#include <netinet/in.h>
```

建议新增：

```c
static int interface_ipv4_network(const char *interface_name,
                                  uint32_t *network,
                                  uint32_t *netmask)
{
    struct ifaddrs *addresses = NULL;
    struct ifaddrs *entry;
    int found = 0;

    if (getifaddrs(&addresses) != 0)
        return DEMO_ERR;
    for (entry = addresses; entry != NULL; entry = entry->ifa_next) {
        if (entry->ifa_addr == NULL || entry->ifa_netmask == NULL ||
            entry->ifa_addr->sa_family != AF_INET ||
            strcmp(entry->ifa_name, interface_name) != 0)
            continue;
        const struct sockaddr_in *address =
            (const struct sockaddr_in *)entry->ifa_addr;
        const struct sockaddr_in *mask =
            (const struct sockaddr_in *)entry->ifa_netmask;
        *netmask = ntohl(mask->sin_addr.s_addr);
        *network = ntohl(address->sin_addr.s_addr) & *netmask;
        found = 1;
        break;
    }
    freeifaddrs(addresses);
    return found ? DEMO_OK : DEMO_ERR;
}
```

再新增：

```c
static int validate_no_sta_ap_overlap(void)
{
    uint32_t sta_network;
    uint32_t sta_mask;
    uint32_t ap_ip;
    uint32_t ap_mask;
    uint32_t ap_network;

    if (interface_ipv4_network(g_cfg.sta_interface,
                               &sta_network, &sta_mask) != DEMO_OK)
        return DEMO_OK;
    if (!parse_ipv4_host_order(g_cfg.subnet, &ap_ip))
        return DEMO_ERR_INVAL;
    ap_mask = prefix_to_mask(g_cfg.prefix_length);
    ap_network = ap_ip & ap_mask;

    if ((ap_network & sta_mask) == sta_network ||
        (sta_network & ap_mask) == ap_network) {
        LOG_E(TAG, "AP 网段与 STA 接口 %s 网段重叠，拒绝启动热点",
              g_cfg.sta_interface);
        return DEMO_ERR_INVAL;
    }
    return DEMO_OK;
}
```

调用位置：`linux_hotspot_start()` 在创建 `ap0` 和启动 `hostapd` 之前。

如果设备业务要求热点必须启动，可以实现自动网段选择；如果没有该要求，推荐先“检测到冲突就失败”，不要静默选择不可追踪的地址。

### E. `demo/net_linux/linux_hotspot.c`：配置 AP 地址

当前代码写死 `/24`：

```c
run_cmd("ip addr add %s/24 dev %s", ...)
```

应改为：

```c
run_cmd("ip addr add %s/%d dev %s",
        g_cfg.subnet, g_cfg.prefix_length, g_cfg.ap_interface)
```

配置后不能只检查命令退出码，还要读取接口地址确认内核实际生效。

建议新增：

```c
static int ap_has_expected_ipv4(void);
```

可使用 `getifaddrs()` 精确比较 `ap_interface` 的 IPv4 和掩码。若不匹配，应立即调用 `linux_hotspot_stop()` 并返回失败。

### F. `demo/net_linux/linux_hotspot.c`：重写 dnsmasq 启动参数

建议把命令调整为：

```c
int dnsmasq_rc = run_cmd(
    "%s --conf-file=/dev/null --port=0 "
    "--bind-interfaces --interface=%s --listen-address=%s "
    "--dhcp-authoritative "
    "--dhcp-range=%s,%s,255.255.255.0,12h "
    "--dhcp-option=option:router,%s "
    "--dhcp-option=option:server-id,%s "
    "--pid-file=%s --log-dhcp",
    g_cfg.dnsmasq_bin,
    g_cfg.ap_interface,
    g_cfg.subnet,
    g_cfg.dhcp_start,
    g_cfg.dhcp_end,
    g_cfg.subnet,
    g_cfg.subnet,
    g_dnsmasq_pid);
```

如果支持非 `/24`，子网掩码不能固定为 `255.255.255.0`，应由 `prefix_length` 生成字符串。

关键变化：

- `--conf-file=/dev/null`：禁止读取系统 dnsmasq 配置。
- `--port=0`：继续禁用 DNS，只提供 DHCP。
- 使用具名 option，减少数字 option 可读性问题。
- DHCP range 显式包含掩码。

如果设备系统已经有一个全局 dnsmasq 占用 UDP 67，即使加 `--bind-interfaces` 仍可能冲突。启动前应检查并明确报错，不要直接杀死系统服务。

### G. `demo/net_linux/linux_hotspot.c`：DHCP readiness

不要只检查 PID。推荐由本进程创建 UDP socket，尝试验证 UDP 67 的端口占用情况有一定局限，因为端口已经由 dnsmasq 持有；更可靠的实现有两种：

方案 1，推荐用于当前 Demo：调用 `ss` 并检查输出中存在 dnsmasq/UDP 67/AP 地址。

```c
static int dhcp_server_is_listening(void)
{
    char cmd[512];
    snprintf(cmd, sizeof(cmd),
             "ss -H -lunp 'sport = :67' | grep -F '%s:67' | grep -F dnsmasq >/dev/null",
             g_cfg.subnet);
    return run_cmd("%s", cmd) == 0 ? DEMO_OK : DEMO_ERR;
}
```

方案 2，推荐用于正式产品：不依赖 shell，读取 `/proc/net/udp` 并结合 PID/fd，或使用 netlink 获取 socket diagnostics。

当前项目是 Demo，可先采用方案 1，但要注意不同 `ss` 版本的输出格式，Linux 实机测试时确认命令兼容。

启动后最多等待 2 秒：

```c
for (int attempt = 0; attempt < 20; ++attempt) {
    if (dhcp_server_is_listening() == DEMO_OK)
        break;
    sleep_ms(100);
}
```

超时后必须回滚并返回 `DEMO_ERR`。

需要强调：UDP 67 监听成功仍不等于客户端一定能收到 DHCP，所以最终验收仍必须包含 `tcpdump` 和真实 PC 获取租约。

### H. `demo/net_linux/linux_hotspot.c`：防火墙处理

不要无条件清空系统防火墙。推荐采用专用链或由部署脚本管理。

如果由程序管理，可使用带唯一注释的规则，并在 stop 时删除完全相同的规则。例如：

```bash
iptables -C INPUT -i ap0 -p udp --dport 67 -m comment --comment modu-provision -j ACCEPT
iptables -A INPUT -i ap0 -p udp --dport 67 -m comment --comment modu-provision -j ACCEPT
iptables -C INPUT -i ap0 -p tcp --dport 5935 -m comment --comment modu-provision -j ACCEPT
iptables -A INPUT -i ap0 -p tcp --dport 5935 -m comment --comment modu-provision -j ACCEPT
```

但如果目标系统使用 nftables/firewalld，上述规则可能不是最终策略。更稳妥的产品方案是：

- 代码只检测端口和记录错误。
- 安装脚本或 systemd 服务负责防火墙。
- 文档明确要求放行 `ap0` UDP 67 和 TCP 5935。

### I. `demo/net_linux/linux_hotspot.c`：启动事务和清理

建议将 `linux_hotspot_start()` 按以下阶段实现：

```text
1. 加载并校验配置
2. 检查 root 和外部命令
3. 检查 AP/STA 网段冲突
4. 清理本程序残留资源
5. 创建 AP 接口
6. 启动 hostapd并验证 AP 模式
7. 配置并验证 AP IPv4
8. 启动 dnsmasq
9. 验证 dnsmasq PID 和 UDP 67
10. 配置可选 NAT/防火墙
11. 设置 g_active=1
12. 返回 DEMO_OK
```

第 4 到第 10 步任意失败都必须走统一失败出口：

```c
fail:
    linux_hotspot_stop();
    return DEMO_ERR;
```

不要在多个分支中遗漏 pidfile、接口或规则清理。

同时建议在 `linux_hotspot_stop()` 中：

- 删除 dnsmasq pidfile。
- 删除 hostapd pidfile和临时配置。
- 删除本程序添加的 NAT/防火墙规则。
- 删除 `ap0`。
- 只有完成清理后设置 `g_active=0`。

### J. `demo/device/device_app.c`

当前 `sm_ap_provision()` 在 `prov_server_start()` 失败后每约 100 ms 重试：

```c
if (rc != DEMO_OK) {
    device_sleep_ms(100);
    return;
}
```

如果失败原因是网段冲突、UDP 67 被占用或缺少权限，这会造成日志刷屏和持续执行外部命令。

建议改为使用已有 `provision_ap_backoff_ms`：

```c
if (rc != DEMO_OK) {
    evlog_record(app, "配网热点启动失败，等待退避后重试");
    app->boot_backoff_until = now +
        (uint64_t)app->params->provision_ap_backoff_ms;
    device_set_state(app, DEV_STATE_BOOT);
    return;
}
```

这样永久配置错误不会每 100 ms 重启 `hostapd/dnsmasq`。

当前顺序为先监听 TCP，再启动 AP。这一设计可以保留，因为 `0.0.0.0:5935` 会覆盖后续创建的 `ap0` 地址。

但建议增强日志：

```text
配网 TCP listener 已创建
AP/DHCP 正在启动
```


## 7.2 不推荐的修复方式

以下修改不能从根本上解决问题：

- 只把 PC DHCP 等待时间从 10 秒增加到 30 秒。永久没有 DHCP 响应时只会让失败更慢。
- PC 在 APIPA 状态下强行连接 `192.168.1.1:5935`。APIPA 与 `192.168.1.0/24` 不同网段，通常没有可用路由。
- PC 扫描 `192.168.1.0/24` 猜测设备地址。会误连现场路由器且存在安全风险。
- 只检查 `dnsmasq` 进程存在。进程存活不等于 DHCP 可服务。
- 发现 UDP 67 被占用后直接杀死系统 dnsmasq。可能破坏设备其他网络业务。
- 同时让 STA 和 AP 使用 `192.168.1.0/24`，再依赖 route metric 修补。ARP 和地址池冲突仍然存在。

## 10. Linux 现场诊断决策树

以下步骤用于在改代码前确认具体根因，也用于改代码后验收。必须按顺序执行，不要在 DHCP 未通过时先排查 JSON/TCP 协议。

### 步骤 1：确认设备 STA 与 AP 是否重叠

执行：

```bash
ip -4 addr show dev wlP2p33s0
ip -4 addr show dev ap0
ip -4 route
```

判断：

- 如果 STA 是 `192.168.1.x/24`，AP 也是 `192.168.1.1/24`：已确认网段冲突，先改 AP 网段。
- 如果 STA 不是 `192.168.1.0/24`：网段冲突不是本次直接原因，继续步骤 2。
- 如果 `ap0` 没有 IPv4：AP 地址配置失败，检查 `ip addr add` 日志和权限。
- 如果 `ap0` 不存在：检查虚拟接口创建、PHY 和 hostapd。

### 步骤 2：确认 dnsmasq 是否真正监听 UDP 67

执行：

```bash
ps -ef | grep '[d]nsmasq'
ss -H -lunp 'sport = :67'
```

判断：

- 没有 dnsmasq 进程：启动命令失败或进程启动后退出。
- 有进程但没有 UDP 67：配置冲突、权限、接口或系统配置有问题。
- UDP 67 监听在错误地址/接口：修正 `--interface`、`--listen-address` 和系统配置隔离。
- UDP 67 正常：继续步骤 3。

### 步骤 3：前台运行独立 dnsmasq 获取真实错误

先停止设备程序创建的热点服务，避免端口冲突，然后测试：

```bash
sudo dnsmasq \
  --no-daemon \
  --conf-file=/dev/null \
  --port=0 \
  --bind-interfaces \
  --interface=ap0 \
  --listen-address=10.42.0.1 \
  --dhcp-authoritative \
  --dhcp-range=10.42.0.100,10.42.0.200,255.255.255.0,12h \
  --dhcp-option=option:router,10.42.0.1 \
  --dhcp-option=option:server-id,10.42.0.1 \
  --log-dhcp
```

判断：

- 报 `Address already in use`：UDP 67 已被其他 DHCP 服务占用。
- 报 `unknown interface ap0`：AP 接口尚未创建或已被删除。
- 报 `cannot bind DHCP socket`：权限、端口、接口或地址配置有问题。
- 前台正常运行：继续步骤 4，并保持该进程运行做抓包测试。

### 步骤 4：抓包判断 DHCP 卡在哪一步

执行：

```bash
sudo tcpdump -ni ap0 -e -vvv 'udp port 67 or udp port 68'
```

让 Windows 重新连接 `Modu_0001`。

判断：

| 抓包结果 | 结论 | 修复方向 |
|---|---|---|
| 完全没有 DHCPDISCOVER | PC 请求没有到达 `ap0`，检查 AP 接口、无线驱动、客户端关联状态 |
| 有 DISCOVER，无 OFFER | dnsmasq 未处理、接口绑定错误、配置冲突或防火墙 INPUT 丢弃 |
| 有 DISCOVER 和 OFFER，无 REQUEST | PC 拒绝 OFFER；检查地址池、掩码、server-id、重复网段和旧租约 |
| 有 REQUEST，无 ACK | dnsmasq 配置/租约处理问题，查看前台日志 |
| 四步完整，但 PC 仍 APIPA | 检查 Windows 适配器状态、是否抓错接口、ACK 内容是否合法 |

### 步骤 5：检查防火墙计数

根据系统选择命令：

```bash
sudo iptables -vnL INPUT
sudo iptables -vnL OUTPUT
sudo nft list ruleset
sudo firewall-cmd --list-all 2>/dev/null
sudo ufw status verbose 2>/dev/null
```

如果规则默认 DROP，应明确放行 `ap0` DHCP 和 TCP 5935。修改后再次抓包，不要只看规则文本，要观察包计数是否变化。

### 步骤 6：DHCP 成功后再验证 TCP

设备端：

```bash
ss -H -lntp 'sport = :5935'
```

Windows：

```powershell
ipconfig /all
route print -4
Test-NetConnection 10.42.0.1 -Port 5935
```

只有 DHCP 地址和默认网关正确后，TCP 结果才有诊断意义。

## 12. 验收标准

### 12.1 必须通过

| 验收项 | 通过条件 |
|---|---|
| AP/STA 网段 | 不重叠；设备日志明确打印两者网络 |
| AP 接口 | `ap0` 存在、AP 模式、拥有预期 IPv4/prefix |
| DHCP 进程 | 独立 dnsmasq 存活，且不读取系统配置 |
| DHCP socket | UDP 67 readiness 检查通过 |
| DHCP 报文 | 抓包看到 DISCOVER/OFFER/REQUEST/ACK |
| Windows 地址 | 获得 DHCP 池地址，不是 `169.254.x.x` |
| Windows 网关 | 等于设备 AP 地址 |
| TCP | Windows 可连接设备 AP 地址的 `5935` |
| 配网协议 | PC 开始发送 `auth` 并收到 `auth_result` |
| 失败回滚 | dnsmasq/AP 地址失败时设备不打印“热点已启动” |
| 重试策略 | 永久错误不会每 100 ms 重启热点服务 |

### 12.2 建议回归场景

1. STA 网络为 `192.168.1.0/24`，AP 默认 `10.42.0.0/24`，应正常启动。
2. 人为把 AP 改为 `192.168.1.1/24`，冲突检测应拒绝启动。
3. 占用 UDP 67，设备应明确失败并回滚。
4. 配置不存在的 STA 接口，设备应打印准确错误或明确进入无 STA 情况。
5. 停止 dnsmasq 后立即退出，readiness 应检测失败。
6. 防火墙丢弃 UDP 67，抓包和规则计数应能定位。
7. 连续启停热点 20 次，不应残留 `ap0`、pidfile 或孤儿进程。
8. PC 原网络分别为 `192.168.1.0/24`、`10.0.0.0/24`，都应能获得设备 DHCP 地址。
9. DHCP 成功后，TCP `5935` 和完整 `auth -> wifi_config` 流程通过。
