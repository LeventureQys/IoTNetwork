### 自决区（不阻塞）

#### Q1. 跨进程集成测试如何避免依赖中文自由日志

- 问题描述：现有跨端测试 `demo/tests/test_host_app.cpp` 通过同进程私有对象和日志判断状态；拆分后 `integration_tests/` 不得包含两端私有源码，且两个进程不能共享 `SimWorld` 内存。
- 自决方案：两端宿主程序新增可选 `--events-jsonl <path>` 与 `--scenario <path>` 测试接口。事件文件使用稳定 JSON Lines schema；scenario 仅在显式模拟后端下允许，支持自动配网、双向 `app_data`、连接故障和定时退出。集成测试只启动公开可执行文件、写 scenario、读取 JSONL 与退出码。
- 自决理由：结构化事件可稳定自动验收，又不暴露私有头或静态库；显式参数确保正式运行默认不启用测试控制能力。
- 风险预警：需要在两端各增加薄事件适配层，但比匹配中文日志更可维护，且不改变线上协议。
- 置信度：93%。

#### Q2. PC 端是否也必须清除所有非 UI C++

- 问题描述：原始需求只限制设备端除顶层界面外必须纯 C；PC 核心、Windows 后端和 PC 模拟后端当前均使用 C++。
- 自决方案：PC 端保持 C++17 + Qt，不做无需求依据的纯 C 重写；只完成目录自包含、职责拆分、运行路径解耦和测试归属迁移。设备端严格执行纯 C 边界。
- 自决理由：语言限制明确只针对设备端，扩大到 PC 会显著增加风险且无验收收益。
- 风险预警：两端模拟后端将不再是同一语言实现，协议与行为一致性必须依靠端侧契约测试和双进程测试保证。
- 置信度：99%。

#### Q3. ESP32-C2 本版本的验收层级

- 问题描述：`demo/net_esp32c2/esp32c2_backend.c` 当前是未实机验证骨架，大部分接口仍返回错误；阶段一已确认不得将其描述为可用固件。
- 自决方案：设备文件夹内提供自包含 ESP-IDF 工程骨架和纯 C 编译入口；工具链存在时执行 `idf.py build`，缺工具链记阻塞。SoftAP、DHCP、STA、发现、会话和 NVS 实机功能明确不属于本版本完成条件；如有板卡可记录信息性现状，但失败不能反向扩大本版本为“补全 ESP32 后端”。
- 自决理由：区分“源码归属/可编译”与“硬件功能完成”，符合零猜测和真实证据原则。
- 风险预警：现有骨架若仍无法通过 ESP-IDF 编译，阶段三必须修到可编译或如实记录失败，不能用宿主语法检查替代；硬件能力继续按骨架 README 标记未实现。
- 置信度：96%。

#### Q4. 公共协议复制后的权威性控制

- 问题描述：需求允许公共代码复制到两端，但不允许保留第三份生产共享源码；两份 `protocol.h/.c` 和 `frame.h/.c` 存在漂移风险。
- 自决方案：两端各自生成公开 `protocol-contract.json`；端侧单测验证本端常量和帧实现；独立集成测试比较两个 manifest 并执行双向真实帧互操作。根目录不保留第三份可编译协议实现。
- 自决理由：同时满足自包含和兼容性门禁，不重新建立源码依赖。
- 风险预警：manifest 不能替代线上互操作测试，两层均为强制项。
- 置信度：95%。
