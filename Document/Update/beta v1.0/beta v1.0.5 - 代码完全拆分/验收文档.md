# beta v1.0.5 代码完全拆分 - 验收文档

## 1. 验收目标

验证 `demo/pc/` 和 `demo/device/` 已成为两个源码、构建、配置、测试和运行资源完全自包含的产品目录；设备端除 Qt UI 与最薄启动入口外全部为纯 C；独立 `demo/integration_tests/` 只消费公开产物，且历史协议和流程行为无回归。

## 2. 验收范围

### 2.1 覆盖

- PC 与设备目录/CMake/源码依赖边界。
- 设备生产代码语言边界和 UI facade 隔离。
- Windows PC 与设备模拟器构建、单测和启动。
- 可用 Linux 环境下 sim 构建、单测、fake hotspot 测试和启动。
- 两端配置、路径、日志、NVS 与 artifact 布局。
- 协议 manifest、帧互操作和双进程 sim 场景。
- 两端复制到仓库外后的独立构建/测试/启动。
- ESP32-C2 ESP-IDF 工程构建（工具链存在时）；ESP32 实机功能仅记录信息性现状，不属于本版本通过条件。
- README、脚本和交付物完整性。

### 2.2 不自动判通过

- Windows 真实 WiFi、现场防火墙和多网卡通告。
- Linux 真实热点、DHCP 和真实无线 STA。
- ESP32 烧录、SoftAP、DHCP、STA、NVS、发现、会话和自愈实机功能。

这些项有环境则执行；缺环境必须记录阻塞，不能以 sim 替代。

## 3. 验收环境

### 3.1 Windows 基线

- Windows 10/11 x64。
- CMake ≥ 3.20、CTest。
- Visual Studio 2022 x64 toolchain。
- Qt 6 Widgets（MSVC 版本匹配）。
- PowerShell 5.1 或更高。

### 3.2 Linux 基线

- 支持 C11/C++17 的 GCC 或 Clang。
- CMake ≥ 3.20、Qt 6 Widgets、pthread。
- 真实热点项另需 root、hostapd、dnsmasq、iw、ip、AP 模式网卡。

### 3.3 ESP32 基线

- ESP-IDF 支持 ESP32-C2 的版本、`idf.py`、Python 和工具链。
- 实机项另需板卡、串口、烧录权限和可控 2.4 GHz 网络。

## 4. 前置条件

1. 使用待验收 Git revision，保存 `git status --short`，不得清理用户无关变更。
2. 删除或使用全新构建目录，不能复用旧 `demo/tests/build` 等缓存。
3. 准备空的验收输出目录 `acceptance/<timestamp>/`。
4. 设置 Qt 路径；自动启动使用 `QT_QPA_PLATFORM=offscreen`。
5. integration 使用两个已构建 artifact，不允许自动回退源码构建。

## 5. 证据规范

每项保存：命令、工作目录、完整 stdout/stderr、退出码、开始/结束时间和判定。建议目录：

## 6. 验收项

### A1. 两个产品目录完整

- 目的：确认两端各自拥有完整工程资源。
- 前置条件：阶段三代码完成。
- 操作步骤：列出 `demo/pc`、`demo/device`，检查各自 CMake、README、源码、配置、脚本、测试、cJSON 和 GoogleTest；检查 `demo/integration_tests`。
- 期望结果：PC 与设备各自资源齐全；integration 不含生产源码。
- 通过标准：两端分别存在 `CMakeLists.txt`、`README.md`、源码、`config/`、`scripts/`、`tests/`、cJSON、GoogleTest 和协议 manifest 生成/install 规则；目录符合设计文档第 4 节。
- 失败标准：配置、第三方、测试或生产源码仍只存在旧根目录；integration 含端侧生产代码。
- 证据要求：目录树和缺失项检查表。

### A2. CMake 源码边界

- 目的：确认没有隐藏的父目录或跨端构建依赖。
- 操作步骤：搜索两端 `CMakeLists.txt`、`.cmake`、源码和头中的 `DEMO_ROOT`、`../pc`、`../device`、旧根 `common/include/net_*/shared_ui/third_party` 引用；检查 `add_subdirectory`、`target_sources`、`target_include_directories`。
- 期望结果：端侧仓库内路径全部位于自身根。
- 通过标准：无生产源码跨根引用，无 symlink/junction 指向旧根。
- 失败标准：任一端配置需要另一端或旧共享生产目录。
- 证据要求：搜索命令及零命中/白名单说明。

### A3. 旧根共享生产源码已清理

- 目的：避免形成第三份权威实现。
- 操作步骤：检查旧根 `cmake/common/include/net_sim/net_win/net_linux/net_esp32c2/shared_ui/config/tests/third_party`。
- 期望结果：已按迁移清单删除；根 `demo/` 只保留导航、两端和 integration。
- 通过标准：不存在第三份可编译生产源码。
- 失败标准：旧库仍可被构建或端侧仍引用它。
- 证据要求：最终目录树和迁移清单逐项核销。

### A4. Integration 无私有源码

- 目的：确认跨端测试为公开产物黑盒测试。
- 操作步骤：扫描 `demo/integration_tests` 的 include、CMake、脚本；只复制 integration 与 artifacts 到临时目录运行配置。
- 期望结果：不出现 `host_app.h`、`device_app.h`、`sim_world.h`，不编译两端 `.c/.cpp`，不 add_subdirectory 两端。
- 通过标准：删除两端源码后 integration 仍能运行 manifest 比较和双进程测试。
- 失败标准：缺源码后配置/编译失败，或链接端侧私有静态库。
- 证据要求：临时目录树、配置日志和依赖扫描。

### B1. 设备生产语言边界

- 目的：验证设备非 UI 全部纯 C。
- 操作步骤：列出设备生产 `.cpp`；扫描 `device/src`、`backends`、`firmware` 中 Qt 头、`std::`、class、new/delete；检查 compile commands 和 CMake target language。
- 期望结果：生产 `.cpp` 仅存在 `app/qt_main.cpp` 和 `ui/`；其余以 C 编译器编译。
- 通过标准：core/runtime/config/platform/backend/firmware 不依赖 C++ runtime 或 Qt。
- 失败标准：任一非 UI `.cpp`、Qt/C++ 符号命中，或 `.c` 被强制按 C++ 编译。
- 证据要求：文件列表、扫描结果、compile commands 片段、链接图。

### B2. UI 仅依赖 C facade

- 目的：验证设备 UI 不绕过边界。
- 操作步骤：检查 `device/app` 和 `device/ui` include 与对象成员。
- 期望结果：UI 只包含公开 `device_host.h` 和 Qt/UI 自身头；不出现 `device_app_t`、`net_ctx_t`、具体 backend。
- 通过标准：依赖方向为 Qt→facade→runtime/core/backend，无反向依赖。
- 失败标准：UI 直接操作核心、网络或后端，C core include UI 头。
- 证据要求：include 扫描和 CMake link graph。

### B3. Facade 生命周期和线程安全

- 目的：验证 create/start/stop/join/destroy 及跨线程 DTO。
- 操作步骤：运行设备 runtime 测试，覆盖未启动销毁、重复 start、stop 幂等、join timeout、运行中 destroy、队列满、日志溢出、并发 snapshot、join 后无写入。
- 期望结果：返回码符合设计文档，无崩溃、死锁、数据竞争或泄漏。
- 通过标准：所有测试通过；可用 sanitizer/TSAN 环境无相关报告。
- 失败标准：覆盖旧命令、悬空日志回调、join 后写入、运行中隐式销毁或 data race。
- 证据要求：CTest/JUnit 和 sanitizer 日志。

### B4. `net_ctx` 初始化失败传播

- 目的：验证后端 init 失败不会产生可用 context。
- 操作步骤：两端分别使用返回错误的 fake backend 调用新 `net_ctx_create`。
- 期望结果：函数返回原错误，输出 ctx 为 NULL，只释放已创建资源，不调用未初始化 deinit。
- 通过标准：PC 与设备副本均有测试且通过。
- 失败标准：忽略 init 错误、返回非 NULL 或双重释放。
- 证据要求：两端测试名称和输出。

### H2. Linux Qt offscreen 启动

### I1. Windows 真实 WiFi

- 操作步骤：在专用无线测试机执行真实扫描、连接设备 AP、下发目标 WiFi、切回目标 WiFi、UDP 通告与 TCP 会话。

### I2. Linux 真实热点与 DHCP

- 通过标准：完整实测通过。
- 失败标准：执行后失败或回退 sim。
- 阻塞标准：缺 root、依赖或 AP 网卡。
- 证据要求：命令、接口状态、进程、DHCP 抓包/日志。

## 7. 回归范围

必须回归：帧、协议、参数、日志、网络抽象、设备状态机、配网、发现、注册、心跳、自愈、AP 失败退避、Linux 热点事务、Windows监听生命周期、双向 app_data。目录重构不得修改协议和 NVS 语义。

只做冒烟：Qt 视觉布局、历史日志流程图展示。真实 PC/Linux 项按 I1、I2 判定；ESP32 实机按 I3 仅记录信息性现状。

## 8. 失败与阻塞处理

- 构建、单测、sim 启动、sim integration、隔离复制失败：阶段三失败，定位对应 SubStage 修复。
- 语言边界或源码依赖泄漏：阶段三失败，不允许豁免。
- 协议 manifest 不一致：阶段三失败，禁止用覆盖文件掩盖。
- 工具链存在但命令失败：失败，不是阻塞。
- 仅外部硬件、权限或专用网络缺失可记阻塞；必须记录项编号、已执行步骤、原命令、错误、缺失条件和解除方法。
- 任一阻塞项不得默认通过，也不得由 sim 结果替代。

## 9. 最终通过条件

阶段四最终通过必须同时满足：

1. A～H、J 中当前环境可执行项全部通过，无失败。
2. PC 与设备仓库外复制验收通过。
3. 设备语言边界和 facade 隔离通过。
4. 双端 protocol manifest 和真实帧互操作通过。
5. integration 不含任何端侧生产源码。
6. 旧根第三份生产源码已删除。
7. I1、I2 已通过，或因真实外部条件明确记录阻塞并由用户接受；I3 仅需如实记录信息性现状。
8. 验收报告逐项附证据，不引用对话历史。
