# 验收文档 - v1.0.6 文档更新说明

## 1. 验收范围

### 1.1 覆盖

- `Document/移植说明/` 下4份 .docx 文档的完整性、准确性、可读性
- 6张重新生成的流程图的布局质量
- .md 源文件的内容一致性
- 硬件抽象层审计结论的准确性

### 1.2 不覆盖

- ESP32 实机验证（文档标明为骨架/指南，不宣称实机可用）
- PC 上位机或设备端源代码的任何修改
- 之前版本的文档（v1.0.0 ~ v1.0.5）

## 2. 验收环境

| 项目 | 要求 |
|------|------|
| 操作系统 | Windows 10/11 |
| Python | 3.8+，含 graphviz + python-docx + Pillow |
| Graphviz | 系统已安装（用于 dot → PNG） |
| Word | Microsoft Word 2016+（用于打开 .docx 验证格式） |
| 源文件 | `net_abstraction.h`、`protocol.h`、ESP32-C2 骨架代码可访问 |

## 4. 验收项列表

### A1. 编译/生成验证

- **目的**：确保所有 .docx 可由 .md + 脚本成功生成
- **前置条件**：Python 依赖已安装
- **操作步骤**：
  1. 运行 `scripts/draw_flowcharts_v2.py` 生成6张流程图
  2. 依次运行 `scripts/md_to_docx_v2.py` 转换4份 .md 为 .docx
- **期望结果**：脚本无报错，4份 .docx 文件生成到 `Document/移植说明/`
- **通过标准**：所有脚本返回零退出码，输出文件存在且文件大小 > 0
- **失败标准**：任一脚本报错或输出文件为空
- **证据要求**：脚本控制台输出日志

### A2. ESP32移植指南验收

- **目的**：验证移植指南的完整性和格式
- **前置条件**：A1 通过
- **操作步骤**：
  1. 打开 `ESP32移植指南.docx`
  2. 检查6个章节是否齐全（前置准备、骨架集成、接口实现、ESP-IDF集成、编译烧录、功能验证）
  3. 检查所有任务项是否使用 checkbox 格式（□）
  4. 检查是否**不含任何代码片段**
  5. 统计任务总数（预期 30~45 条，覆盖29个接口+环境+编译+烧录+验证）
- **期望结果**：章节完整、task list 格式统一、零代码
- **通过标准**：≥6 章节、≥30 条 checkbox、无代码块
- **失败标准**：缺少章节、任务数 < 25、存在代码片段
- **证据要求**：截图展示文档结构、随机抽查3页内容截图

### A3. ESP32移植方案验收

- **目的**：验证移植方案的接口覆盖度和契约完整性
- **前置条件**：A1 通过
- **操作步骤**：
  1. 打开 `ESP32移植方案.docx`
  2. 对比 `net_abstraction.h`，确认29个接口全部有说明
  3. 检查每个接口是否标注了：功能摘要、ESP-IDF API 映射、约定值
  4. 检查是否**不含完整的 C 代码实现**
  5. 检查第9章"关键约定值速查表"是否包含所有来自 `protocol.h` 的常量
  6. 检查第10章"常见陷阱"是否覆盖：STA异步、单核事件循环、mDNS点号规则、NVS命名空间、内存限制
- **期望结果**：29个接口全覆盖，约定值完整，零完整代码
- **通过标准**：29/29 接口有说明、≥15 个常量在速查表中、≥5 条常见陷阱
- **失败标准**：缺少任一接口说明、存在完整函数体代码、约定值表缺失
- **证据要求**：接口覆盖统计截图、速查表截图、抽查3个接口说明截图

### A4. 配网流程说明验收

- **目的**：验证配网文档的流程完整性和可读性
- **前置条件**：A1 通过，流程图已生成
- **操作步骤**：
  1. 打开 `配网流程说明.docx`
  2. 检查是否有6张流程图（Fig01~Fig06）正确嵌入
  3. 检查每张流程图：无重叠节点、无线条穿透节点、无悬垂线段、标签清晰
  4. 检查是否零代码
  5. 检查设备侧5个阶段是否完整（启动→配网→发现→连接→自愈）
  6. 检查上位机侧2个流程是否完整（配网流程、连接保障）
  7. 检查协议参数速查表是否包含全部14条协议命令
- **期望结果**：流程图布局清晰，流程覆盖完整，零代码
- **通过标准**：6张流程图全部嵌入、无布局缺陷、5个设备阶段+2个上位机流程、协议表完整
- **失败标准**：流程图缺失、存在节点重叠/穿透/悬垂、阶段不完整、存在代码
- **证据要求**：每张流程图截图（共6张）、协议速查表截图

### A5. 验收说明验收

- **目的**：验证验收说明自身结构完整和可执行
- **前置条件**：A1 通过
- **操作步骤**：
  1. 打开 `验收说明.docx`
  2. 检查是否包含：环境要求、编译验收、接口验收、流程验收、异常验收、文档自检验收
  3. 检查每个验收项是否有明确的通过/失败标准
  4. 检查是否有可执行的测试步骤
- **期望结果**：6个主要验收区域，每个区域有明确的通过标准
- **通过标准**：≥6 个验收区域、每个区域 ≥2 条可执行验收项
- **失败标准**：验收项无通过标准、步骤不可执行
- **证据要求**：文档结构截图

### A6. 硬件抽象层审计验证

- **目的**：确认审计结论准确（抽象层设计清晰完整）
- **前置条件**：无需
- **操作步骤**：
  1. 打开 `net_abstraction.h` 逐项检查 29 个函数指针的定义
  2. 打开 `src/core/device_app.c` 确认无平台特定 include/API
  3. 打开 `backends/sim/`、`backends/linux/`、`backends/esp32c2/` 确认各有独立实现
  4. 打开 `src/common/net_abstraction.c` 确认 `net_ctx_create` 的安全封装
- **期望结果**：29接口定义完整、core 层零平台依赖、3个后端独立、封装层 NULL 安全
- **通过标准**：以上4条全部满足
- **失败标准**：任一条不满足
- **证据要求**：代码引用（文件路径:行号）截图

### A7. 文档一致性验证

- **目的**：确保4份文档之间的数据一致
- **前置条件**：A1~A5 通过
- **操作步骤**：
  1. 对比指南中的任务数是否与方案中的接口数一致
  2. 对比方案中的约定值与配网文档中的协议参数是否一致
  3. 检查所有文档中的端口号（5935/5936）、组播地址（224.0.2.1）、SSID 格式（Modu_XXXX）是否一致
- **期望结果**：所有跨文档引用一致
- **通过标准**：端口/地址/命名规则在4份文档中无矛盾
- **失败标准**：存在跨文档数据矛盾
- **证据要求**：抽查3个跨文档共有的参数对比截图

## 5. 证据要求

- 每项验收：截图说明或文件路径 + 行号引用
- 验收报告汇总：列出所有通过/失败/阻塞项及证据摘要
- 流程图验收：每张图单独截图

## 6. 失败与阻塞处理

- 验收失败 → 定位到具体 .md 源文件进行修正，重新转换 .docx 后复验
- 流程图布局问题 → 调整 `draw_flowcharts_v2.py` 参数重新生成
- 接口覆盖不足 → 补充对应移植方案章节
- 文档一致性矛盾 → 修正源文件并重新转换

## 7. 回归范围

- **全量回归**：无（本版本仅产出文档，不修改任何代码）
- **冒烟回归**：验证 `流程说明.md`（仓库根目录）未被修改
