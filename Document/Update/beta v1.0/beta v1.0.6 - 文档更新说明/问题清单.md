  ```
  Document/移植说明/
  ├── ESP32移植指南.md        # 纯任务清单，可打勾
  ├── ESP32移植方案.md        # 逐条细化，含接口契约与约定
  ```

#### Q2. "PING码"的含义确认

- **问题描述**：需求第4条提到"比如wifi的名称，以及PING码，端口等等"。这里"PING码"很可能是"**PIN码**"的笔误（配网流程中设备 SoftAP 生成的一次性4位数字 PIN 认证码）。但如果用户确实指的是其他含义（如 heartbeat ping 的序列号约定），则文档覆盖范围会不同。
- **建议方案**：按"PIN码"理解——即配网阶段设备生成的4位数字一次性PIN认证码（随机生成，认证成功后作废），与"wifi的名称"（SSID 命名规则 `Modu_XXXX`）和"端口"（默认 5935）一并作为移植方案中的接口契约约定。
- **备选方案**：如果确实是"PING码"（心跳 ping 协议中的 seq 序号约定），则在移植方案中补充心跳协议的序号规则。
- **风险预警**：无。
- **置信度**：90%
- **归入置顶原因**：措辞歧义可能影响移植方案中接口契约的覆盖范围，需澄清。

#### Q3. 移植指南的目标芯片范围

- **问题描述**：需求只说"ESP32移植指南"，未明确芯片型号。当前代码骨架 `backends/esp32c2/` 以 **ESP32-C2**（ESP8684, RISC-V 单核 120MHz）为主目标，接口注释中同时标注了 ESP32-C3 兼容性。旧版归档文档 `archived/ESP32-C3配网与TCP连接流程_旧版归档.docx` 则是基于 ESP32-C3。移植指南应覆盖哪些芯片？
- **建议方案**：主目标 **ESP32-C2**，正文中注明 ESP32-C3 兼容（二者 ESP-IDF WiFi/lwIP API 兼容，差异仅在于 C3 为 Xtensa LX7 双核、有 FPU，C2 为 RISC-V 单核、无 FPU）。移植指南中的步骤对两芯片通用，仅在注意事项中标注差异。
- **备选方案**：仅覆盖 ESP32-C2（当前代码骨架唯一目标），ESP32-C3 留给后续版本。
- **风险预警**：无。
- **置信度**：85%
- **归入置顶原因**：影响文档标题、范围和嵌入式开发者的目标认知，需确认。

#### Q4. 流程图处理方式

- **问题描述**：配网流程文档需要"带流程图"。当前代码库中 `figures/` 目录已有 6 张流程图 PNG（由 `scripts/draw_flowcharts.py` 通过 graphviz 生成），内容与 `流程说明.md` 完全对齐。同时仓库中有一套 graphviz 绘制脚本。配网流程文档中的流程图应如何处理？
- **建议方案**：直接引用 `figures/` 中已有的 6 张 PNG（已覆盖配网全流程：上位机配网 Fig001A、上位机连接保障 Fig001B、设备启动自检 Fig002A、设备配网 Fig002B、设备服务发现 Fig002C、设备连接与自愈 Fig002D），配网流程文档只需引用图片路径 + 图片说明，不重新生成。如需更新流程图内容，可运行 `scripts/draw_flowcharts.py`。
- **备选方案**：重新运行 `scripts/draw_flowcharts.py` 生成新的流程图（如果图片有过期风险），或使用 Mermaid 文本图表替代 PNG（可嵌入 Markdown 但渲染依赖查看器）。
- **风险预警**：PNG 图片如果在移植说明目录中路径需要调整（`../figures/` → 相对路径），需确认。
- **置信度**：80%
- **归入置顶原因**：影响配网流程文档的技术方案与引用路径设计。

#### Q5. 硬件抽象层审计结论

- **问题描述**：需求要求"检查在 device 设备端程序下，应该在硬件层之上有一层足够清晰的抽象层"。该检查应在何时、以何种形式输出？
- **自决方案**：审计作为移植方案文档的开篇章节（第1章），直接给出审计结论。经代码审查确认：
  - `net_backend_t` vtable（`net_abstraction.h:21-59`）定义了 29 个函数指针，覆盖生命周期/WiFi/TCP/UDP/mDNS/NVS/系统 7 个类别
  - `net_ctx_t` 封装层提供 NULL 安全转发
  - 设备状态机 `src/core/device_app.c` 零平台依赖，全程通过 `net_ctx_t` 调用
  - 当前存在 3 个后端实现：sim（完整）、linux（完整）、esp32c2（骨架占位）
  - **结论**：抽象层设计清晰、接口完整，可支撑 ESP32 移植。
- **自决理由**：代码审查已完成，结论明确，无需用户决策。
- **置信度**：98%

#### Q6. 移植指南的 TODO 格式

- **问题描述**：需求要求移植指南"只需要说明任务，以及 todo list，让嵌入式在迁移的流程中可以有一个非常明确清晰的方向，可以一条条打勾过点"。TODO 列表应采用什么格式？
- **自决方案**：使用 Markdown checkbox 格式（`- [ ] 任务描述`），按 ESP-IDF 初始化 → WiFi → TCP/UDP → mDNS → NVS → 系统 → 集成测试 的依赖顺序排列，共约 30-40 条可打勾任务。每条任务不包含代码，只说明"做什么"和"参考哪个 ESP-IDF API"。
- **自决理由**：Markdown checkbox 是标准的可打勾清单格式，与现有代码骨架注释中的 ESP-IDF API 映射可直接对应。
- **置信度**：95%

#### Q7. 移植方案的粒度控制

- **问题描述**：需求要求移植方案"细化到每一点需要做哪些工作，但尽量不要写非常具体的代码，你只需要告诉开发你需要做什么事，比如抽象层中的哪个接口，你需要做哪些事情，里面有哪些细节是约定出来的"。如何平衡"不说具体代码"与"说清接口契约"？
- **自决方案**：
  - 每个接口给出：函数签名（从 `net_abstraction.h` 复制）、语义说明、ESP-IDF API 映射列表、约定细节（如 SSID 规则 `Modu_XXXX`、PIN 随机4位数字、端口 5935、组播地址 224.0.2.1:5936、NVS namespace `"provision"`、NVS 键名 `wifi_creds`/`host_candidates`/`evlog`、reason code 对齐表 etc.）
  - **不提供**完整的 C 代码实现，但提供数据结构和错误码定义
  - 所有约定值从 `protocol.h`、`device_sim.json`、`device_linux.json` 中提取
- **自决理由**：这种粒度与需求说明中的举例一致（"比如wifi的名称，以及PIN码，端口等等"），嵌入式开发者拿到后可直接对照 ESP-IDF API 编码。
- **置信度**：92%

#### Q9. 验收说明的验收对象

- **问题描述**：验收说明应该验收什么？是验收文档本身的质量（完整性、准确性），还是验收移植工作的完成情况？
- **自决方案**：验收说明既验文档也验工作：
  - **文档自检项**：移植指南 checklist 完整性、移植方案接口覆盖度（29个接口是否全有说明）、参数/约定值是否全部提取到位
