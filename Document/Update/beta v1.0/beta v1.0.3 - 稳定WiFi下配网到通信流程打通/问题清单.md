# 问题清单 - beta v1.0.3 / 阶段一

## v1（范围简化，2026-08-05）

### 场景约束

- 只验证一个稳定、可用的 2.4GHz WiFi。
- 当前使用 Linux 验证流程。
- 设备端后续迁移到 ESP32-C3。
- 本版本只打通配网、UDP 发现、TCP 会话主流程。
- PC 端和设备端分别开发、分别记录验收结果。

### 置顶区（待用户确认）

无。当前简化范围没有重大路线分歧。

### 自决区

#### Q1. `close_ap` 丢失时设备是否应自动继续

- 问题描述：当前真实日志中设备已连接目标 WiFi，但没有收到 close_ap，因此没有启动 UDP。
- 自决方案：设备在 wifi_result ok 后等待一个短宽限期；未收到 close_ap 时主动关闭 AP 并进入 discovery。
- 自决理由：避免依赖旧热点 TCP 的最后一条单向消息，逻辑也适合迁移到 ESP32-C3。
- 风险预警：只有 wifi_config 成功且 STA 校验通过时才能自动继续。
- 置信度：98%。

#### Q2. PC 是否需要复杂的 close_ap 确认和重传协议

- 问题描述：增加确认协议会扩大改动和测试范围。
- 自决方案：不增加新协议；PC 检查一次发送结果，失败时记录并继续切回目标 WiFi，设备负责自动交接。
- 自决理由：在稳定 WiFi 验证场景下足够，且不会增加 ESP32-C3 迁移复杂度。
- 风险预警：PC 日志必须区分发送成功和失败。
- 置信度：96%。

#### Q3. 哪个事件代表完整配网成功

- 问题描述：wifi_result ok 只证明设备连接目标 WiFi，不证明 UDP/TCP 已打通。
- 自决方案：wifi_result ok 记录为“WiFi 配置已接受”；device_hello/host_ack 完成后记录为“配网并建立业务会话成功”。
- 自决理由：与实际阶段边界一致，避免过早宣告成功。
- 风险预警：PC UI 和日志文案需要同步。
- 置信度：100%。

#### Q4. 是否同时修复退避、短断、多网卡和真实 mDNS

- 问题描述：这些问题存在，但不是当前稳定 WiFi 主流程的直接阻断。
- 自决方案：全部移出 beta v1.0.3，后续按真实 ESP32-C3 需求另立版本。
- 自决理由：控制开发范围，优先证明核心协议和状态流可以完整运行。
- 风险预警：本版本不能宣称覆盖复杂网络和异常恢复。
- 置信度：100%。
