# beta v1.0.3 流程差异总览

- 版本名称：稳定 WiFi 下配网到通信流程打通
- 文档日期：2026-08-05
- 当前阶段：阶段一，现状确认
- 验证平台：Linux
- 目标设备平台：ESP32-C3

## 1. 版本目标

本版本只验证一个稳定、单一的 WiFi 环境，不处理弱信号、多路由器、多网卡、频繁断线等复杂场景。

需要打通的唯一主流程为：

```text
PC 连接设备热点
  -> auth
  -> wifi_config
  -> 设备连接目标 WiFi
  -> wifi_result ok
  -> 设备关闭配网热点
  -> PC 切回目标 WiFi
  -> 设备启动 UDP 服务发现
  -> 设备收到 PC 的 host_announce
  -> 设备连接 PC 的 TCP 服务
  -> device_hello / host_ack
  -> ping / pong
```

Linux 只用于当前流程验证。设备端状态机和协议逻辑应保持平台无关，后续可迁移到 ESP32-C3；Linux 专属的 NetworkManager、热点和网卡操作继续放在网络后端，不进入设备状态机核心代码。

## 3. 和计划流程相比还差什么

### 必须修复

| 编号 | 所属端 | 差距 | 结果 |
|---|---|---|---|
| D1 | 设备端 | `wifi_result ok` 后仍强制等待 `close_ap` | `close_ap` 未到达时永远不能进入 UDP 发现 |
| D2 | 设备端 | 成功后仍执行“等待 wifi_config”超时 | 日志错误，配网 TCP 被关闭但状态不前进 |
| D3 | 设备端 | UDP discovery 启动缺少明确日志 | 无法快速判断是否已进入下一阶段 |
| P1 | PC 端 | `close_ap` 发送结果未检查 | 日志可能显示已发送，但设备实际未收到 |
| P2 | PC 端 | 配网结束和切回目标 WiFi 的日志证据不足 | 无法确认 PC 是否已经回到设备所在网络 |
| E1 | 双端 | 缺少一次真实完整流程证据 | 当前只能证明“目标 WiFi 已连接”，不能证明通信已建立 |

### 本版本不处理

- WiFi 弱信号和频繁掉线恢复。
- 多 WiFi 凭据切换。
- 多网卡和复杂路由选择。
- 真实 mDNS；本版本以 UDP 组播为发现主路径。
- BLE/Blufi 配网。
- TLS、OTA、IPv6。
- 每设备唯一热点密码和随机 PIN。
- 完整业务数据协议。
- 对原计划中所有长期能力做一次性补齐。

这些能力可以保留在长期规划中，但不应阻塞当前稳定 WiFi 环境下的主流程验证。

## 4. 简化后的交接规则

### 4.1 设备端规则

1. `wifi_config` 成功后，设备确认目标 SSID 和 IP。
2. 设备保存未确认凭据并发送 `wifi_result ok`。
3. `close_ap` 仍保留，但不再作为进入下一阶段的唯一条件。
4. 收到 `close_ap` 时立即关闭热点并进入 discovery。
5. 如果没有收到 `close_ap`，设备在一个短宽限期后也主动关闭热点并进入 discovery。
6. 只有 `wifi_config` 已成功时才能自动进入 discovery；失败或未配置时不能自动前进。

这个规则适合后续 ESP32-C3：设备成功拿到目标 WiFi 后能够自主完成状态迁移，不依赖 PC 在旧热点 TCP 上再发送一条必须到达的命令。

### 4.2 PC 端规则

1. 收到 `wifi_result ok` 后发送 `close_ap`。
2. 检查并记录发送结果，不再无条件打印“已发送成功”。
3. 无论 `close_ap` 是否成功送达，PC 都结束配网连接并切回目标 WiFi。
4. PC 切回目标 WiFi 后继续提供 UDP `host_announce` 和 TCP 5935 服务。
5. 设备最终应通过 UDP 找到 PC，再建立业务 TCP，而不是继续依赖配网 TCP。

## 5. PC 端与设备端边界

### 设备端负责

- 连接并验证目标 WiFi。
- 回复 `wifi_result`。
- 自主结束配网阶段。
- 关闭 SoftAP，保持 STA。
- 启动 UDP 发现。
- 根据 `host_announce` 连接 PC TCP 服务。
- 完成 hello/ack 和心跳。

详细差距见 `设备端流程差异.md`。

### PC 端负责

- 连接设备热点并发送 auth、wifi_config。
- 接收并判断 `wifi_result`。
- 最佳努力发送 `close_ap`，准确记录结果。
- 断开设备热点并切回目标 WiFi。
- 在目标 WiFi 上发送 UDP `host_announce`。
- 接受设备 TCP 连接并回复 `host_ack`、`pong`。

详细差距见 `PC端流程差异.md`。

## 6. 最小验收标准

### 设备端日志

必须按顺序出现：

```text
RX wifi_config
WiFi STA 已连接到 <目标SSID>
TX wifi_result status=ok
设备热点已停止
状态切换 -> discovery
UDP 组播监听已启动
收到 host_announce
状态切换 -> connect
TX device_hello
RX host_ack
ping / pong
```

### PC 端日志

必须按顺序出现：

```text
已发送 wifi_config
收到 wifi_result ok
close_ap 发送成功或发送失败的真实结果
已切回目标 WiFi
正在发送 host_announce
收到 device_hello
已发送 host_ack
收到 ping 并发送 pong
```

### 通过条件

- 在稳定目标 WiFi 环境中连续完成一次完整主流程。
- 即使设备未收到 `close_ap`，也能自动进入 discovery。
- PC 和设备最终位于同一目标 WiFi。
- UDP 发现成功。
- TCP hello/ack 成功。
- 至少完成 3 轮 ping/pong。

## 7. 版本规模判断

这是一个小规模流程修复，不需要同时重构完整网络框架。预计修改范围集中在：

- 设备端配网交接状态与日志。
- PC 端 `close_ap` 发送结果处理与日志。
- 对应的模拟测试和一次真实启动验证。

本版本完成后，再根据真实 ESP32-C3 迁移结果决定是否继续实现长期增强能力。
