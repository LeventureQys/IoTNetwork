# beta v1.0.3 验收文档

## 1. 验收范围

### 覆盖

- 设备端配网成功后的自动交接。
- PC 端 close_ap 发送结果处理。
- UDP 组播发现。
- 真实 TCP 注册会话。
- 至少三轮 ping/pong。
- Linux 设备逻辑对 ESP32-C3 的平台隔离。

### 不覆盖

- 弱信号、频繁断线、多凭据 fallback。
- 多网卡和复杂路由。
- 真实 mDNS。
- BLE、TLS、OTA、IPv6。
- ESP32-C3 实机编译和运行。

## 2. 验收环境

### 自动化环境

- Linux 当前工作区。
- CMake 测试构建。
- 模拟网络后端。

### 真实环境

- Linux 设备验证机。
- PC 上位机。
- 一个稳定的 2.4GHz WiFi。
- PC 和设备最终位于同一局域网。
- 网络允许 UDP `224.0.2.1:5936` 和 TCP 5935。

真实测试会切换 WiFi，执行前必须确认不会中断关键远程连接。

## 4. 设备端验收

### D-A1. 新参数

- 目的：确认交接宽限期可配置。
- 操作：运行参数默认值和 JSON 加载测试。
- 期望：默认 1000ms；配置可覆盖；0 不产生负数或溢出行为。
- 通过标准：相关参数测试全部通过。
- 失败标准：字段未加载、默认值错误或负值导致异常等待。
- 证据：测试输出和修改文件路径。

### D-A2. 正常 close_ap 路径

- 目的：保证现有协议兼容。
- 操作：执行完整 auth、wifi_config、wifi_result、close_ap 测试。
- 期望：设备立即停止 AP并进入 discovery。
- 通过标准：既有 `Provision.FullFlowAuthConfigClose` 通过。
- 失败标准：设备等待完整宽限期、退回 AP 或测试超时。
- 证据：测试输出。

### D-A3. close_ap 丢失自动交接

- 目的：验证本版本核心修复。
- 操作：完成 wifi_result ok 后不发送 close_ap。
- 期望：宽限期到期后设备主动停止 AP并进入 discovery。
- 通过标准：设备在限定时间内进入 `DEV_STATE_DISCOVERY`。
- 失败标准：仍停留在 `DEV_STATE_AP_PROVISION` 或打印 wifi_config 超时。
- 证据：新增测试输出和关键日志。

### D-A4. 未成功配置不得自动前进

- 目的：防止自动交接绕过配网成功条件。
- 操作：发送无效 wifi_config 或仅完成 auth，等待超过宽限期。
- 期望：设备不进入 discovery。
- 通过标准：状态保持配网或按现有失败策略处理。
- 失败标准：错误进入 discovery。
- 证据：测试输出。

### D-A5. UDP 启动日志

- 目的：提高真实联调可观测性。
- 操作：让设备进入 discovery。
- 期望：日志打印组播地址和端口。
- 通过标准：出现“UDP 组播监听已启动”。
- 失败标准：组播成功但无日志，或日志参数错误。
- 证据：设备日志文件。

### D-A6. ESP32-C3 可迁移性静态检查

- 目的：防止状态机引入 Linux 耦合。
- 操作：检查本版本对 `demo/device/` 的改动。
- 期望：只调用 `net_abstraction` 和公共 C API。
- 通过标准：新增代码不包含 `nmcli`、NetworkManager、Linux 网卡名或 Linux 专属 socket 调用。
- 失败标准：平台实现进入设备核心状态机。
- 证据：代码 diff。

## 5. PC 端验收

### P-A1. close_ap 正常发送

- 目的：验证成功日志准确。
- 操作：执行正常模拟配网。
- 期望：完整写入后打印成功日志。
- 通过标准：日志为“close_ap 已完整写入配网连接”。
- 失败标准：不检查返回值或继续使用无条件“已发送”。
- 证据：测试输出或日志。

### P-A2. close_ap 发送失败

- 目的：验证失败不阻塞切网。
- 操作：通过模拟注入或可控 socket 令 close_ap send 失败。
- 期望：记录返回码，关闭配网连接并继续切回目标 WiFi。
- 通过标准：无死循环、无无限重试，WiFi 配置结果不被错误改为失败。
- 失败标准：PC 卡在设备热点、虚报成功或整个流程异常退出。
- 证据：测试输出和日志。

### P-A3. 阶段日志语义

- 目的：区分 WiFi 配置和业务会话。
- 操作：观察配网和设备上线日志。
- 期望：wifi_result ok 后记录“等待设备回连”；device_hello/host_ack 后才记录业务会话建立。
- 通过标准：两类日志清晰分离。
- 失败标准：wifi_result ok 后立即宣称业务会话成功。
- 证据：PC 日志。

### P-A4. 切回目标 WiFi

- 目的：确认 PC 回到设备所在网络。
- 操作：真实配网后观察切网结果。
- 期望：日志记录目标 SSID和成功结果；失败时有原因码及手动提示。
- 通过标准：PC 实际连接目标 SSID，或明确标记人工阻塞。
- 失败标准：无结果日志、实际 SSID 不符仍报成功。
- 证据：PC 日志和系统 WiFi 状态。

## 6. 双端集成验收

### E-A1. 模拟完整回归

- 目的：保证正常流程不回归。
- 操作：运行 `HostE2E.ProvisionRegisterHeartbeat` 和配网相关测试。
- 期望：设备上线并保持至少两个心跳周期。
- 通过标准：相关测试通过。
- 失败标准：配网、发现、注册或心跳任一失败。
- 证据：测试命令和输出。

### E-A2. 真实稳定 WiFi 主流程

- 目的：验证本版本最终目标。
- 前置：PC 上位机 TCP listener 与 UDP announcer 已启动；目标 WiFi 稳定可用。
- 操作：清除设备未确认配置，执行一次真实配网。
- 期望顺序：
  1. 设备收到 wifi_config。
  2. 设备连接目标 WiFi并发送 wifi_result ok。
  3. 设备停止 AP并进入 discovery。
  4. PC 切回目标 WiFi并发送 host_announce。
  5. 设备收到 announce 并连接 PC TCP 5935。
  6. hello/ack 成功。
  7. 至少三轮 ping/pong。
- 通过标准：全部步骤连续完成，无需手动重启设备。
- 失败标准：停留在 AP_PROVISION、未启动 UDP、未建立 TCP 或心跳中断。
- 证据：同一轮设备日志、PC 日志和目标 SSID 状态。

### E-A3. 真实 close_ap 丢失容错

- 目的：确认核心故障不再出现。
- 操作：如果 PC 端可注入则阻止 close_ap；否则以设备自动交接测试作为自动化证据，真实流程只观察是否能稳定迁移。
- 期望：设备在宽限期后进入 discovery。
- 通过标准：无 `RX close_ap` 时仍出现 AP 停止和 discovery。
- 失败标准：再次出现“wifi_result ok 后等待 wifi_config 超时”。
- 证据：设备连续日志。

## 8. 验收结论规则

- 所有设备端 D-A 项通过，设备端可判通过。
- 所有 PC 端 P-A 项通过或 Windows/真实环境项明确阻塞，PC 端才可提交用户检查。
- E-A2 未执行或失败时，版本不能判定完整完成。
- ESP32-C3 实机不在本版本验收范围，不能因未执行判失败，也不能宣称已在 ESP32-C3 通过。
