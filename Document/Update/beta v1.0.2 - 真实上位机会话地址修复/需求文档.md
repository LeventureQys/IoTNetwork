# beta v1.0.2 真实上位机会话地址修复需求文档

## 1. 文档目的

本文档定义设备完成真实 WiFi 配网后，发现并连接局域网真实上位机的修复需求。文档面向后续开发 Agent、测试人员和 Windows 上位机验收人员；阅读者不需要依赖本次对话即可理解问题、修改范围、行为契约和验收标准。

## 2. 版本信息

- 版本号：`beta v1.0.2`。
- 版本名称：真实上位机会话地址修复。
- 版本类型：小规模缺陷修复版本。
- 前置版本：`beta v1.0.1 - Linux设备热点DHCP可靠性修复`。
- 当前阶段：阶段二设计；设备端与PC端计划分开编制，尚未进入代码修改。
- 主要平台：Linux 设备端、Windows 10/11 上位机。

## 3. 问题背景

Linux 设备最近一次通过 `demo/start_device.sh` 启动。设备持久化事件日志 `demo/run/dev0.nvs.json` 解码后得到以下关键时间线：

1. 设备上电并启动配网热点。
2. 设备成功接收 WiFi 配置并连接 `CMCC-KnW5`。
3. 设备进入服务发现阶段。
4. 设备发现上位机 `192.168.1.191:5935`。
5. 设备立即记录“连接上位机失败，进入自愈阶段”。
6. 后续 WiFi 曾短暂断开，状态机返回 STA 重连并成功恢复。

这表明配网流程和服务发现流程已经运行到真实上位机会话建立之前，主故障发生在 TCP 建连阶段，而不是热点启动、DHCP、WiFi 密码下发或上位机发现阶段。

## 4. 已确认根因

### 4.1 设备实际连接地址与发现地址不一致

服务发现层已正确把 `192.168.1.191:5935` 写入 `app->sess_host`：

- `demo/device/device_discovery.c` 解析 `host_announce.ip` 和 `host_announce.tcp_port`。
- `demo/device/device_app.c` 在发现成功后记录远端 IP/端口并进入 `DEV_STATE_CONNECT`。
- `demo/device/device_session.c` 把 `app->sess_host` 传给 `net_tcp_connect()`。

但设备当前复用了 `demo/net_sim/sim_backend.cpp` 的 socket 实现。其 `TcpConnect()` 虽然读取了 `addr->ip`，最终仍无条件执行：

```cpp
dst.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
```

因此日志显示目标是 `192.168.1.191:5935`，实际系统调用连接的却是 `127.0.0.1:5935`。本机没有该端口监听时，设备必然进入连接失败和自愈流程。

### 4.2 模拟地址翻译和真实网络连接混用了同一路径

当前 `TcpConnect()` 同时承担两种不同语义：

- 模拟模式：把模拟逻辑地址翻译为 `127.0.0.1` 和本机测试端口。
- Linux 真实设备模式：应直接连接服务发现返回的局域网 IPv4 和端口。

代码只完成了模拟翻译，没有在真实设备模式下保留真实目的地址，导致模拟行为泄漏到真实网络路径。

### 4.3 上位机仍需满足真实监听和通告一致性

即使设备端使用正确远端地址，上位机也必须满足以下条件：

- TCP 服务监听 `0.0.0.0:5935` 或发现通告 IP 对应的局域网接口地址，而不是只监听 `127.0.0.1`。
- `host_announce.ip`、mDNS 地址、上位机日志中的地址和操作系统实际可达地址一致。
- 上位机防火墙允许设备所在局域网访问 TCP 5935。
- 上位机启动失败时不得继续发送可用的服务通告。

现有上位机 `HostTcpServer` 通过网络后端调用 `net_tcp_listen()`，Windows 后端的最终绑定行为需要在开发阶段核对并按本需求修正。用户已明确允许修改上位机代码。

## 5. 修复目标

### 5.1 总目标

设备在真实 Linux WiFi 模式下，必须对服务发现得到的真实上位机 IPv4 和 TCP 端口发起连接；上位机必须在其通告地址对应的局域网接口上提供可达的 TCP 服务。模拟模式继续使用回环地址翻译，且现有模拟配网和会话测试不得回归。

### 5.2 可观察目标

修复后应能观察到：

1. 设备日志记录发现上位机地址，例如 `192.168.1.191:5935`。
2. 设备网络后端日志记录真实 TCP 连接目标，必须与发现地址完全一致。
3. 抓包或系统连接表显示设备源地址连接上位机真实地址，而不是连接 `127.0.0.1`。
4. 上位机接受连接并收到 `device_hello`。
5. 上位机返回 `host_ack status=ok`。
6. 设备记录“会话已建立”，并将新 WiFi 凭据确认为最近一次有效配置。
7. 后续 ping/pong 心跳保持正常。

## 6. 功能需求

### FR-01 真实设备 TCP 连接必须使用调用方目标地址

- 适用条件：Linux、设备实例、`use_real_wifi_sta=1`。
- 输入：`net_tcp_connect()` 的 `net_addr_t`，其中 `ip` 和 `port` 均为网络字节序。
- 行为：socket 目的地址必须直接使用 `addr->ip` 和 `addr->port`。
- 禁止：不得把真实目标替换成 `INADDR_LOOPBACK`，不得使用 `params.host_virtual_ip` 覆盖发现地址。
- 错误处理：socket 创建、立即连接失败、超时和 `SO_ERROR` 均按现有 `DEMO_ERR*` 契约返回，并关闭本次创建的 socket。

### FR-02 模拟地址翻译必须保持兼容

- 模拟设备 AP 逻辑地址继续映射到 `127.0.0.1:<device_ap_real_port>`。
- 模拟上位机逻辑地址继续映射到 `127.0.0.1:<host_tcp_port>`。
- 模拟环境中的其他地址不得被静默当作本机服务；无明确翻译规则时应保持既有测试契约或显式失败。
- 不改变 `PROTO_SIM_AP_IP` 和 `SimWorld::HostVirtualIp()` 的数值。

### FR-03 地址模式判定必须显式且唯一

`TcpConnect()` 必须先判定当前运行模式，再决定地址处理：

```text
Linux 真实设备模式
  -> 目的 IP = addr->ip
  -> 目的端口 = addr->port

模拟模式
  -> 已知模拟 AP 地址：翻译到 loopback + AP 实际端口
  -> 已知模拟 Host 地址：翻译到 loopback + host_tcp_port
  -> 其余地址按模拟后端既定契约处理
```

模式判定必须复用当前后端已有条件 `dev_index() >= 0 && params_.use_real_wifi_sta`，不得通过目标地址是否属于 `192.168.1.0/24` 猜测运行模式。

### FR-04 TCP 连接诊断日志必须打印请求目标和实际目标

连接开始时应记录：

- 运行模式：真实或模拟。
- 请求目标：调用方传入的 IPv4 和端口。
- 实际目标：socket 最终使用的 IPv4 和端口。

连接失败时应记录：

- 请求目标和实际目标。
- 失败阶段：立即失败、等待超时或 `SO_ERROR`。
- 系统错误码。

日志不得包含 WiFi 密码、PIN、会话敏感数据或其他凭据。

### FR-05 设备事件日志应保留稳定的用户级错误信息

- 继续保留“连接上位机失败，进入自愈阶段”。
- 详细系统错误只写常规诊断日志，不要求写入容量有限的 NVS 事件日志。
- 设备状态机继续进入 `DEV_STATE_HEAL`，不得因单次连接失败崩溃或退出。
- 本版本不改变连接退避、重发现和 WiFi 自愈策略。

### FR-06 上位机 TCP 服务必须对通告地址可达

- Windows 真实上位机启动 TCP 服务时，监听地址必须是 `0.0.0.0:<host_tcp_port>`，或明确绑定到 `params.host_virtual_ip:<host_tcp_port>`。
- 推荐使用 `0.0.0.0` 监听，以容忍 DHCP 地址刷新和多网卡环境；服务发现仍只通告选定的局域网 IPv4。
- 禁止真实模式只监听 `127.0.0.1`。
- 模拟模式继续只监听 loopback，避免模拟测试暴露到局域网。
- 若 bind/listen 失败，`HostApp::Start()` 必须失败，上位机不得进入正常运行状态或发送服务通告。

### FR-07 上位机通告地址必须与真实可达地址一致

- Windows 真实模式启动时，通过 `win_backend_get_ipv4()` 得到当前局域网 IPv4。
- `params.host_virtual_ip`、mDNS TXT、`host_announce.ip` 和启动日志必须使用同一地址。
- 不得在真实模式通告 `127.0.0.1`、`0.0.0.0`、APIPA `169.254.0.0/16` 或无效地址。
- 若无法获得有效局域网 IPv4，上位机必须启动失败，不得退回模拟地址。
- 多网卡选择算法若现有实现已能稳定选择当前目标 WiFi 接口，则保持；若不能，应在代码设计阶段补充明确的接口优先规则，不在本需求中引入用户手选网卡 UI。

### FR-08 上位机应提供监听与通告一致性日志

上位机启动成功后至少记录：

- TCP 实际监听地址和端口。
- 服务发现通告地址和端口。
- 当前运行模式：Windows 真实或模拟。

若实际监听不覆盖通告地址，应视为启动错误，而不是仅打印警告继续运行。

### FR-09 服务发现到会话建立的地址不得被二次覆盖

- `device_discovery.c` 生成的 `app->sess_host` 是本轮连接的唯一目标来源。
- `device_app.c`、`device_session.c` 和网络抽象层不得把该地址替换成默认 host 地址。
- 候选列表持久化和自愈重连继续使用同一个真实地址和端口。
- mDNS、组播通告和候选列表三种发现来源必须遵循同一连接契约。

### FR-10 启动脚本应保存设备诊断日志

为避免后续只能依赖 Base64 NVS 事件摘要，`demo/start_device.sh` 应支持设备诊断日志落盘：

- 默认目录：`demo/logs/`。
- 文件名建议：`provision_device_YYYYMMDD_HHMMSS.log`。
- 同时保留终端输出，推荐通过 `tee` 或程序日志文件接口实现。
- 构建阶段与运行阶段日志应可区分；至少必须保存设备程序 stdout/stderr。
- 日志目录不存在时自动创建。
- 日志不得改变 `sudo`、Qt platform、配置路径、设备索引和附加参数语义。

如果代码已有稳定的 `log_set_file()` 接口，优先让设备程序与上位机一样直接写日志文件；脚本只负责确保目录存在和显示文件路径。不得同时引入两套重复日志导致每条记录重复输出。

## 7. 非功能需求

### NFR-01 网络字节序正确性

- `net_addr_t.ip` 和 `net_addr_t.port` 按当前抽象层契约保持网络字节序。
- 用于日志显示时必须转换为可读主机格式，不得因二次 `htonl()` 或 `htons()` 造成地址、端口反转。

### NFR-02 安全与边界

- 不通过 shell 拼接远端 IP 或端口。
- 不新增防火墙自动修改逻辑。
- 不自动关闭未知占用 5935 的进程。
- 不记录 WiFi 密码。

### NFR-03 兼容性

- 不修改 TCP 帧格式、JSON 命令和协议版本。
- 不修改 `device_hello`、`host_ack`、ping/pong 字段。
- 不改变模拟 AP 地址和模拟 host 地址数值。
- 不改变 Linux 热点 DHCP、UDP 67 和配网 TCP 5935 的既有实现。

### NFR-04 可诊断性

- 从日志中必须能独立判断“发现了谁”“请求连接谁”“实际连接谁”“在哪个阶段失败”。
- 上位机日志必须能判断监听端点和通告端点是否一致。

### NFR-05 失败恢复

- 单次 TCP 失败不得退出设备程序。
- 继续使用当前 HEAL 退避与重新发现流程。
- 上位机监听失败属于启动失败，不得以降级方式继续通告。

## 9. 详细修改方案要求

### 9.1 设备共用后端

推荐在 `SimBackend::TcpConnect()` 中先计算两个端点：

```text
requested = addr 传入端点
effective = 最终 socket 端点
```

伪代码：

```cpp
bool real_device_mode = dev_index() >= 0 && params_.use_real_wifi_sta;
sockaddr_in destination{};
destination.sin_family = AF_INET;

if (real_device_mode) {
    destination.sin_addr.s_addr = addr->ip;
    destination.sin_port = addr->port;
} else {
    destination.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    destination.sin_port = translated_simulation_port;
}
```

要求：

- 不对真实地址执行 `htonl(addr->ip)`，因为该字段已经是网络字节序。
- 不对真实端口执行 `htons(addr->port)`，因为该字段已经是网络字节序。
- 模拟翻译生成主机序端口时，转换一次为网络字节序。
- 连接超时逻辑、非阻塞 socket 和 `SO_ERROR` 检查保持现有结构。
- 所有失败分支关闭 socket。

为了可测试性，可把“根据模式和请求地址生成 effective sockaddr”提取为无系统调用的内部 helper；helper 不应成为跨模块公共抽象。

### 9.2 上位机监听

核对 `win_backend.cpp` 的 `socket_tcp_listen()` 或等价函数：

- 真实 Windows 后端：`sin_addr.s_addr = htonl(INADDR_ANY)`，端口使用调用方传入值。
- 设置 `SO_REUSEADDR` 时应符合当前 Windows 行为，不引入允许多个服务同时成功占用同一端口的错误配置。
- bind 和 listen 任一失败均关闭 socket并返回错误。
- 日志打印 `WSAGetLastError()` 和端口。
- `HostTcpServer::Start()` 失败后，`HostApp::Start()` 不启动 announcer 和 mDNS；若当前启动顺序会先通告后监听，应调整为“TCP 监听成功 -> mDNS -> announcer”。

### 9.3 上位机地址通告

核对以下数据链：

```text
win_backend_get_ipv4()
  -> params.host_virtual_ip
  -> HostMdns TXT/address
  -> HostAnnouncer host_announce.ip
  -> 启动日志
```

所有环节必须使用同一份已校验字符串。不得由不同模块分别重新枚举网卡，以免多网卡环境中通告不同地址。

### 9.4 设备日志落盘

推荐参照 `demo/pc/app/main.cpp`：

1. 创建 `logs` 目录。
2. 生成 `logs/provision_device_<timestamp>.log`。
3. 在 `log_init()` 后调用 `log_set_file()`。
4. 启动时打印日志文件路径。
5. 正常退出前调用 `log_close_file()`。

若设备程序在创建日志前因配置路径或后端初始化失败退出，这些早期错误仍保留在 stderr；脚本可选择只对这种早期输出做外层重定向，但不得产生重复日志。设计阶段需在“程序内文件日志”和“脚本 tee”之间选定唯一主方案。

## 10. 测试需求

### 10.1 当前 Linux 环境必须执行

- 编译设备工程。
- 编译测试工程。
- 运行与 `sim_backend`、socket 地址翻译、设备状态机相关的定向测试。
- 运行现有模拟 socket 和模拟配网回归测试。
- 静态核对真实模式目的地址不再写死 loopback。
- 验证设备日志文件可以创建，且包含连接请求目标和实际目标。

### 10.2 当前 Linux 环境不要求执行

用户已明确当前 Linux 环境可能无法测试 Windows 真实上位机，因此以下项目不作为当前开发阶段完成的阻塞条件：

- 编译或启动 Windows `provision_pc.exe`。
- Windows Native WiFi 配网流程。
- Windows 防火墙实际放行测试。
- Windows 上位机真实局域网监听和服务发现。

这些项目必须在验收文档中标记为“待 Windows 环境执行”，不得伪造通过结果，也不得因未执行而回退或删除上位机修复代码。

### 10.3 Windows 环境后续必须执行

- 使用 Visual Studio 2022 和 Qt6 编译 PC 工程。
- 启动真实模式上位机，确认日志中的局域网 IP。
- 使用 `netstat`、PowerShell `Get-NetTCPConnection` 或等价工具确认当前进程监听 `0.0.0.0:5935` 或选定局域网 IP:5935。
- 确认 UDP 5936 组播通告中的 `ip`、`tcp_port` 与 TCP 监听一致。
- 从 Linux 设备所在网络连接上位机 5935。
- 完成 `device_hello -> host_ack -> ping/pong`。
- 采集两端日志和至少一份连接表或抓包证据。

## 11. 验收标准

### AC-01 真实目的地址正确

- 给定发现地址 `192.168.1.191:5935`，真实设备后端计算出的实际目标必须是 `192.168.1.191:5935`。
- 若实际目标为 `127.0.0.1:5935`，直接判定失败。

### AC-02 模拟翻译无回归

- 模拟设备配网仍通过 loopback 和动态 AP 端口完成。
- 模拟设备连接模拟上位机仍通过 loopback 的 `host_tcp_port` 完成。

### AC-03 上位机监听覆盖通告地址

- Windows 真实上位机监听 `0.0.0.0:5935` 或通告 IP:5935。
- 只监听 `127.0.0.1:5935` 判定失败。

### AC-04 通告一致性

- mDNS、`host_announce`、启动日志中的 IP/端口完全一致。
- 通告 IP 为有效局域网 IPv4，不得为 loopback、unspecified 或 APIPA。

### AC-05 会话建立

- 设备发送 `device_hello`。
- 上位机返回 `host_ack status=ok`。
- 设备事件日志出现“会话已建立”。
- 设备不因该连接进入 HEAL。

### AC-06 失败行为

- 上位机不可达时设备仍进入现有 HEAL 流程，无崩溃、无 socket 泄漏。
- 上位机端口被占用时，上位机启动失败且不发送可用通告。

### AC-07 日志

- 设备产生带时间戳的持久日志文件。
- 日志能够区分请求目标和实际目标。
- 日志中无 WiFi 密码。
