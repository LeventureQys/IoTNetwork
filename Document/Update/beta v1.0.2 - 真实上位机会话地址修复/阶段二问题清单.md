# 问题清单 - beta v1.0.2 / 阶段二

## v1（设计梳理，2026-08-05）

### 置顶区（待用户确认，阶段阻塞）

无。用户已明确要求设备端和 PC 端修改计划分开编写、分开执行；当前代码事实足以形成两套独立设计，不存在需要再次选择的重大技术路线。

### 自决区（不阻塞阶段流）

#### Q1. 两端工作如何拆分与设置门禁

- 问题描述：根因发生在设备共用后端，但 PC 端还存在监听启动顺序和通告诊断不足。若混成一个任务，任一平台阻塞会影响另一端交付。
- 自决方案：建立两条独立工作线。
  - 设备端工作线：真实 TCP 目的地址、模拟回归、设备日志落盘、设备侧文档和 Linux 测试。
  - PC 端工作线：真实监听事实核对、监听先于通告、失败回滚、通告地址校验与日志、PC 侧文档和 Windows 待验收项。
  - 两端分别提交开发结果；真实端到端联调只在两端均完成后执行。
- 自决理由：符合用户“分开走、分开编写”的明确要求，并让当前 Linux 可验证的设备端不被 Windows 环境阻塞。
- 风险预警：单端通过不等于版本最终通过；最终仍需双端真实会话证据。
- 置信度：100%。

#### Q2. 设备 TCP 目的地址 helper 放在哪里

- 问题描述：直接在 `SimBackend::TcpConnect()` 内写分支难以在不初始化真实 WiFi 的情况下单测；加入公共网络抽象又会扩大接口面。
- 自决方案：在 `demo/net_sim/` 增加仅该模块和测试使用的内部地址解析 helper，输入运行模式、请求端点和模拟端口信息，输出有效 IPv4/端口；不修改 `net_backend_t` 和 `net_tcp_connect()` 公共签名。
- 自决理由：能够纯逻辑测试真实地址保持和模拟翻译，又不把实现细节暴露为跨后端公共 API。
- 风险预警：helper 必须只处理地址选择，不封装 socket 生命周期，避免形成第二套 connect 实现。
- 置信度：96%。

#### Q3. 模拟模式未知地址是否改为显式失败

- 问题描述：当前模拟后端除模拟 AP/Host 地址外，其他地址也映射到 loopback；`SimSocket.LoopbackTcp` 依赖该兼容行为。
- 自决方案：本版本保留模拟模式现有行为，未知地址仍以 loopback 和原请求端口连接；只对 Linux 真实设备模式改为真实 IP。
- 自决理由：本版本是针对真实模式的缺陷修复，改变模拟未知地址语义会造成无关回归。
- 风险预警：模拟模式不是通用网络后端；文档不得把该兼容行为描述成真实直连能力。
- 置信度：98%。

#### Q4. Windows TCP listener 是否需要修改绑定地址

- 问题描述：需求阶段推测真实 listener 可能只绑定 loopback，但代码核对显示 `demo/net_win/win_backend.cpp` 已绑定 `INADDR_ANY`。
- 自决方案：不改变绑定地址；保留 `0.0.0.0:<host_tcp_port>`。只补充真实绑定日志、错误码和启动失败回滚。`HostTcpServer` 当前显示 `host_virtual_ip` 的日志改为区分“监听端点”和“通告端点”。
- 自决理由：现有绑定已覆盖通告 IP，修改为单网卡绑定反而引入 DHCP 地址变化和多网卡生命周期问题。
- 风险预警：通配监听扩大到所有 IPv4 接口，实际访问控制继续由 Windows 防火墙负责。
- 置信度：99%。

#### Q5. PC 端真实 mDNS 是否在本版本实现

- 问题描述：Windows 后端的 mDNS 当前委托 `SimWorld`，并非局域网真实 mDNS。设备真实发现主要依赖 UDP 组播 `host_announce`。
- 自决方案：本版本不新增 Windows DNS-SD/mDNS 网络栈；保留现有 mDNS 兼容代码，但不得把它作为 Windows 真实验收通过条件。真实发现验收以 UDP `224.0.2.1:5936` 通告和候选连接为准。
- 自决理由：实现真实 mDNS需要新增系统 API或第三方依赖、接口作用域和冲突处理，明显超出已确认的 TCP loopback 根因。
- 风险预警：若 UDP 组播被网络策略阻断，设备只能依赖候选列表；真实 mDNS应另立版本实现。
- 置信度：97%。

#### Q6. PC 多网卡最优地址选择是否纳入本版本

- 问题描述：`win_backend_get_ipv4()` 当前选择第一个 Up 且非 loopback 的 IPv4，可能选到 VPN、虚拟网卡或 APIPA。
- 自决方案：本版本只增加基础有效性过滤：拒绝 `0.0.0.0`、loopback 和 `169.254.0.0/16`；不新增默认路由 metric、WLAN GUID 绑定、网络变化通知或网卡选择 UI。
- 自决理由：多网卡最优路由需要产品定义“服务所有接口还是目标 WLAN”及网络切换语义，属于独立功能；当前需求只要求不通告明显无效地址。
- 风险预警：复杂多网卡环境仍可能选中非目标局域网地址，Windows 验收必须核对通告地址是否从设备可达。
- 置信度：93%。

#### Q7. PC 启动顺序如何定义

- 问题描述：当前 `HostApp::Start()` 先注册 mDNS、再启动 announcer、最后启动 TCP listener；listener 失败时依赖析构延迟清理。
- 自决方案：启动顺序固定为 `TCP listener -> announcer -> mDNS`。TCP 或 announcer 失败时立即逆序回滚；mDNS 保持非关键兼容能力，注册失败记录警告但不使真实组播服务启动失败。
- 自决理由：只有 listener 就绪后才应暴露服务；当前真实 mDNS并非局域网能力，不应阻断组播主路径。
- 风险预警：必须给 `HostTcpServer` 增加显式幂等 `Stop()`，避免只能等析构关闭 listener。
- 置信度：95%。

#### Q8. 设备日志由程序还是脚本落盘

- 问题描述：脚本 `tee` 与程序 `log_set_file()` 同时使用会重复日志，并可能改变 `exec`、sudo 和信号行为。
- 自决方案：只修改 `demo/device/app/main.cpp`，复用 PC 端 `log_set_file()`；`start_device.sh` 不增加 tee。
- 自决理由：公共日志已同时输出终端和文件，且程序切换工作目录后能稳定写入 `demo/logs/`。
- 风险预警：日志初始化前的配置错误仍只写 stderr；本版本不为早期错误引入第二套日志。
- 置信度：98%。

#### Q9. 日志是否新增单元测试文件

- 问题描述：公共日志已有文件输出能力，本版本只是设备入口接入；新增全局日志状态测试可能与其他测试产生干扰。
- 自决方案：设备端工作线不修改公共日志实现；新增最小日志测试时放入现有 `provision_demo_tests`，每例清理 sink 和文件。设备程序日志路径通过启动冒烟验证。
- 自决理由：覆盖“不重复落盘”和文件切换有价值，但不需要建立新测试二进制。
- 风险预警：日志测试不可并行操作同一进程级全局日志状态。
- 置信度：92%。

### 阶段二结论

- 设备端和 PC 端分别设计、分别开发、分别提交检查。
- 设备端可在当前 Linux 完成构建、单测和启动冒烟。
- PC 端可完成代码修改和 Linux 可编译的共用核心测试，但 Windows 专有构建与真实运行必须标记待 Windows 环境验收。
- 双端真实联调不归入任一端“开发完成”的单端判定，但属于版本最终验收必需项。
