### 自决区（不阻塞阶段流）

#### Q1. 真实设备连接应使用发现地址还是配置默认地址

- 问题描述：设备已从 mDNS、组播或候选列表得到 `app->sess_host`，但共用后端仍使用 loopback。需要确定真实连接目标的唯一来源。
- 自决方案：真实 Linux 设备模式直接使用 `net_tcp_connect()` 传入的 `net_addr_t.ip` 和 `port`；不得使用 `host_virtual_ip` 或硬编码地址覆盖。
- 自决理由：服务发现的职责就是输出本轮可连接端点，且 `net_addr_t` 已经沿调用链传到后端；使用它能同时覆盖 mDNS、组播和候选列表。
- 风险预警：必须严格保持网络字节序，避免二次转换。
- 置信度：99%。

#### Q2. 上位机真实模式监听通配地址还是单一局域网地址

- 问题描述：上位机可能存在多网卡或 DHCP 地址变化；只监听回环不可达，绑定单一地址则可能因地址刷新启动失败。
- 自决方案：真实 Windows 后端监听 `0.0.0.0:<host_tcp_port>`，服务发现只通告 `win_backend_get_ipv4()` 选定的局域网地址；模拟后端继续只监听 loopback。
- 自决理由：通配监听能覆盖被通告的局域网地址且不要求每次地址变化重建 listener；对外暴露范围由 Windows 防火墙和部署策略控制。
- 风险预警：多网卡主机仍需保证通告算法选中设备可达的接口；本版本不新增网卡选择 UI。
- 置信度：95%。

#### Q3. 上位机代码在当前 Linux 下无法实测如何处理

- 问题描述：PC 真实 WiFi 后端仅 Windows 支持，当前 Linux 入口会强制回退模拟模式，不能验证 Windows Native WiFi、Winsock 监听和防火墙。
- 自决方案：当前阶段完成代码核对、可交叉编译范围内的静态检查和 Linux 可运行测试；Windows 构建、启动、监听、通告和端到端会话写入后续验收项，标记“待 Windows 环境执行”。
- 自决理由：用户已明确不要求在当前 Linux 下测试上位机，且开发规范禁止把无法执行项默认判定通过。
- 风险预警：Windows 专有代码可能存在仅 MSVC/运行时可暴露的问题，版本最终验收仍依赖 Windows 环境。
- 置信度：100%。

#### Q4. 设备诊断日志应由脚本 tee 还是程序文件日志实现

- 问题描述：`start_device.sh` 当前不落盘，设备程序也未像 PC 程序一样调用 `log_set_file()`。脚本 tee 可捕获早期 stderr，程序日志更结构化，但同时启用会重复记录。
- 自决方案：设计阶段优先采用设备程序内 `log_set_file()` 作为主日志链路，脚本负责创建目录或显示日志路径；仅对日志初始化前的早期失败保留 stderr，不再额外 tee 全部运行日志。
- 自决理由：项目已有 PC 端同类实现，复用现有日志生命周期最一致，也避免 sudo 管道、退出码和信号转发复杂化。
- 风险预警：配置解析失败发生在 `log_init()` 前，仍只能从终端看到；若必须持久化全部早期错误，可在后续设计中把日志初始化提前，但不能掩盖原错误码。
- 置信度：92%。

#### Q5. 是否修改设备状态机连接失败行为

- 问题描述：TCP 连接失败后设备进入 HEAL，并在 WiFi 无效时返回 STA 重连。日志中也观察到一次 WiFi 短暂断开。
- 自决方案：本版本不修改状态机、自愈退避、WiFi 校验或凭据确认逻辑，只修正 TCP 目标地址和诊断能力。
- 自决理由：当前主根因发生在后端目标地址改写；现有状态机对不可达上位机的恢复行为符合设计。扩大修改会增加回归风险且缺少直接证据。
- 风险预警：端到端修复后若仍频繁掉 WiFi，应作为独立问题采集 NetworkManager、内核和设备日志，不与本修复混合。
- 置信度：97%。

#### Q6. 是否硬编码现场上位机 `192.168.1.191`

- 问题描述：现场发现地址当前为 `192.168.1.191`，但该地址由 DHCP 和网络环境决定。
- 自决方案：禁止硬编码；设备始终连接服务发现结果，上位机始终通告运行时选定的真实 IPv4。
- 自决理由：硬编码只能暂时绕过现场问题，会破坏 DHCP、多网络和后续部署。
- 风险预警：如果上位机通告错误地址，设备会按协议连接错误目标，因此必须补充通告一致性日志和验收。
- 置信度：100%。
