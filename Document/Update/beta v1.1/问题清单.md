# 问题清单 - beta v1.1 / 阶段一

## v1（初次梳理，2026-08-03）

### 置顶区（待用户确认，阶段阻塞）

#### Q1. beta v1.1 的交付边界是否必须包含可在真实 ESP32-C2 硬件运行的设备端实现
- 问题描述：需求要求“PC端程序和设备端程序”的业务流程都裁剪（`Document/Update/beta v1.1/需求说明.md:5`），并明确 ESP32 上电后主动扫描、连接 PC 热点（`Document/Update/beta v1.1/需求说明.md:9`）。但仓库设备端真实硬件后端仍是骨架：`demo/device/backends/esp32c2/esp32c2_backend.c:44` 的扫描、`demo/device/backends/esp32c2/esp32c2_backend.c:57` 的 STA 连接、`demo/device/backends/esp32c2/esp32c2_backend.c:179` 的 TCP 连接均返回占位错误；固件入口也明确说明所有能力未实现（`demo/device/firmware/esp32c2/main/app_main.c:43`）。如果要求实机可用，就不只是业务层裁剪，还必须实现或接入硬件抽象层。
- 建议方案：本 Version 以“PC Windows 后端 + 设备 sim 后端 + 设备纯 C 业务状态机 + ESP32-C2 业务接线/接口契约”为交付范围；保留 ESP32-C2 HAL 骨架，不在本 Version 实现真实 `esp_wifi/lwIP/NVS` 驱动。用单元测试、双进程 sim 启动测试和协议集成测试验证业务流程；将真实 ESP32-C2 后端实现与实机测试单列后续硬件移植 Version。
- 备选方案 A：本 Version 同时落地完整 ESP-IDF 后端并进行 ESP32-C2 实机测试。该方案会跨越“只改业务层、硬件层不要做过多修改”的边界，且需要 ESP-IDF 工具链、板卡、串口及可用 WiFi 环境。
- 备选方案 B：只修改 PC/设备模拟 Demo，不调整 ESP32 固件入口和移植契约。该方案开发范围最小，但设备端交付容易被误解为真实固件已支持 v1.1。
- 风险预警：若选择建议方案，beta v1.1 不能宣称“ESP32-C2 实机已验证”；若选择备选方案 A，需求范围、开发周期、测试环境和硬件层修改约束都会发生重大变化。
- 置信度：85%
- 归入置顶原因：是否实现真实硬件后端会改变代码边界、任务拆分、验收环境和完成定义，选错将导致阶段二设计及阶段三开发大幅返工。

#### Q2. PC 热点的 SSID `Modu_xxx` 中 `xxx` 应采用什么稳定来源
- 问题描述：需求只规定名称形态 `Modu_xxx`（`Document/Update/beta v1.1/需求说明.md:9`），未规定 `xxx` 的长度、字符集、来源或用户是否可配置。旧流程由设备生成 `Modu_XXXX`，现有设备端状态初始化使用设备索引生成热点名，且 PC 端只负责扫描设备热点；反转角色后必须定义 PC 热点的确定名称，否则设备的选择规则和一对一绑定规则无法设计。
- 建议方案：将热点 SSID 设为配置项 `pc_ap_ssid`，格式强制为 `Modu_` + 1~27 个 ASCII 字母/数字/短横线/下划线；默认值 `Modu_PC`。设备扫描所有 `Modu_` 前缀热点，但仅连接配置中的精确 SSID；这样一对一关系明确、可测试，也允许现场多套系统共存而不误连。
- 备选方案 A：固定使用唯一名称 `Modu_xxx`（字面值）。设备无需额外配置，但同一区域有两台 PC 时无法区分。
- 备选方案 B：由 PC 自动使用无线网卡 MAC 后 4 位生成 `Modu_XXXX`，设备连接信号最强的 `Modu_` 热点。部署无需手工配置，但网卡更换会改变名称，且多个 PC 同场时可能误连。
- 风险预警：若不定义稳定来源，设备可能连接错误 PC；若依赖网卡 MAC，虚拟网卡/多网卡选择和硬件更换会导致热点名称变化。
- 置信度：80%
- 归入置顶原因：SSID 生成和设备选网策略是 PC/设备跨端的基础契约，会决定配置模型、状态机和一对一安全边界。

#### Q3. PC 热点的固定 IP 与“如果不是，PC 端自己想办法”的处理策略
- 问题描述：需求要求 PC 检查固定 IP，且文档约定 IP；若不是则程序“自己想办法”（`Document/Update/beta v1.1/需求说明.md:11`），但没有给出具体 IP、子网掩码、DHCP 范围或是否允许程序修改网卡配置。当前协议仅保留旧设备热点地址 `192.168.1.1`（`demo/device/include/protocol.h:20`），Windows 后端只能读取接口 IP（`demo/pc/backends/windows/win_backend.cpp:568`），没有设置静态 IP 的能力。
- 建议方案：约定 PC 热点地址 `192.168.137.1/24`、设备通过热点 DHCP 获取地址、设备固定连接 `192.168.137.1:5935`。PC 启动热点后校验承载热点的虚拟网卡 IP；若不符合，则通过受控系统命令/API 配置为该地址，配置失败时明确报错并停止 TCP 服务，不在错误接口上继续运行。
- 备选方案 A：约定 `192.168.4.1/24`，与 ESP-IDF 常见 SoftAP 默认网段一致；但 Windows 移动热点默认网段通常不是该地址，PC 端更可能需要强制改网卡配置。
- 备选方案 B：不强制固定 IP，PC 将实际热点网关地址写入一个设备可获取的额外发现机制。该方案重新引入服务发现，违背本次简化目标。
- 风险预警：Windows 移动热点、ICS 和网络配置通常需要系统权限，地址可能受系统版本或 ICS 管理影响；强改 IP 可能影响用户现有网络。具体地址若后续改变，ESP32 固件常量与 PC 配置必须同步升级。
- 置信度：75%
- 归入置顶原因：固定 IP 是设备 TCP 目标地址，也是 Windows 权限与网卡配置策略的核心；地址和失败策略不明确无法形成可实施、可验收的跨端契约。

#### Q4. PC 在 Windows 上主动创建热点应采用哪条系统技术路线
- 问题描述：需求要求 PC 主动打开带密码热点（`Document/Update/beta v1.1/需求说明.md:9`），但当前 Windows 后端把 `wifi_ap_start/wifi_ap_stop` 明确映射为不支持（`demo/pc/backends/windows/win_backend.cpp:298`、`demo/pc/backends/windows/win_backend.cpp:506`）。Windows 的热点能力受系统版本、无线网卡驱动、ICS/移动热点服务和权限影响，技术路线会直接影响可部署性。
- 建议方案：目标平台限定 Windows 10/11；PC 后端新增“系统托管移动热点适配器”，优先调用 Windows 现代移动热点能力，启动后验证 SSID、热点网卡及固定 IP；能力不可用或权限不足时 fail-closed，UI 展示可操作错误，不回退到模拟后端。开发时同时保留 sim 热点后端以支持自动化测试。
- 备选方案 A：调用 `netsh wlan set hostednetwork/start hostednetwork`。实现边界清晰，但 Hosted Network 在新网卡/新 Windows 驱动中已废弃或不受支持，部署成功率不可控。
- 备选方案 B：程序只检测用户手动开启的 Windows 移动热点，不主动创建。兼容性较高，但不满足“PC端会主动打开”这一明确需求。
- 风险预警：现代 Windows 热点 API 可能涉及 WinRT、异步调用、用户授权及系统策略；无支持 WiFi Direct/移动热点的网卡时无法由软件规避。若要求非 Windows 平台，需重新选择 NetworkManager/hostapd 等实现。
- 置信度：75%
- 归入置顶原因：热点实现是本 Version 最大的 PC 平台能力新增，路线决定依赖、权限、后端接口和启动测试环境，错误选择会造成大量返工。

#### Q5. v1.1 应保留多大范围的握手、心跳和断线重连协议
- 问题描述：需求明确“建立握手、心跳包连接”（`Document/Update/beta v1.1/需求说明.md:13`），但未说明是否沿用 v1.0 的长度前缀 JSON、`device_hello/host_ack`、`ping/pong`、`session_id`、诊断、限速和重连策略。现有握手与心跳位于 `demo/device/src/core/device_session.c:24`、`demo/device/src/core/device_session.c:60`、`demo/device/src/core/device_session.c:147`，PC 端在 `demo/pc/core/host_tcp_server.cpp` 中配套处理；服务发现是独立模块 `demo/device/src/core/device_discovery.c`。裁剪过多会重写协议，保留过多则可能不符合“大幅度裁剪”。
- 建议方案：保留传输帧（2 字节大端长度 + JSON）、`device_hello`/`host_ack`、`ping`/`pong`、应用数据和基本断线重连；删除 SoftAP 配网消息 `auth/auth_result/wifi_config/wifi_result/close_ap`，删除 mDNS、UDP `host_announce/host_bye`、候选地址发现、多 WiFi 凭据/回滚和多设备容量逻辑。握手保留设备 ID、协议版本、心跳间隔，去掉 `busy`、多设备注册表扩展和不影响一对一通信的诊断字段。
- 备选方案 A：完整保留现有会话协议，仅替换 WiFi 建链和服务发现。兼容风险最低，但业务裁剪程度较小。
- 备选方案 B：协议简化为连接后固定 `hello/ack` 和无序号心跳。代码更少，但会破坏现有协议契约、测试和帧健壮性，需要双端大面积重写。
- 风险预警：协议字段删除会影响 `share/protocol-contract.json`、跨端 golden 契约、UI 流程图和大量单元测试；若后续仍需诊断/多设备，删除后需重新引入。
- 置信度：85%
- 归入置顶原因：这是业务裁剪深度的核心产品决策，决定哪些现有模块删除、哪些协议兼容、测试需要重写到什么程度。

#### Q6. 热点密码字面值采用需求中的 `modu_leventure`
- 问题描述：需求明确密码为 `modu_leventure`（`Document/Update/beta v1.1/需求说明.md:9`），而旧设备热点实现使用 `modutech_leventure`（`demo/device/src/core/device_provision.c:31`），两者不同。
- 自决方案：beta v1.1 PC 热点与设备连接统一使用精确字面值 `modu_leventure`，不沿用旧密码；将其作为跨端配置默认值并在协议/验收文档中明确。
- 自决理由：新需求给出了无歧义的精确密码，旧值属于被裁剪流程，不能覆盖新需求。
- 风险预警：已有脚本、配置或人工操作若仍使用旧密码会连接失败，需要同步更新测试夹具和文档。
- 置信度：99%

#### Q7. TCP 服务端口固定为 5935
- 问题描述：需求明确 PC 在 5935 端口开启 TCP 服务器（`Document/Update/beta v1.1/需求说明.md:11`）；现有两端协议常量也均为 5935（`demo/device/include/protocol.h:12`、`demo/pc/include/pc/protocol.h:12`）。
- 自决方案：生产默认端口和跨端契约固定为 5935；sim 测试可通过端口映射避免本机冲突，但对设备暴露的逻辑端口仍为 5935。
- 自决理由：需求与现有协议完全一致，无路线分歧。
- 风险预警：端口被占用或被防火墙阻止时必须明确启动失败，不允许静默改用其他生产端口。
- 置信度：99%

#### Q8. 一对一限制应在 PC 服务端和设备选网两端同时执行
- 问题描述：需求只考虑一对一（`Document/Update/beta v1.1/需求说明.md:9`），但旧协议支持 16 个设备连接（`demo/device/include/protocol.h:17`），PC 注册表和 TCP 服务也按多连接设计。
- 自决方案：PC TCP 服务最多接受一个已握手设备；第二连接明确回复拒绝后关闭。设备只连接配置的精确 PC SSID，且任一时刻仅维护一个 TCP 会话。
- 自决理由：双端限制才能真正实现一对一；仅限制服务端仍会允许设备误连错误热点，仅限制设备端则 PC 仍存在多连接状态与 UI 歧义。
- 风险预警：若未来恢复多设备，连接上限、注册表和 UI 必须重新扩展；当前应保留清晰的拒绝日志便于定位误连。
- 置信度：95%

#### Q9. 服务发现链路应从 v1.1 生产业务流程中移除
- 问题描述：新需求要求设备连接“指定 IP 的指定端口”（`Document/Update/beta v1.1/需求说明.md:13`），固定 IP 已替代当前 mDNS→组播→候选地址三级发现（`demo/device/src/core/device_discovery.c:73`）；PC 仍在启动 mDNS 与 UDP 通告（`demo/pc/core/host_app.cpp:26`）。
- 自决方案：生产流程不启动 mDNS、UDP announce/bye 或候选地址探测；设备完成 WiFi 连接后直接进入 TCP CONNECT。相关抽象接口可按最小改动保留给后端，但不进入 v1.1 业务状态机；无引用的业务类、配置和测试按设计阶段进一步确定删除或归档。
- 自决理由：固定 IP 直连正是此次简化的核心，保留并行发现链路会产生两个主机地址来源和额外失败状态。
- 风险预警：固定 IP 配置失败时不再有发现回退，必须由 PC 热点/IP 启动门禁保证地址正确。
- 置信度：97%

#### Q10. 设备 WiFi 凭据不再由 PC 通过 TCP 下发
- 问题描述：旧流程由 PC 扫描设备热点并发送 `wifi_config`（`demo/pc/core/host_app.cpp:90`、`demo/device/src/core/device_provision.c:198`）；新流程反转角色，SSID/密码已由产品约定，设备上电主动扫描 PC 热点（`Document/Update/beta v1.1/需求说明.md:9`）。
- 自决方案：设备将 PC 热点 SSID（见 Q2 决策）和固定密码作为设备配置/编译默认值，扫描后直接 STA 连接；删除运行时配网认证、WiFi 凭据下发、确认回滚和 `close_ap` 交接流程。
- 自决理由：新流程不存在传递目标 WiFi 凭据的控制通道，继续保留旧配网服务器没有业务意义。
- 风险预警：热点名称改变时设备配置必须同步；配置入口与默认值需在设计文档中明确，避免硬编码散落。
- 置信度：97%

#### Q11. 新功能测试必须覆盖双端单元测试、双进程启动与异常路径
- 问题描述：本需求修改 PC 热点数据流、设备状态机、TCP 建链和跨端协议，符合新功能/较大更新标准；规范要求单元测试和启动测试（`Document/Agent开发规范.md:159`）。仓库已有 PC gtest、设备 CTest 和跨端集成测试入口（`README.md:80`）。
- 自决方案：阶段二验收设计至少覆盖：PC 热点启动/固定 IP 校验正常与失败、设备扫描过滤与密码错误、单设备 TCP 握手、心跳超时重连、第二设备拒绝、PC/设备 offscreen 启动、sim 双进程完整路径。若选择实机交付，再追加 Windows 真热点与 ESP32-C2 实机启动证据。
- 自决理由：规范和现有测试基础都明确，测试类型无路线分歧。
- 风险预警：真实 Windows 热点测试依赖网卡、管理员权限和系统服务；无法满足时必须记录阻塞，不得用 sim 结果冒充实机结果。
- 置信度：99%

#### Q12. beta v1.1 的设备端生产运行目标应以 Linux 后端为准，还是还需同步交付 ESP32-C2 实机能力
- 问题描述：用户明确“Device设备端代码也需要修改”，并指出 Linux backend 已完成实验。复核确认 Linux 后端具备真实 WiFi 扫描、STA 连接和 TCP 客户端能力：`demo/device/backends/linux/linux_wifi.c:296` 实现 `nmcli` 扫描，`demo/device/backends/linux/linux_wifi.c:76` 实现连接热点，`demo/device/backends/linux/linux_socket.c:85` 实现 TCP 连接，且由 `demo/device/backends/linux/device_linux_backend.c:172`、`demo/device/backends/linux/device_linux_backend.c:177`、`demo/device/backends/linux/device_linux_backend.c:232` 接入网络抽象。与此同时，需求文字使用“esp32设备”（`Document/Update/beta v1.1/需求说明.md:9`），但 ESP32-C2 后端的对应接口仍是骨架占位（`demo/device/backends/esp32c2/esp32c2_backend.c:44`、`demo/device/backends/esp32c2/esp32c2_backend.c:57`、`demo/device/backends/esp32c2/esp32c2_backend.c:179`）。阶段二必须明确生产验收对象，否则无法确定是否需要 ESP-IDF 实机开发。
- 建议方案：本 Version 的设备端代码必须修改，生产业务以“设备纯 C 状态机 + 已完成的 Linux 真实后端”为主要实现和真实环境验收目标；sim 后端承担自动化测试；ESP32-C2 侧同步更新业务状态机复用、默认配置、接口契约和移植文档，但不补写现有 HAL 占位实现，也不宣称 ESP32-C2 实机通过。这样可按用户说明充分利用已完成实验的 Linux backend，同时遵守“硬件层不要做过多修改”。
- 备选方案 A：Linux 真实后端和 ESP32-C2 实机后端都作为本 Version 生产交付，补齐 `esp_wifi/lwIP/NVS` 并执行板卡测试。
- 备选方案 B：只以 Linux 设备为最终产品目标，删除或停止维护 ESP32-C2 的本次业务接线与文档。该方案与需求中的“esp32设备”表述冲突。
- 风险预警：采用建议方案时，功能流程会在 Linux 真实后端和 sim 上完成，但 ESP32-C2 仍需后续硬件移植才能上板；采用备选方案 A 会引入 ESP-IDF 工具链、硬件、串口和真实无线环境，并显著扩大硬件层范围。
- 置信度：85%

#### Q13. Linux 后端只复用 STA、扫描和 TCP 能力，不再调用设备侧热点能力

### 已确认的版本契约
