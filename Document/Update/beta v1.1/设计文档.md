## 2. 背景与目标

beta v1.0 使用“设备创建 SoftAP、PC 下发目标 WiFi、mDNS/组播发现 PC、设备连接 PC”的多阶段流程。beta v1.1 将其裁剪为一对一固定拓扑：Windows PC 主动创建带密码的热点，Linux 设备扫描并连接该热点，然后直接连接固定地址 `192.168.137.1:5935`，执行握手、心跳和应用数据通信。

本 Version 只交付 Windows PC 与 Linux 设备端；设备 sim 后端继续用于自动化测试。`demo/device/backends/esp32c2/` 与 `demo/device/firmware/esp32c2/` 完全不在开发和验收范围。

## 3. 范围

### 3.1 纳入范围

1. PC Windows 10/11 现代移动热点启动、停止、SSID/密码设置、热点网卡 IPv4 校验和固定地址配置。
2. PC sim 后端发布虚拟热点，支持双进程自动化。
3. Linux 设备扫描精确 SSID、STA 连接、获取 IP、直连固定 PC 地址。
4. 设备 sim 后端读取 PC 虚拟热点记录并执行同等流程。
5. 一对一 TCP 服务、基础握手、心跳、应用数据和断线重连。
6. PC/设备 UI、配置、协议契约、事件、测试、README 和集成脚本同步更新。

### 3.2 明确不纳入范围

1. ESP32-C2 后端、ESP-IDF 固件、板卡构建和实机测试。
2. PC 在 Linux 上创建热点。
3. 设备侧创建热点、PIN 认证、WiFi 凭据下发、NVS 凭据确认回滚。
4. mDNS、UDP 组播 `host_announce/host_bye`、候选地址列表。
5. 多设备并发管理、动态服务容量和多目标 PC 选择。
6. TLS、应用层加密、互联网依赖和云服务。

## 5. 目标拓扑与生命周期

```text
Windows PC
  1. 校验配置
  2. 启动 SSID=Modu_PC（可配置）的 WPA2 热点
  3. 确保热点接口 IPv4=192.168.137.1/24
  4. 监听 0.0.0.0:5935
  5. 等待唯一 Linux 设备连接

Linux Device
  1. 校验配置
  2. 扫描 WiFi，查找精确 pc_ap_ssid
  3. 用 modu_leventure 连接
  4. 获取 DHCP IPv4 并复核当前 SSID
  5. 连接 192.168.137.1:5935
  6. device_hello → host_ack
  7. ping/pong + app_data
  8. WiFi/TCP 失败后退避并重试
```

PC 正常退出顺序：停止接收新连接 → 关闭在线/待握手连接 → 关闭 TCP listener → 停止热点 → 删除 sim catalog/释放 Windows 系统资源。

PC 启动任一步失败都按逆序回滚，不允许 TCP 已监听但热点未就绪，也不允许热点已创建但固定 IP 未配置成功后继续运行。

## 7. 公共网络后端契约

### 7.1 PC 后端

现有 `wifi_ap_start/wifi_ap_stop` 保留，语义调整为 PC 主动热点。新增：

```c
typedef struct net_ap_status {
    int started;
    char ssid[33];
    char ipv4[16];
    int prefix_length;
} net_ap_status_t;

int (*wifi_ap_status)(void *user, net_ap_status_t *status);
int (*wifi_ap_configure_ipv4)(void *user, const char *ipv4, int prefix_length);
```

包装函数为 `net_wifi_ap_status`、`net_wifi_ap_configure_ipv4`。

- `wifi_ap_start(user, ssid, pass, NULL)`：成功时热点已可被设备扫描；PIN 参数必须忽略且调用方传 NULL。
- `wifi_ap_status`：成功填充实际 SSID、IPv4、前缀；热点未运行返回 `DEMO_ERR`。
- `wifi_ap_configure_ipv4`：只配置热点承载适配器；成功后再次 status 必须得到目标值。
- `wifi_ap_stop`：幂等；未启动返回 `DEMO_OK`。
- 不支持平台返回 `DEMO_ERR`，不得回退 sim。

### 7.2 Windows 热点组件

## 8. PC 业务设计

### 8.1 `HostApp` 生命周期

`HostApp::Start()`：

1. `net_wifi_ap_start(net_, pc_ap_ssid, pc_ap_password, NULL)`。
2. `net_wifi_ap_status` 查询实际状态。
3. 若 IP/前缀不匹配，调用 `net_wifi_ap_configure_ipv4`，然后重新查询。
4. 任一 SSID/IP/前缀仍不匹配，停止热点并返回错误。
5. `tcp_server_.Start()`。
6. 发出结构化事件 `hotspot_ready`：`{"ssid":"Modu_PC","ip":"192.168.137.1","prefix_length":24}`；不得包含密码。

`RequestStop()`/析构：停止 TCP，再停止热点。删除 announcer、mDNS 和 provision client 成员与线程。

### 8.2 一对一 TCP

- listener 可接受待握手连接，但“在线设备 + pending”总数不得超过 1。
- 超过上限回复 `host_ack busy reason=single_device_only` 后关闭。
- 同一设备 ID 重连时，如果旧连接已离线，允许恢复；如果旧连接仍在线，新连接按 busy 拒绝，不再替换旧连接。
- `host_ack ok` 保留字段：`status`、`heartbeat_interval`、`session_id`、`proto_ver`。删除 `server_time`、`fw_min_req`。
- `device_hello` 必需字段：`cmd`、`id`、`fw_version`、`proto_ver`、`uptime`；`session_id` 可选。删除 `type`、`capabilities`。

### 8.3 PC UI

删除目标 WiFi 下发组合框、密码输入、扫描按钮和配网按钮。新增只读热点区：SSID、固定 IP、端口、热点状态。设备表固定最多一行，保留设备 ID、在线状态、会话、固件、协议、丢失心跳、重连次数。停止按钮文案改为“停止服务并关闭热点”。流程图节点为：启动→热点启动→固定 IP→TCP 监听→设备握手→会话在线。

## 9. 设备业务设计

### 9.1 状态枚举

```c
typedef enum {
    DEV_STATE_BOOT = 0,
    DEV_STATE_WIFI_SCAN,
    DEV_STATE_STA_JOIN,
    DEV_STATE_CONNECT,
    DEV_STATE_SESSION,
    DEV_STATE_HEAL,
    DEV_STATE_COUNT
} device_state_t;
```

### 9.2 状态转换

- `BOOT`：应用上电抖动；到期进入 `WIFI_SCAN`。
- `WIFI_SCAN`：调用 `net_wifi_scan`，只接受与 `pc_ap_ssid` 精确相等且 `band_2g=1` 的记录。找到进入 `STA_JOIN`；未找到按 WiFi 退避留在/返回该状态。
- `STA_JOIN`：调用 `net_wifi_sta_connect(pc_ap_ssid, pc_ap_password)`；成功后必须 `wifi_get_ip != 0` 且 `wifi_get_current_ssid` 精确匹配，随后构造固定 `sess_host=pc_host_ip:host_tcp_port`，进入 `CONNECT`。失败进入 `HEAL`。
- `CONNECT`：调用现有 `session_connect`。TCP 或握手发送失败进入 `HEAL`，成功进入 `SESSION` 并等待 `host_ack`。
- `SESSION`：维持心跳与应用数据；`host_ack busy` 设置长退避；断线/超时进入 `HEAL`。
- `HEAL`：若 WiFi 当前 SSID/IP 仍有效，按 TCP 退避回 `CONNECT`；否则断开 STA，按 WiFi 退避回 `WIFI_SCAN`。不进入 AP，不进入 discovery。

### 9.3 设备内部结构裁剪

`device_app` 删除 AP listener/connection/PIN/凭据数组/确认窗口/discovery socket/候选列表字段。保留一个 `net_addr_t sess_host`、单会话字段、退避和事件日志。`device_app_handle_rx` 只处理业务连接，签名改为：

```c
void device_app_handle_rx(device_app_t *app, void *sock);
```

删除 `is_business` 分支和 provision 分发。

### 9.4 Linux 后端边界

当前 `demo/device/backends/linux/device_linux_backend.c:431` 无条件创建需要 root 的热点实例，`demo/device/backends/linux/device_linux_backend.c:447` 又把它传给 `linux_wifi_create`；WiFi 仅在 `demo/device/backends/linux/linux_wifi.c:41` 用它读取 STA 接口名。v1.1 必须解除该创建期耦合：

```c
int linux_wifi_create(linux_wifi_t **out, const char *sta_interface,
                      const linux_wifi_ops_t *ops_override);
```

`device_linux_backend_create` 直接把配置的 `sta_interface` 传入 WiFi，不创建 `linux_hotspot_t`，因此纯 STA 设备启动不要求 root。Linux backend vtable 的 `wifi_ap_start/stop` 对 v1.1 实例返回 `DEMO_ERR`。

保留 `linux_hotspot*` 源码及其独立模块测试，不修改 hostapd/dnsmasq 实现；状态机不得调用热点、`tcp_listen`、mDNS 或 UDP。允许为 STA 扫描/连接的错误语义补测试或修正与抽象不一致的局部 bug。

### 9.5 设备 UI

流程节点改为：启动→扫描 PC 热点→连接热点→连接 PC→会话在线→异常重连。删除设备 AP SSID、密码、PIN 和配网端口展示；增加目标 SSID、PC 地址和 WiFi 状态。

## 10. 协议契约

### 10.1 帧

所有 TCP 消息继续使用 2 字节大端长度 + UTF-8 JSON，负载 1~1024 字节。空帧、超长帧和非法 JSON 沿用每连接最多 3 次后关闭规则。

### 10.2 Commands

保留：`device_hello`、`host_ack`、`ping`、`pong`、`app_data`。

删除：`auth`、`auth_result`、`wifi_config`、`wifi_result`、`close_ap`、`host_announce`、`host_bye`、`diag_query`、`diag_report`。

### 10.3 报文

```json
{"cmd":"device_hello","id":"02:00:00:00:00:01","fw_version":"1.1.0","proto_ver":1,"uptime":10,"session_id":"a1b2c3d4"}
```

`session_id` 首次连接可省略。

```json
{"cmd":"host_ack","status":"ok","heartbeat_interval":10,"session_id":"a1b2c3d4","proto_ver":1}
```

```json
{"cmd":"host_ack","status":"busy","reason":"single_device_only"}
```

```json
{"cmd":"host_ack","status":"fail","reason":"unsupported_protocol"}
```

```json
{"cmd":"ping","seq":1}
{"cmd":"pong","seq":1}
```

`pong.seq` 必须回显 ping 序号。

`app_data` 格式保持现有 `seq + data.type + data.text`。

### 10.4 protocol-contract schema 2

三份契约（PC、设备、integration golden）语义一致，核心结构：

```json
{
  "schema_version": 2,
  "protocol_version": 1,
  "frame": {"prefix_bytes":2,"byte_order":"big","max_payload":1024},
  "tcp": {"host_ip":"192.168.137.1","port":5935,"max_connections":1},
  "wifi": {"ssid_prefix":"Modu_","default_ssid":"Modu_PC","password":"modu_leventure","prefix_length":24},
  "limits": {"app_data_text_bytes":512,"session_id_length":8},
  "commands":["device_hello","host_ack","ping","pong","app_data"],
  "device_states":{"boot":0,"wifi_scan":1,"sta_join":2,"connect":3,"session":4,"heal":5,"count":6}
}
```

注意：密码写入契约是阶段一明确的固定产品常量；任何运行日志和事件仍不得输出密码。

## 11. 结构化事件

### PC

- `hotspot_ready ok`：SSID/IP/prefix。
- `hotspot_error fail`：operation/reason，不含密码。
- `tcp_listening ok`：ip=`0.0.0.0`、port=5935。
- `session_online/session_offline`：沿用。
- `single_device_rejected ok`：reason=`single_device_only`。
- `ping/pong/app_data_tx/app_data_rx/shutdown_complete`：沿用并同步字段。

### Device

- `wifi_scan_started`。
- `wifi_target_found`：SSID/RSSI。
- `wifi_connected`：SSID/device_ip，不含密码。
- `wifi_connect_failed`：reason code。
- `tcp_connecting`：host/port。
- `session_online/session_offline`、`ping/pong/app_data_*`、`shutdown_complete`。

事件 JSON 每行一个对象，继续作为集成测试唯一机器可读证据。

## 12. Stage 与 SubStage

### Stage 1：冻结跨端契约（串行前置）

- SS1.1 协议、配置与 sim catalog 契约。
- 产物：两端 protocol 头/配置字段与三份 contract；不实现业务流程。
- 完成后 Stage 2 才能开始。

### Stage 2：端侧实现（并行）

- SS2.1 PC 热点后端与 HostApp 生命周期。
- SS2.2 PC 一对一会话与 UI。
- SS2.3 设备状态机、配置与 UI。
- SS2.4 sim catalog 双端反转与端侧单元测试。

SS2.1/SS2.2 可由同一 PC Agent 串行完成以减少同文件冲突；SS2.3 与 PC 任务并行；SS2.4 需等待 SS1.1，但可与真实后端业务并行，修改 sim 文件时由 MainAgent协调。

### Stage 3：集成、启动与文档（等待 Stage 2）

- SS3.1 黑盒集成场景、runner、README 和启动测试证据模板。
- MainAgent 汇总执行构建、单元测试、sim 双进程启动、Windows 热点和 Linux 真实路径测试。

## 13. 跨 SubStage 契约

1. SS1.1 对 `protocol.h`、配置字段、contract schema 2 拥有最终定义权；后续不得私自改字段和值。
2. SS2.1 暴露 `net_wifi_ap_start/status/configure_ipv4/stop`，SS2.2 只调用，不直接接触 WinRT。
3. SS2.4 的 PC/设备 catalog 只通过文件 schema 2 交互，不共享源码或静态库。
4. SS2.3 只依赖现有 Linux vtable 的 scan/STA/IP/SSID/TCP 能力，不修改 Linux hotspot 实现。
5. SS3.1 只消费可执行文件、CLI、事件和 contract，不 include 或链接端侧生产源码。

## 14. 错误处理

- 配置非法：进程启动失败，退出码 1，事件 `error`/`hotspot_error`，不得创建热点或 TCP。
- Windows 热点失败：退出码 2，清理已创建资源，不回退 sim。
- 固定 IP 配置失败：退出码 2，停止热点，不启动 TCP。
- TCP 5935 占用：退出码 2，停止热点。
- Linux 扫描无目标：不退出，按退避持续扫描并产生日志/事件。
- Linux 认证失败 202：进入 HEAL 后按配置退避重试，不进入设备 AP。
- DHCP/IP/SSID 校验失败：断开 STA 后回扫描。
- TCP/心跳失败：WiFi 健康则重连 TCP；WiFi 不健康则回扫描。
- 第二设备：PC 回复 busy/single_device_only 后关闭，不影响第一设备。

## 15. 测试策略

### 15.1 单元测试

- PC 配置校验：正常、SSID 非法、密码错误、IP/端口不符。
- PC HostApp 生命周期：热点成功/IP 已正确；热点成功/IP需修正；修正失败回滚；TCP失败关闭热点；重复停止幂等。
- Windows 热点组件：使用可注入系统 ops 测试成功、权限、能力缺失、超时，不要求普通单元测试真实开热点。
- PC 一对一：首设备成功、第二设备 busy、协议版本错误、心跳超时、app_data 边界。
- 设备配置校验：正常和非法。
- 设备状态机：无目标持续扫描、找到目标、认证失败、DHCP失败、直连固定地址、握手、心跳超时、WiFi失效回扫描、busy长退避。
- sim schema 2：发布/读取/过期/owner/错误密码/endpoint 翻译。
- UI QtTest：节点与状态文本不含旧配网/发现文案。

### 15.2 启动与集成

sim 双进程场景：

- A 契约一致。
- B PC 发布热点→设备扫描→STA→TCP→握手→心跳。
- C PC 正常退出→catalog 删除→设备离线并重试。
- D TCP 故障→重连成功。
- E 第二设备被拒绝，第一设备保持在线。
- F 密码错误或目标 SSID 不存在，不产生 session_online。
- G 双向 app_data 512/513/UTF-8。
- H 帧拆包/粘包/畸形/版本错误。

真实环境：

- Windows 10/11 真实热点创建、SSID 可见、密码可连接、热点 IP 为固定值、TCP 监听。
- Linux 真实设备运行 `--backend linux`，扫描并连接 PC 热点，完成会话核心路径。
- 若环境缺失，记录为阻塞，不得由 sim 替代。

7. 禁止跳过单元测试或启动测试宣称完成。

## 17. 可观察验收标准

1. PC 启动后先产生 `hotspot_ready`，再产生 `tcp_listening/ready`；失败时无残留热点和监听端口。
2. 设备事件顺序至少包含 scan→target_found→wifi_connected→tcp_connecting→session_online。
3. 正常会话 10 秒内可见匹配序号 ping/pong。
4. 第二设备得到 `single_device_only` 拒绝，第一设备不断线。
5. 代码、配置、UI、contract 和集成场景不再出现旧生产命令和 AP_PROVISION/DISCOVERY 状态。
6. PC、设备单元测试与 sim 黑盒场景全部通过。
7. Windows 和 Linux 真实启动测试通过，或按规范形成明确环境阻塞项。
