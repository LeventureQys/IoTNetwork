# beta v1.1 验收文档

## 1. 文档目的

本文件供一个不掌握历史对话的验收 Agent 使用。验收对象是 Windows PC 主动热点与 Linux 设备固定地址直连的一对一通信流程。验收必须依次执行编译、单元测试、启动测试、功能完整性和整体回归；任何无法执行项只能标记“阻塞”，不得默认通过。

## 2. 验收依据

- `Document/Update/beta v1.1/需求说明.md`
- `Document/Update/beta v1.1/问题清单.md`
- `Document/Update/beta v1.1/阶段二问题清单.md`
- `Document/Update/beta v1.1/设计文档.md`
- `Document/Update/beta v1.1/开发文档/`

## 3. 验收范围

### 3.1 覆盖

1. PC Windows 10/11 现代移动热点。
2. PC 固定热点 IPv4 `192.168.137.1/24`。
3. PC TCP 5935 与一对一连接。
4. Linux 设备 WiFi 扫描、STA 连接、固定地址 TCP。
5. 基础握手、心跳、应用数据、断线重连。
6. sim 双进程自动化、协议契约、UI、配置和文档。

### 3.2 不覆盖

1. ESP32-C2 和 ESP-IDF。
2. Linux PC 热点。
3. 多设备并发、动态发现、设备 SoftAP 配网。
4. TLS/互联网/云服务。

## 4. 验收环境

### 4.1 自动化环境

- Windows 10/11 x64。
- Visual Studio 2022、CMake ≥3.20。
- Qt 6.8.3 MSVC 2022 x64，默认 `D:/Devtools/Qt/6.8.3/msvc2022_64`。
- PowerShell 5.1+ 或 Python 3。
- 可绑定本机测试端口。

### 4.2 Windows 真实热点环境

- Windows 10/11。
- 支持现代移动热点的无线网卡和驱动。
- 移动热点/ICS相关系统服务可用。
- 测试账号具备所需权限。
- 附近有第二台设备或 Linux 测试机可扫描热点。

### 4.3 Linux 真实设备环境

- Linux 主机作为设备端。
- NetworkManager 与 `nmcli` 可用。
- 可用 WiFi STA 网卡。
- 能扫描并连接 Windows PC 热点。
- Qt 6 Widgets 可运行设备 UI；无桌面时可用 offscreen，但 WiFi/TCP 必须真实。

## 5. 前置条件

1. 工作树包含 beta v1.1 全部阶段三代码。
2. PC/设备配置使用相同 `pc_ap_ssid`，默认 `Modu_PC`。
3. 密码为 `modu_leventure`。
4. PC IP/端口为 `192.168.137.1:5935`。
5. 测试前无残留 `provision_pc`、`provision_device` 进程，无旧 sim catalog。
6. 真实测试前记录网卡原始配置，测试结束检查恢复/清理。

## 6. 证据规范

每项至少记录：执行时间、环境、命令/操作、退出码、关键输出、日志或事件文件路径。UI项提供截图说明；网络项提供适配器/IP或 `nmcli` 输出。密码必须打码。证据建议保存到 `out/beta-v1.1-evidence/<item-id>/`。

状态仅允许：通过、失败、阻塞、未执行。

## 7. 第一层：编译与静态边界

### A1. PC Debug 全量构建
- 目的：确认 PC 生产代码和测试可编译。
- 操作步骤：按 `README.md` 配置 `PC_BUILD_TESTS=ON`，构建 Debug。
- 期望结果：退出码0，无编译错误；新增 Windows 热点组件进入 `pc_win_backend`。
- 通过标准：构建成功且不存在将 WinRT 类型泄露到公共 C 头的错误。
- 失败标准：任一编译/链接失败。
- 证据要求：configure/build 完整日志。

### A2. Device Debug 全量构建
- 目的：确认纯 C core、sim、Linux stub/真实目标和 Qt UI 可编译。
- 操作步骤：配置 `DEVICE_BUILD_TESTS=ON` 后构建 Debug。
- 期望结果：退出码0；device_core不再编译旧 provision/discovery 主流程。
- 通过标准：构建成功。
- 失败标准：任一编译/链接失败。
- 证据要求：构建日志和生成目标列表。

### A3. ESP32 范围隔离
- 目的：确认本 Version 未修改 ESP32。
- 操作步骤：检查版本 diff 中 `demo/device/backends/esp32c2/` 与 `demo/device/firmware/esp32c2/`。
- 期望结果：无 beta v1.1 代码变更。
- 通过标准：两个目录未修改。
- 失败标准：存在未获用户授权的修改。
- 证据要求：diff/状态输出。

### A4. 自包含边界
- 目的：确认 PC、设备、集成测试仍相互源码隔离。
- 操作步骤：运行既有 self-contained 检查；搜索 integration 是否 include/link端侧源码。
- 期望结果：双方可独立构建；integration只消费二进制/JSON/事件。
- 通过标准：检查全部通过。
- 失败标准：出现跨目录生产源码依赖。
- 证据要求：脚本 summary 和搜索结果。

## 8. 第二层：单元测试

### B1. PC 单元测试
- 目的：验证配置、热点生命周期、一对一会话、sim schema和UI。
- 操作步骤：执行 PC CTest。
- 期望结果：全部通过，至少覆盖设计文档15.1列出的PC正常/异常路径。
- 通过标准：0失败，新增测试可在报告中定位。
- 失败标准：任一失败或关键路径无测试。
- 证据要求：CTest日志和用例清单。

### B2. Device 单元测试
- 目的：验证六态状态机、Linux调用边界、sim schema、会话和UI。
- 操作步骤：执行设备 CTest。
- 期望结果：全部通过；fake backend证明不调用AP/mDNS/UDP/listen。
- 通过标准：0失败，正常路径和至少一个异常路径覆盖。
- 失败标准：任一失败或状态机旧路径仍被调用。
- 证据要求：CTest日志和关键断言说明。

### B3. 协议契约一致性
- 目的：确认PC、设备和golden语义相等。
- 操作步骤：执行integration场景A或等价JSON语义比较。
- 期望结果：schema_version=2，命令仅五种，设备六态，IP/端口/SSID/密码常量一致。
- 通过标准：无差异。
- 失败标准：任一语义差异。
- 证据要求：protocol-diff.json。

## 9. 第三层：启动测试

### C1. PC sim offscreen 启动
- 目的：验证PC不依赖真实网卡即可完成sim热点生命周期。
- 操作步骤：以 `--backend sim --duration 3 --events-jsonl ... --sim-catalog-dir ...` 启动。
- 期望结果：顺序出现 `hotspot_ready`、`ready`、`shutdown_complete`；退出码0；结束后catalog清空。
- 通过标准：全部满足，无ERROR。
- 失败标准：崩溃、顺序错误、残留catalog/端口。
- 证据要求：stdout/stderr、事件、日志、目录清理记录。

### C2. Device sim 无PC启动
- 目的：验证找不到热点时持续扫描且可正常停止。
- 操作步骤：空catalog启动 `--backend sim --duration 3`。
- 期望结果：产生scan事件，无session_online，不启动AP，退出码0。
- 通过标准：无崩溃和旧配网事件。
- 失败标准：启动AP、进入discovery或异常退出。
- 证据要求：事件和日志。

### C3. sim 双进程完整启动
- 目的：验证新核心链路。
- 操作步骤：执行场景B。
- 期望结果：PC热点→设备扫描/STA→TCP→握手→心跳，双方正常退出。
- 通过标准：所有顺序断言通过。
- 失败标准：任一事件缺失、超时、异常退出。
- 证据要求：summary.json、双方事件/日志。

### C4. Windows 真实热点启动
- 目的：验证生产PC能力。
- 操作步骤：以Windows后端启动；从另一设备扫描SSID；检查热点适配器IPv4；确认5935监听；正常关闭。
- 期望结果：SSID可见、密码有效、IP为192.168.137.1/24、端口监听、关闭后热点停止。
- 通过标准：所有实际观察满足且日志无密码。
- 失败标准：程序回退sim、使用deprecated hostednetwork、IP错误仍继续、残留热点。
- 阻塞标准：测试机网卡/驱动/权限/系统服务明确不支持。
- 证据要求：截图、适配器/IP命令、事件、日志、操作记录。

### C5. Linux 真实设备启动
- 目的：验证生产设备能力。
- 操作步骤：Windows热点运行后，在Linux执行 `provision_device --backend linux`；观察扫描、连接、IP和session。
- 期望结果：连接精确SSID，获得DHCP地址，TCP对端为192.168.137.1:5935，建立会话并心跳。
- 通过标准：完整核心路径成功，无设备AP/mDNS/UDP调用。
- 失败标准：误连其他SSID、进入旧流程、无法会话。
- 阻塞标准：无Linux WiFi设备、nmcli或跨机环境。
- 证据要求：Linux事件/日志、`nmcli`连接信息、IP、PC侧会话事件。

## 10. 第四层：功能完整性

### D1. PC热点配置校验与fail-closed
- 操作步骤：分别使用非法SSID、错误密码、错误IP、错误端口配置启动。
- 期望结果：启动失败，无热点/TCP残留，错误不泄露密码。
- 通过标准：四种输入均正确拒绝。
- 失败标准：任一继续运行或泄露密码。
- 证据要求：退出码、事件、残留检查。

### D2. 固定IP修正
- 操作步骤：在可控Windows测试环境使热点接口初始IP不符后启动。
- 期望结果：程序只修改热点接口并复核为192.168.137.1/24；失败时关闭热点。
- 通过标准：成功修正或明确fail-closed，其他网卡不变。
- 失败标准：修改错误网卡、错误IP仍启动TCP。
- 证据要求：修改前后适配器快照。

### D2A. Linux纯STA后端无需热点root初始化
- 操作步骤：在普通用户环境创建并启动Linux backend，提供可用nmcli/STA接口但不提供root权限或hostapd/dnsmasq。
- 期望结果：后端创建成功并可扫描；不创建hotspot实例，不检查热点单实例锁，不要求hostapd/dnsmasq。
- 通过标准：scan可执行，AP相关调用计数为0。
- 失败标准：因热点root检查、hostapd/dnsmasq或热点配置失败而无法启动。
- 证据要求：Linux backend日志、进程权限和后端调用记录。

### D3. 精确SSID选择
- 操作步骤：sim或真实环境同时存在 `Modu_PC`、`Modu_PC2`、`Other`。
- 期望结果：设备只连接配置的精确SSID。
- 通过标准：没有误连。
- 失败标准：按前缀或最强信号误连。
- 证据要求：scan与connected事件。

### D4. 一对一拒绝
- 操作步骤：场景E启动第一设备上线，再启动第二设备。
- 期望结果：第二设备收到busy/single_device_only；第一设备持续在线并心跳。
- 通过标准：拒绝事件存在，第一设备无offline。
- 失败标准：替换/断开第一设备或允许两台在线。
- 证据要求：双方事件和PC日志。

### D5. 握手兼容与版本错误
- 操作步骤：合法hello和proto_ver=2探针。
- 期望结果：合法ack ok；版本错误ack fail/unsupported_protocol并关闭。
- 通过标准：字段和行为符合设计10.3。
- 失败标准：接受错误版本或无明确响应。
- 证据要求：帧探针日志。

### D6. 心跳与断线重连
- 操作步骤：正常心跳后注入TCP发送失败，恢复网络。
- 期望结果：双方offline，设备在WiFi健康时不重新扫描，退避后固定地址重连并恢复心跳。
- 通过标准：reconnect_count增加，恢复后ping/pong。
- 失败标准：进入AP/discovery、无限忙等或无法恢复。
- 证据要求：场景D summary和事件时间线。

### D7. WiFi失效降级
- 操作步骤：让当前SSID/IP失效。
- 期望结果：设备断开STA，回WIFI_SCAN；不启动AP。
- 通过标准：状态序列符合设计。
- 失败标准：继续假在线或进入旧流程。
- 证据要求：设备事件/日志。

### D8. 应用数据边界
- 操作步骤：双方发送512字节、513字节和UTF-8文本。
- 期望结果：512与UTF-8双向sha一致；513发送端拒绝且对端无rx。
- 通过标准：场景G全部断言通过。
- 失败标准：超长发送或内容不一致。
- 证据要求：事件sha和summary。

### D9. 帧健壮性
- 操作步骤：拆包、粘包、空帧、1025长度头、非法JSON。
- 期望结果：合法帧正确处理；畸形达到3次关闭对应连接，不影响后续新连接。
- 通过标准：场景H通过。
- 失败标准：崩溃、越界、全局服务不可恢复。
- 证据要求：探针结果和日志。

### D10. UI完整性
- 操作步骤：打开PC和设备UI，检查流程节点/控件/状态。
- 期望结果：PC显示热点/IP/端口和单设备；设备显示六态目标流程；无下发WiFi、设备AP、PIN、mDNS、组播文案。
- 通过标准：UI与设计一致，无异常布局。
- 失败标准：旧控件仍可操作或状态映射错误。
- 证据要求：PC/设备截图说明。

## 12. 失败与阻塞处理

- 编译/单元/sim失败：标失败，退回对应SubStage。
- Windows真实热点或Linux真实设备失败：先区分实现缺陷与环境缺失；实现缺陷退回开发，环境缺失追加当前阶段问题清单置顶并标阻塞。
- 验收标准不清：先补设计/验收文档，不得猜测通过。
- 同一修复最多重试3次，仍失败时暂停阶段并重规划。
