### 自决区（不阻塞，记录方案与理由）

#### Q-D1. 设备 MAC / device_id 来源
- 问题描述：device_hello 的 `id` 字段（MAC）与热点名 `Modu_XXXX`（MAC 后 4 位）在模拟环境中如何生成。
- 自决方案：main 按设备索引生成确定性 MAC（`02:00:00:00:00:0X` 起，OUI 用本地管理地址段避免与真实 MAC 冲突），热点名取后 4 位大写十六进制（如 `Modu_0001`）；配置可覆盖。
- 自决理由：确定性便于测试断言与日志核对；本地管理地址段（02:）符合 IEEE 保留规则。
- 置信度：97%。

#### Q-D2. host_announce 的 ip 字段在模拟环境中的值
- 问题描述：host 真实地址是 127.0.0.1，但流程语义上 host 应在目标 WiFi 下有一个局域网 IP。
- 自决方案：host 通告的 `ip` 为虚拟 IP（默认 `192.168.1.50`，可配置）；device 收到后由 sim 后端翻译为 127.0.0.1 真实连接。日志中同时打印虚拟与真实地址。
- 自决理由：保持协议字段与流程文档语义一致；翻译在抽象层完成。
- 置信度：96%。

#### Q-D3. 心跳判死参数表达
- 问题描述：流程文档判死 = 1.5 × 心跳间隔，为避免浮点（ESP32-C2 无 FPU），如何表达。
- 自决方案：参数表用 `heartbeat_dead_ms = heartbeat_interval_ms * 3 / 2` 整数运算（= 1.5 倍），配置中只写 interval，dead 由代码推导；如要独立覆盖则直接配置 dead_ms。
- 自决理由：整数运算零浮点，贴合无 FPU 芯片；推导逻辑单一。
- 置信度：98%。

#### Q-D4. WiFi reason code 模拟语义
- 问题描述：模拟环境中 STA 连接如何产生 reason code 分类（201/202/205）。
- 自决方案：sim 后端 STA 连接规则：SSID 不在虚拟网络表 → 201（NO_AP_FOUND）；密码错误 → 202（AUTH_FAIL）；剧本注入 `wifi_auth_fail` 或目标网络标记 5G → 对应失败；其余成功。device 仅消费 reason code，分类逻辑与真实 ESP-IDF 一致。
- 自决理由：reason code 语义对齐 ESP-IDF `WIFI_REASON_*`，device 代码可无缝移植。
- 置信度：96%。

#### Q-D5. 配网确认窗口（120s）与重启回滚的演示方式
- 问题描述：设备写 NVS 后 120s 内未连上 host 则回滚；Demo 如何在有限时长内演示。
- 自决方案：确认窗口参数化（演示配置压缩为 12s）；回滚演示通过剧本 `nvs_unconfirmed_reboot`（模拟设备在确认前重启：device 线程销毁重建，NVS 保留，状态机启动时检测未确认凭据并回滚到上一组）。
- 自决理由：参数压缩 + 确定性剧本即可完整验证 last-known-good 语义。
- 置信度：94%。

#### Q-D6. device 与 host 的日志模块前缀
- 问题描述：多线程日志如何区分来源。
- 自决方案：模块前缀约定：`[MAIN]`（main/剧本）、`[HOST]`（host 全部）、`[DEV:n]`（第 n 台设备）、`[SIM]`（sim 后端注入/事件）、`[NET]`（抽象层通用）；日志线程安全（CRITICAL_SECTION），时间戳毫秒。
- 自决理由：日志即验收证据，前缀约定保证可自动 grep 断言。
- 置信度：99%。

#### Q-D7. gtest 与 C 模块测试的编译边界
- 问题描述：device C 模块与 host C++ 模块分别如何接入 gtest。
- 自决方案：全部测试用 gtest（C++），device 的 C 代码以 extern "C" 编译进测试；device 内部无 C++，测试代码可访问内部符号（tests 编译时 include device 源目录 + 定义 TEST_INTERNAL）。
- 自决理由：单一测试框架统一断言与报告；C 模块保持纯 C 编译（不因测试引入 C++ 依赖到产品代码）。
- 置信度：97%。

#### Q-D8. 剧本与 host/device 的时序竞态
- 问题描述：剧本按 wall-clock 注入故障，与设备状态机的实际进度可能不同步（如设备还在配网时注入 wifi_disconnect）。
- 自决方案：剧本动作分为两类：绝对时间（at_ms）与条件触发（when: "device_state", "== ap_provision" 等）；Demo 默认剧本全部用条件触发 + 最大等待超时（等待超时则记录 WARN 继续），保证确定性。
- 自决理由：条件触发保证故障注入一定发生在目标状态，验收可断言。
- 置信度：93%。

#### Q-D9. 上位机配网客户端的 PIN 获取方式
- 问题描述：流程文档中 PIN 由用户从设备标签输入；模拟环境 host 如何获得 PIN。
- 自决方案：sim 后端提供 `sim_ap_get_pin(ssid)`（模拟"读取设备标签"），host 配网客户端自动获取并在日志打印"模拟人工输入 PIN=xxxx"；同时 device 控制台日志打印 PIN 与热点 WPA2 密码。
- 自决理由：保持 PIN 一次性语义（每次 AP 开启重新生成），仅获取方式自动化。
- 置信度：95%。

#### Q-D10. 设备限速（50 msg/s）的演示必要性
- 问题描述：设备正常流程消息量远低于 50 msg/s，限速逻辑难以自然触发。
- 自决方案：实现真实计数限速逻辑（滑动窗口），剧本可注入 `burst_send`（强制设备突发发送）以触发丢弃并记录事件日志；默认剧本不注入。
- 自决理由：逻辑真实实现 + 剧本演示，验收项可自动化。
- 置信度：95%。

#### Q-D11. host_ack 的 fw_min_req 与协议降级演示
- 问题描述：版本协商的"设备版本过低"分支如何演示。
- 自决方案：设备 fw_version 可配置（默认 1.0.0，与 fw_min_req 1.0.0 匹配）；剧本 `fw_version_old`（设为 0.9.0）触发 host_ack 带 `status=ok` + 告警日志（fw_min_req 语义为提示不阻断）；proto_ver 不匹配（配置 proto_ver=0 或 2）触发 `status=fail` 断开，事件日志记录。
- 自决理由：与流程文档 3.4 节语义一致（fw_min_req 提示不阻断，proto_ver 不符拒绝）。
- 置信度：96%。

#### Q-D12. 多设备并发配网与 busy 演示
- 问题描述：host 连接上限 16、busy 拒绝如何演示。
- 自决方案：配置设备数 > host_max_conn 或剧本 `busy_inject`（临时把上限降到已连接数）触发 host_ack busy；设备 60s 长退避后重试成功。
- 自决理由：busy 是容量保护核心语义，剧本可控演示。
- 置信度：95%。
