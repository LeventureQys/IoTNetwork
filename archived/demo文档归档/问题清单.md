#### Q2. 进程内网络模拟方式（抽象层后端形态）

- 问题描述：Demo 同一进程内让 device（纯 C）与 host（C++）"真实地"走完 配网（AP 5935 TCP）→ 服务发现（组播 5936）→ 业务连接（TCP 5935）全链路。存在三种后端形态，决定抽象层接口设计与模拟后端复杂度。
- 建议方案（推荐）：**方案 B——真实 socket 全链路 + 模拟 WiFi 介质**。配网阶段：device 在 127.0.0.1 上真实监听 TCP 端口（逻辑地址映射为 AP 的 192.168.1.1:5935），host 真实 connect 并走 auth → wifi_config → wifi_result → close_ap 全消息流；业务链路：device 真实 TCP connect 到 host，host 真实 listen/accept；服务发现：UDP 组播真实加入 `224.0.2.1:5936` 组收发；mDNS 因 Windows 原生服务注册 API（DnsServiceRegister）不稳定，sim 后端用进程内注册表模拟（host 注册 → device 查询），真实后端映射 ESP-IDF mdns 组件。仅"WiFi 热点介质"（AP 开关、热点扫描、STA 连接成功/失败、RSSI）在抽象层内用虚拟状态机模拟，可注入失败场景。这样长度前缀帧（粘包/拆包）、TCP 断线、心跳超时、重连退避、组播收发全部经过真实协议栈验证。
- 备选方案：方案 A——纯函数回调模拟（host/device 通过内存队列直接交换报文，不经过 socket，实现最快但验证不了任何真实网络行为）；方案 C——连 WiFi 介质也调 Windows WLAN API 真实切换热点（开发机需真实断网连热点，不可自动化，Windows 自动切回不可靠，风险高）。
- 风险预警：真实 UDP 组播在部分开发机/虚拟机网络可能被屏蔽，Demo 有"候选列表直连"兜底路径（缓存上次主机地址直连），保证组播不通时流程仍可走通；方案 B 的虚拟 IP 映射（192.168.1.1 等）需在抽象层中维护地址翻译表。
- 置信度：85%。
- 归入置顶原因：后端形态决定整个抽象层接口设计、sim 后端实现方式与验收方式，两种路线后续返工成本高，需用户拍板。

回复：按照建议方案来吧，目前的实现可以按照windows的方式来，但是抽象层一定要给好。

#### Q5. 依赖选型
- 问题描述：JSON、线程、测试、日志四个依赖如何选择。
- 自决方案：JSON 统一 cJSON（C99 单头文件实现，ESP-IDF 生态事实标准，host/device 共用一套序列化语义）；线程用 std::thread（仅 main 编排与 host 侧，device C 模块内零线程，单线程事件循环——贴合 ESP32-C2 单核 120MHz 资源模型）；测试 gtest（FetchContent 拉取，拉取失败则降级 CTest + 自写断言宏）；日志自研轻量 C 实现（级别/模块/时间戳/线程安全），不引入 spdlog（C 模块无法使用）。
- 自决理由：cJSON 是嵌入式 JSON 事实标准且 ESP-IDF 自带；device 单线程事件循环天然满足"线程严格区分"并可直接移植 ESP32-C2；自研日志避免依赖污染与 C/C++ 边界问题。
- 风险预警：FetchContent 需要网络，无网时用降级方案。
- 置信度：94%。

#### Q6. 网络抽象层形态：纯 C99 接口 + 后端函数表（vtable）
- 问题描述：抽象层接口如何定义，才能同时服务 C++ host 与 C device，并支持 sim / esp32c2 双后端。
- 自决方案：抽象层用纯 C99 头文件 `net_abstraction.h` 定义（接口集合见下），上下文指针 `net_ctx_t *` + 后端函数表 `net_backend_t`（vtable）实现多后端。接口集合：WiFi（AP 启停、STA 连接/断开、热点扫描、状态查询、RSSI 查询）、TCP（listen/accept/connect/recv/send/close）、UDP（组播 join/send/recv）、mDNS（服务注册/解析）、NVS 存储（blob 读写）、时间（毫秒时钟）、随机数（退避抖动）、日志。sim 后端（Winsock/POSIX，宿主机编译）与 esp32c2 后端（映射 ESP-IDF lwIP socket + esp_wifi + mdns 组件 + NVS + esp_timer，仅骨架交付不参与宿主机构建）。
- 自决理由：ESP32-C2 的 lwIP 提供 BSD socket 兼容 API，抽象层按 BSD socket 语义定义，esp32c2 后端可近乎 1:1 映射（这是抽象层能"做好"的关键）；vtable 后端模式是嵌入式可移植层标准做法；NVS/时间/随机/日志一并抽象后，device C 模块零平台依赖。
- 风险预警：接口一旦定型改造代价高，阶段二设计文档需先锁定接口契约并经用户检查。
- 置信度：90%。

#### Q7. 设备 C 模块架构：单线程事件循环 + 五阶段状态机
- 问题描述：device 侧如何组织才能满足"纯 C、可移植、单线程"。
- 自决方案：C99 单线程事件循环（poll + 定时器驱动），模块划分：五阶段主状态机、配网会话服务器（auth/PIN/wifi_config 校验/close_ap）、发现器（mDNS 查询/组播监听/候选直连三级降级）、连接与心跳（hello/ack/ping/pong）、自愈器（退避+抖动/RSSI 判定/降级链）、事件日志环形缓冲、参数表；所有 I/O 非阻塞 + 超时驱动。
- 自决理由：与 ESP32-C2（单核、576KB SRAM、无 FPU）资源模型一致；状态机 + 事件循环可原样移植到 ESP-IDF（main 换成 esp_main 即可）。
- 风险预警：单线程模型约束所有 I/O 必须非阻塞 + 超时，开发文档需写明每处超时行为。
- 置信度：92%。

#### Q17. 组播同机多 socket 绑定冲突
- 问题描述：host 与多台 device 同时 join 224.0.2.1:5936，Windows 下绑定冲突。
- 自决方案：全部使用 SO_REUSEADDR（Windows 语义允许同端口重复绑定）后再 bind + IP_ADD_MEMBERSHIP；若组播不可用（防火墙/虚拟机），由"候选列表直连"兜底（剧本可注入 mcast_block 验证）。
- 自决理由：Windows SO_REUSEADDR 支持完全重复绑定（与 Linux 语义不同但满足需求）。
- 置信度：92%。

#### Q18. 演示运行模式
- 问题描述：Demo 如何让用户/验收自动化观察完整链路与自愈行为。
- 自决方案：配置文件含"故障剧本"（scenario 数组，按时间注入 wifi_disconnect / rssi_set / mcast_block / host_stop / host_crash / wifi_auth_fail），`--duration` 控制运行时长后自动优雅退出；日志即完整链路证据。
- 自决理由：自动化验收需要确定性的故障注入与退出时机；剧本由 main 定时器执行，不侵入 host/device 线程。
- 置信度：95%。
